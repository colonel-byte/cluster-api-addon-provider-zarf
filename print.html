cluster-api-addon-provider-zarf

A Cluster API add-on provider for Zarf packages (CAAPZ). It automates the deployment, day-2 lifecycle, and one-time initialization (“seed”) of self-contained Zarf packages onto CAPI workload clusters in air-gapped enterprise environments - the Zarf analogue of cluster-api-addon-provider-helm, whose HelmChartProxy / HelmReleaseProxy split it follows.

Status: early development. The CRDs and controller are being built; nothing is released yet.

How it works

CAAPZ runs as a controller in the management cluster. A platform team declares a ZarfPackageProxy naming a package in an internal OCI registry and a clusterSelector; for every matching CAPI Cluster, the controller resolves the package to a digest, verifies its Cosign signature, and stamps a deploy Job that mounts the cluster’s kubeconfig secret, pulls the verified digest, and deploys it over the wire via Zarf’s Go SDK - the result is recorded in a per-cluster ZarfPackageRelease owned by that Cluster. The controller itself never pulls or deploys a package. The full design - dependency ordering, ApplyOnce seed packages, auto-init, non-blocking cluster deletion - is in docs/dev/architecture.md.

    signatureKeySecretRef:
      name: cosign-pubkey
  strategy: Reconcile

strategy: Reconcile keeps matching clusters converged on the declared version; strategy: ApplyOnce deploys exactly once per cluster and never re-executes, for bootstrap and seed payloads.

deletionPolicy: Delete (the default) uninstalls the package from each cluster when its release is deleted - a proxy deletion or a selector un-match; deletionPolicy: Retain orphans it there, left running and operator-owned. ApplyOnce proxies always behave as Retain - a seed cannot be un-run. Note the default’s reach: deleting a Delete proxy uninstalls its package fleet-wide.

Installation

Each release publishes the provider three ways, all carrying the same component manifest:

  • clusterctl: addon-components.yaml and metadata.yaml on the release page, fetched by name.
  • Rancher Turtles / Cluster API Operator: a CAPIProvider of type addon, from the release page, from in-cluster ConfigMaps, or from the OCI artifact at ghcr.io/colonel-byte/turtle/addon-zarf - see the Rancher Turtles guide.
  • Air-gapped: a Zarf package at ghcr.io/colonel-byte/zarf/cluster-api-addon-provider-zarf, carrying the controller image and the manifest, cosign-signed. Its optional rancher-turtle-artifacts component pre-renders the Turtles install.

The controller image is ghcr.io/colonel-byte/cluster-api-addon-provider-zarf-controller, and everything is verifiable against cosign.pub at the repository root.

Security Policy

Supported versions

This project is pre-1.0 and releases from main on every conventional commit that warrants one, so fixes land in a new minor release rather than being backported. Only the most recent release line receives security fixes; upgrade before reporting an issue against an older tag.

VersionSupported
Latest v0.x releaseYes
Any earlier releaseNo

Reporting a vulnerability

Report privately through GitHub: open a draft advisory. Do not open a public issue, and do not include a working exploit against a third party’s system.

You should expect an acknowledgement within 3 business days and an assessment – whether we consider it a vulnerability, and the severity we assign – within 10 business days. Confirmed issues are fixed in the next release, and we aim to publish the advisory within 90 days of the report, sooner when a fix is already out. You will be credited in the advisory unless you ask not to be.

Include the version you are running, the host OS, the commands that reproduce the behaviour, and what an attacker gains.

Scope

In scope: the released binary and the packages under the module root; the signing and verification path; credential handling; and the release workflow and the artifacts it publishes.

Out of scope: vulnerabilities in upstream components this project packages or depends on – report those to the project that owns them; anything that requires an attacker to already have root on the machine this runs from, which by design holds its credentials; resource exhaustion from deliberately malformed input supplied by the operator themselves; and misconfiguration of a user’s own environment.

Installing the provider with Rancher Turtles

Rancher Turtles installs Cluster API providers through the Cluster API Operator rather than through clusterctl, so on a Turtles management cluster the install path is one CAPIProvider object. Everything else about the provider - the CRDs, the controller, the flags - is the same install; this guide mirrors cluster-api-provider-cargoship’s Turtles guide, adapted to a single addon provider.

Declare the provider

The namespace is not created for you, and the operator installs the provider into the namespace of the object that asked for it. Using the one this repository’s manifests already name keeps log commands portable:

kubectl create namespace caapz-system

apiVersion: turtles-capi.cattle.io/v1alpha1
kind: CAPIProvider
metadata:
  name: addon-zarf
  namespace: caapz-system
spec:
  name: zarf
  type: addon
  version: v0.0.1
  fetchConfig:
    url: https://github.com/colonel-byte/cluster-api-addon-provider-zarf/releases

Three things in there are easy to get wrong:

  • spec.name is the provider name, not metadata.name. Turtles resolves the provider from spec.name and falls back to metadata.name only when it is unset.
  • spec.type is addon, lower-case. The ClusterctlConfig spelling below is AddonProvider instead.
  • spec.version must be semver with a leading v, and it names the release tag. A CEL rule on the CRD rejects the bare form. With fetchConfig.url pointing at the releases page, it is also the only thing telling the operator which release to read, including the metadata.yaml beside the components that carries the contract version.

Or register it centrally

Where the provider should be known to the whole cluster - or where the components come from a mirror rather than from GitHub - put the URL in Turtles’ ClusterctlConfig and drop fetchConfig from the object above:

apiVersion: turtles-capi.cattle.io/v1alpha1
kind: ClusterctlConfig
metadata:
  name: clusterctl-config
  namespace: cattle-turtles-system
spec:
  providers:
    - name: zarf
      type: AddonProvider
      url: https://github.com/colonel-byte/cluster-api-addon-provider-zarf/releases/v0.0.1/addon-components.yaml

The name and namespace are not free: Turtles merges this object into the clusterctl-config ConfigMap it ships and looks it up at that ConfigMap’s own name and namespace - cattle-turtles-system by default, rancher-turtles-system on older installs. One created anywhere else is read by nothing, and nothing says so. Ask the cluster rather than guessing: kubectl get configmap clusterctl-config --all-namespaces.

Air-gapped, from ConfigMaps

fetchConfig takes a selector instead of a url, and then the operator reads the components and the metadata out of a ConfigMap in the cluster - no route to GitHub, no mirror standing in for it. On the connected side, download addon-components.yaml and metadata.yaml from the release; inside:

kubectl create configmap v0.0.1 --namespace caapz-system \
  --from-file=components=addon-components.yaml \
  --from-file=metadata=metadata.yaml
kubectl label configmap v0.0.1 --namespace caapz-system provider-components=addon-zarf

Then the CAPIProvider loses fetchConfig.url and gains the selector:

  fetchConfig:
    selector:
      matchLabels:
        provider-components: addon-zarf
  • The ConfigMap’s name is the version the operator offers, unless a provider.cluster.x-k8s.io/version label says otherwise - and it has to match the CAPIProvider’s spec.version.
  • The label is yours. provider-components is only the convention the operator’s examples use; nothing reads the key, the selector just has to match.
  • The components still name a ghcr.io image. Mirror the controller image and override the registry through the CAPIProvider’s configSecret, whose images key the operator reads as a clusterctl image override.

Or let the Zarf package carry it

The ConfigMap and the CAPIProvider are pre-rendered into the air-gapped Zarf package as its rancher-turtle-artifacts component - nothing to assemble on the inside:

zarf package deploy zarf-package-cluster-api-addon-provider-zarf-amd64-0.0.1.tar.zst \
  --components rancher-turtle-artifacts

It is optional, so it has to be named - zarf package deploy --confirm skips every optional component without a word, and a cluster installing with clusterctl wants exactly that. And Rancher Turtles has to be on the cluster first: a CAPIProvider applied where the Turtles CRDs are missing fails the component, and with it the deploy.

Air-gapped, from a registry

fetchConfig.oci is the third option, for the air gap that already has a registry: the operator pulls metadata.yaml and the components out of one OCI artifact. Every release publishes it at ghcr.io/colonel-byte/turtle/addon-zarf, tagged with the release’s own tag and cosign-signed by digest. Mirror it with oras cp, or - where the connected side cannot reach the mirror either - build it as a file to carry in:

go run ./magefiles/core release:ociArtifact v0.0.1

That writes an OCI image layout to out/oci and tars it beside it; nothing is pushed, deliberately. Fill the mirror on the inside with oras cp --from-oci-layout, then point the CAPIProvider at it:

  fetchConfig:
    oci: registry.internal/caapz/capi-provider

A reference with no tag takes spec.version as the tag. A registry served over plain HTTP needs an http:// prefix, which is how the operator decides to skip TLS. Registry credentials come from the configSecret’s OCI_USERNAME/OCI_PASSWORD variables, not from a pull secret. The layer names inside the artifact are the operator’s typed lookups - addon-components.yaml, metadata.yaml - carried in each layer’s title annotation, which is the only thing the operator reads a layer by.

Check it came up

kubectl get capiproviders --all-namespaces

The row reaches Ready in Phase, with zarf as ProviderName and the release tag as InstalledVersion. A row stuck in Provisioning is the operator failing to fetch or apply the components, and its reason is in the Turtles controller’s log rather than on the object.

What this does not solve

clusterctl and Turtles are two ways to install the same component manifest, and installing with one leaves the other unaware. If the provider was installed with the Zarf package’s default component instead, Turtles does not manage it and kubectl get capiproviders shows nothing - deploy the next package to upgrade, or delete it and declare the CAPIProvider to hand it over. On a Turtles cluster, the selector or OCI routes above are the better air-gapped options, because what they install is still a provider Turtles manages.

docs/dev/

Pages for the person changing this project: how it builds, how it is tested, how a release is cut, and what the task runner does. The audience is a contributor with the repository checked out, which is what separates this directory from docs/guides/.

What belongs here

  • Build flags, and what each one measured. The flags a release is built with are not obvious from the code, and a size or performance number compared against a baseline built with different flags is worse than no number at all. A page here is the one safe reference for how to produce a comparable build, and the rule is to read it rather than to remember the flags.
  • The test harness. What each suite covers, what it needs installed, and - the part that actually gets people - what each backend or environment does not exercise. A suite that skips fifteen steps because the environment cannot reach them is not a pass, and the page saying so is what stops it being read as one.
  • The task runner reference. One entry per target, what it reads and what it writes. Several rules in the root AGENTS.md and in docs/AGENTS.md defer to this page for which target regenerates what.
  • Release mechanics, where they go beyond what docs/workflows/ covers - the artifact set, the signing keys, how to run the release tooling locally without cutting a release.

Two things to get right

  • Name the forbidden invocation, not just the right one. A page that says how to run the tests and not which invocation pulls in the suites that need real infrastructure gets the wrong one run first. The root AGENTS.md carries the short version; this is where the reason lives.
  • A measured number needs the date and the method. Every count, size, and pin in a tree defaults to having been measured once and never again. Say what was measured, with what flags, against what baseline - and re-measure rather than quoting an earlier run, since toolchain and dependency drift move absolute numbers with nobody editing a file.

What does not belong here

Operator-facing walkthroughs are docs/guides/. The reasoning behind a decision - as opposed to the mechanics of a process - is docs/agent/; a choice-*.md explains why the build does an odd thing, while a page here explains how to do it.

Six workflows ship with this template: check-go-mod, codeql, commitlint, pre-commit, scan-lint, and scorecard, plus the two release workflows. Nothing runs the tests, because a test workflow for a repository with no tests is a green check that means nothing.

  2. A page under docs/workflows/ named after it - required by .github/AGENTS.md, then go run ./magefiles/core generate:document to put it in the summary.
  3. The Which CI job dropdown in .github/ISSUE_TEMPLATE/01-failing-build.yml, which lists the name: a workflow shows in the checks list. That one goes stale silently.

Unit tests

Triggers on pull_request and merge_group, checks out, setup-go with go-version-file: go.mod, and runs the suite. Four decisions to make deliberately:

  • Name the packages, or name the exclusion. go test ./... picks up magefiles/ at the root, which cannot build outside mage. Either list the package paths or pass -short and let the suites gate themselves.
  • -short is not optional once there are e2e suites in the module. Without it, a unit-test job pulls in suites that want Docker or a cluster and either hangs or fails for reasons that have nothing to do with the change. This is the rule the TEMPLATE: stub in the root AGENTS.md is waiting for - write it there too, naming the forbidden invocation.
  • Build offline, like every other job. GOFLAGS=-mod=vendor, GOPROXY=off. A test run that silently reaches a proxy hides a vendor tree that is missing a file.
  • Replay the fuzz seed corpus if there are fuzz targets. go test -run=Fuzz replays the committed corpus without fuzzing, which is cheap and catches a regression on an input that already found a bug once. It is not the same as a fuzzing run, and should not be confused for one in the job name.
# The shape, not the whole file.
- name: Run unit tests
  run: go test -short -mod=vendor ./cmd/... ./internal/... ./pkg/...
  env:
    GOFLAGS: -mod=vendor
    GOPROXY: "off"

End-to-end tests

Worth writing only once there is something to drive end to end, and worth treating as the most expensive workflow in the repository - cargoship’s is 154 lines and provisions a fleet.

  • Decide what provisions the fixture, and make the job’s name say which. A suite that brings up containers, a suite that brings up VMs, and a suite that runs against hosts that already exist are three different workflows’ worth of setup, and a result is only as good as the backend that produced it.
  • Check what skipped, not just what failed. A skip on an e2e suite usually means a capability the environment does not have, and a run with fifteen of them read as a pass is the commonest way this kind of suite misleads. Make the job surface the skip count.
  • Do not make it a required status check until it is reliable. An e2e job that flakes becomes a job people merge past, which is worse than not having it.
  • Upload diagnostics on failure. actions/upload-artifact with the suite’s logs is the difference between a reproducible report and “it failed in CI”. The flaky-test issue form asks for exactly that artifact.

If the suite needs credentials or a registry, give it its own workflow rather than adding secrets to the unit-test job - a fork pull request cannot see secrets, and a unit-test job that silently degrades on forks is a check that means different things depending on who opened the pull request.

Architecture Proposal: Cluster API Add-on Provider for Zarf (CAAPZ)

Inspired by the design of cluster-api-addon-provider-helm (CAAPH), this document proposes a declarative Cluster API Add-on Provider for Zarf packages: cluster-api-addon-provider-zarf (CAAPZ).

The goal of CAAPZ is to automate the deployment, day-2 lifecycle, and one-time initialization (“seed”) of self-contained Zarf packages onto CAPI workload clusters across air-gapped enterprise environments.

1. High-Level Architecture

CAAPZ operates in the management cluster as an add-on controller. It watches CAPI Cluster resources, resolves and verifies packages in an internal OCI registry by digest, and stamps one Kubernetes deploy Job per cluster - the Job mounts that cluster’s kubeconfig and drives Zarf deployment via Zarf’s Go SDK against the workload cluster API (§6 step 6). The controller itself never deploys.

2. Declarative CRD Design

CAAPZ separates cluster selection and configuration templates from per-cluster release status tracking, following CAAPH’s HelmChartProxy / HelmReleaseProxy pattern.

A. Cluster-Wide Proxy: ZarfPackageProxy

Managed on the management cluster to declare desired package states across matching clusters:

apiVersion: addons.colonel-byte.dev/v1alpha1
kind: ZarfPackageProxy
metadata:
  name: security-baseline
  namespace: fleet-default
spec:
  # Cluster matching
  clusterSelector:
    matchLabels:
      environment: production
      cargoship.colonel-byte.dev/profile: mission

  # Package source specification
  package:
    repository: zarf-docker-registry.zarf.svc.cluster.local:5000/packages/security-baseline
    version: "1.4.2"
    # Cosign signature verification before extracting/applying
    signatureKeySecretRef:
      name: cosign-pubkey

  # Deployment strategy: Reconcile (continuous) vs ApplyOnce (seed)
  strategy: Reconcile

  # Explicit dependency ordering across ZarfPackageProxies
  dependsOn:
    - zarf-init
    - csi-ceph

  # Zarf initialization parameters if target cluster is not initialized
  init:
    autoInit: true
    # The init package to deploy - a full package source, resolved, digest-pinned, and
    # signature-verified exactly like spec.package. Required when autoInit is true.
    package:
      repository: zarf-docker-registry.zarf.svc.cluster.local:5000/packages/init
      version: "v1.0.1"
      signatureKeySecretRef:
        name: cosign-pubkey
    # Variables for the init deploy, same semantics as spec.set (v1alpha1 packages only; the
    # upstream init package published at v1.0.1 is v1alpha1). A v1beta1 init package takes
    # init.values instead - e.g. registry.persistence.storageClass.
    set:
      REGISTRY_STORAGE_CLASS: "ceph-bucket"

  # Component filtering
  components:
    - name: agent
    - name: logging
    - name: security-rules
      flavor: enterprise-linux

  # Native zarf.dev/v1beta1 structured values override (supports CAPI templating)
  values:
    logging:
      retentionDays: 30
      storage:
        storageClassName: "{{ .Cluster.metadata.annotations['storage.infra/class'] }}"

(spec.set, the legacy variable mechanism, applies only to v1alpha1 packages and requires declaring spec.package.api: v1alpha1 - see §4C.)

B. Per-Cluster Release: ZarfPackageRelease

Created by the controller in the cluster’s namespace and owned by the target Cluster:

    - type: PackageSignatureVerified

C. Cross-Namespace Selection Is Flag-Gated, Same-Namespace by Default

By default a proxy’s clusterSelector matches only Clusters in the proxy’s own namespace, and every object reference resolves in the referrer’s namespace. This diverges from CAAPH deliberately: the controller reads and deploys with a cluster-wide role, so a cross-namespace selection is a request the controller performs with its permission, not the proxy author’s - allowing it by default would let anyone who can create a ZarfPackageProxy in a namespace they own deploy arbitrary packages onto clusters in namespaces they do not. (This mirrors cargoship’s --secret-namespaces design; see its docs/agent/choice-cross-namespace-secrets.md for the full argument.)

Two manager flags open it up, each a comma-separated namespace list where * permits any, empty (the default) permits none:

  • --cluster-namespaces - namespaces beyond its own that a proxy may select Clusters in. When a release is created in another cluster’s namespace, its packageProxyRef.namespace points back at the proxy.
  • --secret-namespaces - namespaces a proxy may name its signatureKeySecretRef in besides its own, matching cargoship’s flag of the same name.

A selection or reference into a namespace the flags do not permit is an error surfaced as a condition with reason: CrossNamespaceNotEnabled - never a quiet fallback to the local namespace, because resolving a different object than the one named is worse than refusing: it succeeds. Opening up later is a flag value; closing down later breaks every fleet that relied on it, which is the asymmetry the default follows from.

Two operational caveats, documented rather than startup-validated (a permitted-but-unused configuration should not refuse to start):

  • clusterctl move moves what a Cluster owns; a proxy or secret in another namespace is not that, and arrives missing on the new management cluster.
  • A manager whose cache is scoped to one namespace reads every cross-namespace referent as NotFound, whatever the flags permit.

3. The “Seed” Package Pattern (ApplyOnce)

An ideal capability for this architecture is supporting Seed Packages that run strictly once per imported or provisioned cluster:

Motivation

Certain foundational packages perform initialization tasks that must not be continuously reconciled or reverted on subsequent reconciliation loops, such as:

  1. One-time cluster credential seeding or bootstrap tokens.
  2. Initial root user/admin setup.
  3. Foundational certificate generation or initial storage class bindings.
  4. One-time registration or enrollment jobs.

Implementation via strategy: ApplyOnce

Borrowing from core CAPI’s ClusterResourceSet.spec.strategy, CAAPZ supports two strategies:

  1. strategy: Reconcile (Continuous Lifecycle):

    • Reacts to changes in spec.package.version, values, and variables by redeploying the package to converge the workload cluster to the new state. The package content itself is pinned by digest (see “Package identity” below); following a mutable tag is an explicit per-proxy opt-in, polled rather than watched - there is no OCI watch primitive.
    • “Drift repair” is periodic idempotent redeploy of the pinned digest on the controller’s resync interval; the Zarf SDK has no drift detection.

  2. strategy: ApplyOnce (Seed / Initialization Package):

    • When a new cluster matching the selector is discovered or imported, a deploy Job (§6 step 6) pulls and applies the Zarf package.
    • Once the deployment succeeds, the ZarfPackageRelease is marked phase: Completed and applied: true.
    • The controller will never re-execute this package against that cluster, even if the proxy’s spec or variables change.
    • Ideal for Day-0/Day-1 cluster bootstrap hooks and registration payloads.

Package identity: a tag resolves once to a digest

spec.package.version is an OCI tag, and tags are mutable; the deployed fleet must not be. So the tag is an input to resolution, not the package’s identity:

  • On first resolution - proxy creation, or any edit to spec.package.repository/version - the controller resolves the tag to its digest and records it in status.resolvedDigest. Every subsequent pull, Cosign verification, and deploy uses the digest, not the tag (Zarf resolves digest references natively), and each release records the digest it actually deployed. A re-pushed tag therefore cannot change what the fleet runs, even in principle.
  • The controller still re-checks the tag on reconcile. When the registry’s tag no longer matches the pinned digest, the proxy gets a warning condition with reason: TagContentChanged, naming both digests. Pinned deploys continue untouched; the new content is not adopted. The update path is the one that already exists: bump spec.package.version, which re-resolves and re-pins.
  • In an air-gapped registry that is periodically re-staged, a re-push of the same tag trips TagContentChanged on every re-stage. That is working as intended: the operator’s move is a version bump (or the opt-in below), never silent adoption.

Following a mutable tag is an explicit, per-proxy opt-in via annotations - an operational/dev toggle for connected test environments, deliberately kept out of the GitOps-owned spec:

ApplyOnce proxies take no part in re-resolution or tag-following: their one deploy pinned what it pinned.

The ZarfPackageRelease is a cache of the guarantee, not the guarantee itself: it is deliberately garbage-collected with its owning Cluster (§7), and a Cluster object is deleted without the infrastructure being wiped during clusterctl move and de-import/re-import - exactly the imported-cluster flows seed packages target. The durable record is the one Zarf itself writes on the workload cluster: every deploy stores a zarf-package-<name> secret (labeled package-deploy-info) in the zarf namespace, which survives management-cluster churn because it lives on the physical cluster being guarded.

So the seed check is two-tier:

  • status.applied: true on an existing release short-circuits the reconcile with no workload-cluster round trip.
  • When the release is missing or not yet applied - the only states in which a deploy would fire - the controller first probes the workload cluster for the package’s deployed-package secret. If present, the release is marked Completed/applied: true without re-executing (adoption); only a cluster with no record is seeded.

Consequences, all deliberate:

  • Re-importing a live cluster re-creates its releases but does not re-run its seed packages.
  • Hand-deleting a ZarfPackageRelease does not re-run the seed; the recreated release adopts the existing record.
  • Intentionally re-seeding takes two deletions, record first: remove the package’s record on the workload cluster (zarf package remove, or deleting the zarf-package-<name> secret), then delete the ZarfPackageRelease. The release alone is not enough - the recreated release adopts the surviving record - and the record alone is not enough either, because status.applied: true short-circuits without probing. Deleting the release before the record just re-adopts.
  • Wiping and rebuilding infrastructure behind the same Cluster object re-seeds, because the rebuilt cluster carries no record. That is the desired reading of “once per physical cluster”.

One restriction follows: Zarf only stores the deployed-package record when the package has at least one cluster-touching component, so an ApplyOnce package must include one. A pure-actions package would leave no durable record, silently degrading the guarantee to the garbage-collectable release; the controller surfaces a condition on the release when a completed seed deploy left no record behind.

Seed-then-manage handoff, and the package name as identity

A supported pattern (used by the sister ansible-collection-zarf tooling): an ApplyOnce proxy seeds a package - zarf-init, say - and a Reconcile proxy later takes over the same package name for day-2 lifecycle. This works by construction: the Reconcile path never consults the seed record, Zarf treats a same-name deploy as an in-place upgrade updating the same record, and on re-import the seed proxy adopts whatever version the successor last deployed. Two properties to hold on to:

  • Adoption is keyed on the Zarf package name on the cluster - nothing else. Not the proxy’s name, not the declared version or digest. Any ApplyOnce proxy whose package carries that name adopts the record, even if its spec declares different content. Package names are therefore an identity namespace the fleet’s conventions must own; two unrelated packages sharing a name will silently satisfy each other’s seed checks.
  • A successor proxy for a seeded package must be deletionPolicy: Retain (§8). Under the default Delete, deleting the successor runs zarf package remove on the shared package name - destroying both the package and the deployed-package record the seed’s guarantee rests on, while the seed’s release still reports Completed and its applied cache suppresses any re-seed. The cluster loses the package; nothing notices. Retain on the successor keeps the handoff safe.

Composition guidance: separate packages by default, bundle into init only for storage bootstrap

Heterogeneous fleets (one segment wants vsphere CSI, another rook-ceph) are the reason foundational packages stay separate from the init package by default - the layout the CRDs already express with no extra machinery:

  • One shared init proxy (or autoInit), identical fleet-wide; per-variant proxies (csi-vsphere, csi-rook-ceph) with disjoint clusterSelectors keyed on the cluster’s existing labels, each with dependsOn: [zarf-init]. The DAG and the init-first eligibility gate (§6) order everything; a cluster gets the variant its labels declare. Where variants share most content, Zarf flavors via spec.components let two thin proxies select from one package.
  • Bundling components into a custom init package is the escape hatch for one constraint only: storage that must exist before init can finish - Zarf’s internal registry needing a real StorageClass with nothing provisioning one pre-init. Zarf’s component import mechanism composes this (a custom ZarfInitConfig importing, say, rook-ceph’s components); the cost is per-variant init packages, paid knowingly by the fleet segment that needs it. The decision rule per segment: can init complete on this cluster’s day-zero storage? Yes - shared init, selector-driven variants. No - that segment carries a variant init package. The init package’s own storage-class knob (init.set’s REGISTRY_STORAGE_CLASS, or its v1beta1 value equivalent) bridges the two where a StorageClass exists at provision time.
  • Day-2 handoff of bundled components follows the package name, per the handoff rules above. The clean path is one Retain Reconcile proxy managing the custom init package itself - same name, same record, in-place upgrades. Splitting a bundled component out to its own proxy later changes the package name: no adoption, no shared record, and the first deploy collides with Helm releases the init components own. Zarf’s DeployOptions.TakeOwnership exists for exactly that adoption, which implies a proxy-level takeOwnership knob - not in the API today; decide whether to add it before v1alpha1 ships to real users, since the name-discontinuous handoff is impossible without it.

4. Native zarf.dev/v1beta1 Package Support

CAAPZ natively implements the modern zarf.dev/v1beta1 Zarf package schema while maintaining backward compatibility with zarf.dev/v1alpha1:

A. Native Deployment, No Conversion

  • When pulling a package from an OCI registry, CAAPZ inspects the apiVersion. A proxy may assert it up front via spec.package.api (v1alpha1 or v1beta1); when the declared version does not match the pulled artifact, the release fails with a condition before any deploy runs.
  • Packages deploy as their native schema version - CAAPZ performs no in-memory conversion. Converting a v1alpha1 package to v1beta1 before deploy would trip Zarf’s rejection of deploy-time variables on v1beta1 packages and silently break spec.set; Zarf’s deployer handles both versions natively.
  • Deprecation: v1alpha1 package support exists for compatibility and will be dropped when upstream Zarf drops v1alpha1 support. New packages should be authored as v1beta1 and configured through spec.values.

B. Hierarchical Structured Values (spec.values)

In v1beta1, Zarf supports structured values maps (analogous to Helm values.yaml). CAAPZ exposes spec.values directly on ZarfPackageProxy:

  • Values accept full YAML trees rather than only string scalars (spec.set).
  • Supports Go template substitution referencing CAPI Cluster metadata and annotations (e.g. {{ .Cluster.metadata.name }}).
  • Merged with the package’s internal defaults at deployment time.

Deferred, additive later: sourcing values from a Secret or ConfigMap (valuesFrom, CAAPH/Flux-style). The seam already exists - the deploy Job reads only the rendered deploy-spec Secret, never the proxy - so a future valuesFrom is purely a controller-side resolution step at render time, merged into the same Values/Set fields; the deploy pod and subcommand need no change, and a changed source changes the rendering, so the spec-hash redeploy path picks it up for free. Adding the optional field later is API-compatible (no version bump), and signatureKeySecretRef’s CrossNamespaceNotEnabled refusal is the reference-shape and namespace-policy precedent to reuse. The future change owes three things: ConfigMap get/list/watch RBAC (Secrets are already covered), an answer for “the referenced source changed but the proxy didn’t” (the lazy version is the periodic resync re-render, consistent with the drift-repair item owed from M3; immediate reaction needs a watch plus mapping), and precedence semantics between inline and referenced values (Flux’s “later entries win, inline wins last” is the boring default).

C. Legacy Variables (spec.set) Are Gated on a Declared v1alpha1 Package

Zarf rejects deploy-time variables (SetVariables) for v1beta1 packages, so spec.set is only valid against v1alpha1 packages - and the CRD enforces that at admission:

  • spec.package.api is an optional enum (v1alpha1 | v1beta1). Unset means “detect from the artifact”.
  • Using spec.set requires declaring spec.package.api: v1alpha1. A CEL validation rule on the CRD rejects the object at kubectl apply otherwise, turning a deploy-time Zarf error buried in a Job log into an immediate admission message. (CEL CRD validation is GA from Kubernetes 1.29, the management-cluster floor this sets.)
  • The declaration is a claim: the controller verifies it against the pulled artifact’s actual apiVersion and fails the release with a condition on mismatch, before stamping a deploy Job.
  • spec.set values support the same Go templating as spec.values, and the field is deprecated on the same schedule as v1alpha1 support itself (§4A).

D. Architecture & Flavor Auto-Detection

v1beta1 formalizes component selectors with flavor and architecture. CAAPZ automatically extracts the target cluster’s architecture from CAPI Machine specifications (amd64, arm64) and selects the appropriate component variants automatically unless explicitly overridden in spec.components.

5. Dependency Management & Execution Ordering (dependsOn)

Foundational platform services require strict execution ordering. For example, workloads cannot schedule PersistentVolumeClaims before storage drivers exist, and Zarf packages cannot deploy before the cluster has a running registry or injector:

[ zarf-init ] ──► [ csi-ceph (CSI Driver) ] ──► [ logging / monitoring ]

A. Declarative Ordering via spec.dependsOn

A ZarfPackageProxy can declare dependencies on other ZarfPackageProxy resources:

apiVersion: addons.colonel-byte.dev/v1alpha1
kind: ZarfPackageProxy
metadata:
  name: logging-stack
  namespace: fleet-default
spec:
  dependsOn:
    - zarf-init
    - csi-ceph

B. Dependency Resolution & Reconcile Gating

For each workload cluster, every entry in dependsOn is resolved to a verdict. The rule that prevents deadlock: a dependency that cannot be satisfied on this cluster is a named error condition, never a silent wait. Waiting is reserved for the one case where progress is actually coming.

  • The dependent release holds in phase: Pending with DependenciesSatisfied: False and the reason above; the message names the offending dependency.
  • DependencyNotApplicable is deliberately an error rather than auto-satisfied: declaring “X needs Y here” when Y’s selector will never match this cluster is a configuration contradiction, and silently skipping the ordering would hide exactly the label mistake the admin needs to see.
  • All verdicts are level-triggered: fixing labels, creating the missing proxy, or the dependency deploying re-evaluates the dependent with no operator intervention. Re-evaluation is watch-driven - the proxy reconciler watches ZarfPackageRelease phase changes and maps them back to dependents - with the periodic resync as backstop; there is no requeue polling loop.
  • A dependency proxy deleted after its ApplyOnce package seeded a cluster reports DependencyNotFound, even though the package is on the cluster. This is strict on purpose - keep proxies that the dependency graph references. (Softening it by probing the workload cluster’s deployed-package record (§3) is a possible later relaxation, not a commitment.)

C. Circular Dependency Detection

Directed Acyclic Graph (DAG) validation runs at reconcile time, not admission - cross-object graph checks cannot be expressed in CEL, and a validating webhook is not worth its cert plumbing in air-gapped installs when admission-time validation can be invalidated by the very next edit to a different proxy anyway. Each reconcile builds the dependency graph from the namespace’s proxies (informer cache, no API round trips) and runs a cycle check; every proxy in a detected cycle gets DependenciesValid: False, reason: DependencyCycle and deploys nothing until the cycle is broken.

6. Reconcile Workflow

  1. Cluster Discovery: The controller watches for CAPI Cluster resources reaching status.initialization.controlPlaneInitialized == true (the v1beta2 initialization signal, surfaced by the ControlPlaneInitialized condition) and matching spec.clusterSelector.

  2. Kubeconfig Resolution: CAAPZ retrieves the cluster’s administrative kubeconfig secret (<cluster-name>-kubeconfig) using CAPI’s cluster client cache.

  3. Seed Check: If spec.strategy == ApplyOnce, skip execution when the release is already applied: true. Otherwise probe the workload cluster for the package’s zarf-package-<name> deployed-package secret in the zarf namespace; if present, mark the release Completed without deploying (see §3, “Where the ‘never re-execute’ record actually lives”).

  4. Digest Resolution & Signature Verification: The controller resolves the tag to its pinned digest (status.resolvedDigest, §3) and, if signatureKeySecretRef is set, verifies the Cosign signature against that digest in the controller, at resolution time - a manifest-and-signature read against the registry, not a package pull, so the controller needs no package-sized disk. The deploy Job later pulls that verified digest: content addressing makes the verified artifact and the deployed artifact the same bytes. Verification binds to the digest, so a re-pushed tag never inherits a prior verification. See docs/agent/choice-deploy-job.md for why verification sits here rather than in the Job.

  5. Auto-Init Check: If spec.init.autoInit == true, the controller probes the target cluster for Zarf state (zarf-state secret in the zarf namespace) at deploy-prep, and only an absent state triggers an init deploy. Auto-init is keyed on observed cluster state, never on a package or proxy name - so it commutes with a fleet that manages init through its own proxy (the §3 seed-then-manage handoff): whoever initialized first, the probe finds the state and auto-init no-ops. When both are declared, dependsOn naming the init proxy is the deterministic ordering; the remaining concurrent-first-deploy race is closed structurally by step 6’s one-Job-per-cluster rule. Init-first is an eligibility gate, not a priority: on a cluster with no Zarf state, the only releases eligible for a Job slot are init-capable ones - a package that resolves as an init package (kind: ZarfInitConfig, read at resolution) or a proxy with autoInit: true; everything else holds in Pending with condition reason WaitingForZarfState rather than failing inside a Job. With step 6’s one-Job-per-cluster rule, “the init package deploys first” is therefore an invariant, not a scheduling preference.

    The auto-init deploy path. spec.init.package names the init package - a full package source (repository, version, optional api claim and signatureKeySecretRef), required when autoInit: true. The controller resolves and verifies it exactly as step 4 does the main package - pinned to status.initResolvedDigest/initResolvedRef, surfaced on the InitPackageResolved condition - and additionally refuses an artifact that does not resolve to kind: ZarfInitConfig. On a state-less cluster, an autoInit release stamps an init Job: the step 6 Job contract verbatim (same image, kubeconfig, cache volume, deploy subcommand) with an -init name suffix, reading init-spec.yaml rendered into the release’s deploy-spec Secret beside the main spec. The init Job takes the one-Job-per-cluster slot like any other Job, so two autoInit proxies racing on a fresh cluster serialize, and the loser’s next probe finds the state and no-ops - the commuting property above, preserved. Success leaves no status record beyond the probe finding state (the zarf-state secret is the record, and Zarf keeps its own deployed-package record for the init package); the controller deletes the finished Job and the release proceeds to its normal deploy on the next pass. Failure surfaces as Ready: False, reason: InitFailed with the pod’s error, and retry is edit-to-retry via the init spec hash - the same stance as deploys. The proxy’s own package never takes the slot while state is absent: autoInit makes the init Job eligible, not the main package. A proxy whose main package itself resolves as ZarfInitConfig needs no autoInit - it is init-capable as-is, and deploying it initializes the cluster. spec.init.values and spec.init.set pass through to the init deploy exactly as the proxy-level fields do to the main one - same {{ .Cluster... }} templating, same v1alpha1-only rule for set (keyed on init.package.api) - so there is no dedicated storage-class field: it is the REGISTRY_STORAGE_CLASS variable in the v1alpha1 init package upstream publishes at v1.0.1, or the registry.persistence.storageClass value in a v1beta1 one. CAAPZ never removes an init package it auto-deployed - deletionPolicy governs spec.package only.

  6. Deploy Execution (the deploy Job): Render values and variables ({{ .Cluster.metadata.name }}) and stamp one Kubernetes Job per release - a deploy never runs in the controller process. The Job’s contract, which §4C, the Signature Trust Model, and §8A reference:

    • It runs the controller’s own image (or spec.deployJob.image) with a deploy subcommand. The pod acts as a pure operator: its entire input is files on disk - a rendered deploy spec the controller writes to a per-release Secret and mounts (package repository pinned by digest, rendered values and variables, component selection), the kubeconfig, and the cache. It holds no management-cluster credentials and makes no management-cluster API calls; the subcommand assembles packager.DeployOptions from the spec file alone.
    • Results return in the pod’s termination message; the controller reads the finished Job and patches ZarfPackageRelease.status. The deploy pod’s service account grants nothing.
    • The target cluster’s <cluster-name>-kubeconfig secret is mounted and KUBECONFIG points at it - the Zarf SDK resolves its target from the process environment, so the pod’s environment is what selects the cluster. No mutex, no serialization: deploys to different clusters are different pods.
    • The package is pulled inside the Job by the verified digest from step 4 (repository@digest, never a tag) into the Job’s zarf-cache volume (default emptyDir, PVC-replaceable via spec.deployJob.volumes).
    • The pod runs a restricted security profile by default; spec.deployJob exposes the knobs (service account, security contexts, volumes and mounts, node selector, tolerations). A package action - arbitrary command execution - is thereby contained to a pod holding one cluster’s kubeconfig, not the fleet-wide controller.
    • backoffLimit: 0: the controller owns retries, so the release stays the single record of attempts. The Job is controller-owned by its release and garbage-collects with it; a removal Job (§8) reuses this same contract with a remove subcommand.
    • One Job per cluster at a time. Upstream Zarf recommends a single package operation per cluster with current tooling, so the controller stamps at most one deploy or removal Job per target cluster; further ready releases hold in phase: Pending with condition reason WaitingForActiveDeploy until the slot frees. This holds even where the dependency DAG (§5) would permit parallelism - the DAG decides who goes next, never simultaneity - and it is what closes step 5’s double-init race without naming conventions. Parallelism across clusters is unaffected. A CAPI Cluster annotated addons.colonel-byte.dev/concurrent-deploys: "true" opts that cluster out of the serialization, for when tooling or operator confidence allows it; the annotation lives on the Cluster because concurrency tolerance is a property of the target, not of any one proxy. Bounded concurrency - the annotation carrying a slot count rather than a boolean - is deliberately deferred to a later phase of the controller; "true" is specified to leave room to grow into an integer without breaking existing annotations. Why a Job rather than the in-process SDK - and why verification precedes it - is recorded in docs/agent/choice-deploy-job.md.

  7. Status Update: Update ZarfPackageRelease.status and surface condition Ready: True on the release and proxy objects.

Signature Trust Model

signatureKeySecretRef adopts the sister cargoship repository’s semantics verbatim (its signatureKeySecretRef field and the reasoning in its doc comment):

  • The reference names a Secret whose cosign.pub key holds the Cosign public key. It resolves in the proxy’s namespace unless --secret-namespaces permits another (§2C), which is what bounds “anyone who can edit the proxy picks the key”: a proxy author can only name keys their own namespace holds.
  • Empty verifies nothing. A signature with no key to check it against is not verification, so the controller logs that it could not verify and deploys anyway - for a signed package exactly as for an unsigned one. The PackageSignatureVerified condition is absent, not True.
  • Naming a key makes verification a precondition. An unsigned package, a signature the key does not verify, and a signature in a form that cannot be checked are all refused, and the refusal comes out of digest resolution in the controller (§6 step 4) - before a deploy Job is ever stamped, so unverified content never reaches a pod holding a cluster’s kubeconfig. The Job then pulls the verified digest; content addressing makes what was verified and what is deployed the same bytes. Verification binds to the pinned digest (§3), so a re-pushed tag never inherits a prior verification.
  • Rotation is a Secret edit. Verification runs on the passes that deploy, against the key as it currently reads, so a rotated key takes effect on the next reconcile and a Secret deleted under a converged fleet is reported as a failed precondition rather than noticed the next time something changes.
  • Fleet-wide enforcement is deliberately deferred. Per-proxy keys match the sister repository’s model; a controller-level --require-signature flag (refuse any proxy with no key named) is the natural later addition if an environment needs “no unverified package, ever” as policy rather than convention.

7. Non-Blocking Cluster Deletion & Lifecycle Safety

A critical architectural pitfall in add-on controllers (including earlier versions of CAAPH) is hanging or blocking cluster deletion when a workload cluster is destroyed. CAAPZ explicitly avoids blocking cluster deletion:

A. Non-Blocking Finalizer Policy

  • No Blocking Finalizer on the CAPI Cluster: CAAPZ does not install a finalizer on the CAPI Cluster resource itself. When an operator or automation deletes a CAPI Cluster, CAPI begins tearing down the infrastructure and VMs immediately.
  • Immediate Reconcile Termination on Deletion: If Cluster.DeletionTimestamp.IsZero() == false, CAAPZ immediately halts any pending deployments, releases any local mutexes or downloads, and exits without attempting to connect to the dying cluster.
  • Cascade via Kubernetes ownerReferences: The per-cluster ZarfPackageRelease CR carries a standard ownerReferences pointing to the CAPI Cluster. When the Cluster is deleted, Kubernetes garbage-collects the ZarfPackageRelease automatically via background cascading deletion.

B. Graceful Degradation on Unreachable Clusters

  • When an infrastructure provider tears down VMs (or when connectivity to the workload API drops), attempts to uninstall or communicate will fail (connection refused or context deadline exceeded).
  • CAAPZ treats cluster deletion as an infrastructure-level wipe for teardown purposes: attempting an orderly Zarf uninstall over the wire is neither necessary nor desirable, and the controller discards its state without blocking CAPI or Machine deletion. But Cluster-object deletion is not always an infrastructure wipe - clusterctl move and de-import/re-import delete the object while the cluster lives on - which is why the ApplyOnce guarantee is anchored on the workload cluster itself rather than on anything garbage-collected in this cascade (§3).

8. Uninstall Semantics & Deletion Policy

§7 covers the cluster going away; this section covers the declaration going away while the cluster lives on: a ZarfPackageProxy is deleted, or a cluster’s labels change so the selector no longer matches it.

A. spec.deletionPolicy: Delete | Retain

The proxy declares what happens to its deployed packages when their release is deleted:

  • Delete (the default, matching CAAPH): the package is uninstalled from the workload cluster - via packager.Remove, run in a removal Job on the same plumbing as deploys (§6’s deploy Job: same image, kubeconfig mount, cache volume, and deployJob knobs) - before the release object is allowed to go away.
  • Retain: the release object is deleted immediately and the deployed package is orphaned on the workload cluster, left running and operator-owned from then on. The honest choice for large or foundational packages, where an in-place uninstall is unreliable and an orphaned-but-working package beats a half-removed one.
  • ApplyOnce proxies ignore the policy and always behave as Retain: a seed cannot be un-run, and its durable record lives on the workload cluster (§3) regardless of what happens to management-cluster objects.
  • A Reconcile proxy managing a package an ApplyOnce proxy seeded must also be Retain: Delete on the successor removes the shared package name’s deployed-package record along with the package, silently voiding the seed guarantee while the seed’s release still reports Completed - see §3’s seed-then-manage handoff.

B. Mechanics: a finalizer only where a removal is owed

  • Releases under Delete carry a CAAPZ finalizer; the controller runs the removal Job and drops the finalizer on success. Releases under Retain (and all ApplyOnce releases) carry no finalizer at all, so their deletion can never block on anything.
  • The finalizer’s presence tracks the proxy’s current policy: flipping a proxy between Delete and Retain adds or strips the finalizer on its releases on the next reconcile, so the policy is live-editable and acts as the declarative break-glass for a stuck removal.
  • Proxy deletion: a finalizer on the proxy deletes its releases (found via spec.packageProxyRef) and waits for them to finish their own finalization before the proxy goes away. Releases are deliberately not owner-referenced to the proxy: Kubernetes garbage collection only deletes a dependent once all of its owners are gone, so a second ownerRef would stop Cluster deletion from collecting releases and quietly break §7’s cascade. The Cluster stays the sole owner.
  • Selector un-match: the controller deletes the no-longer-matching release, and the same finalizer path decides whether that is an uninstall (Delete) or an orphan (Retain).

C. The §7 override: cluster teardown always wins

If the release’s owning Cluster has a deletion timestamp, no longer exists, or is unreachable, the finalizer is dropped without attempting removal. Uninstall semantics never block or delay cluster deletion; §7 outranks this section wherever they conflict.

When removal fails while the Cluster is alive and reachable, the controller requeues with backoff and surfaces a RemovalFailed condition on the release. The operator’s escape hatches, in preference order: flip the proxy to Retain (declarative, affects all its releases), or remove the finalizer by hand (surgical, one release).

D. Known limitation: shrinking spec.components

Removing an entry from spec.components does not remove that component from the workload cluster - a redeploy with fewer components leaves the extras running. Removed components are orphaned until the package is removed and redeployed. Per-component removal choreography is deliberately out of scope until a real need arrives.

9. Clusterctl Provider Contract

CAAPZ ships as a clusterctl-manageable provider, the same way the sister cargoship repository does:

  • metadata.yaml at the repository root maps each release series to its Cluster API contract (v1beta2). Release-please owns the current series entry via x-release-please-major/-minor markers; past series are appended as releases are cut so clusterctl upgrade can map an installed version. Without this file, clusterctl init refuses to install the provider.
  • Provider labels - clusterctl.cluster.x-k8s.io: "" and cluster.x-k8s.io/provider: addon-zarf - go on every manifest in the release bundle, so clusterctl can find and manage what it installed. They land with the manager deployment manifests.
  • clusterctl move: ZarfPackageProxy and ZarfPackageRelease carry the clusterctl.cluster.x-k8s.io/move label so a pivot carries the declarations to the new management cluster. Releases are re-derivable (the controller re-stamps them from proxies and Clusters), but moving them preserves status history and avoids a re-deploy window; proxies are not re-derivable and must move. The ApplyOnce guarantee survives either way - it lives on the workload cluster (§3), not in anything being moved. The §2C caveat stands: a cross-namespace secret is outside what move carries.

10. Enterprise & Air-Gap Advantages

  • Air-gap Compliant: Zarf packages bundle container images, Helm charts, and manifests together in an OCI artifact, eliminating out-of-band image syncing.
  • Supply Chain Security: Cosign signature verification occurs on the management plane before any package payload touches the remote workload cluster.
  • Native CAPI Integration: Works across all CAPI infrastructure providers (vSphere, AWS, Azure, bare-metal) and bootstrap providers (Cargoship, RKE2, Kubeadm).

E2E testing: the kind + CAPD topology

The end-to-end suite runs the things test:envtest structurally cannot: real CAPI lifecycle machinery (a control-plane provider flipping ControlPlaneInitialized, the <cluster-name>-kubeconfig secrets CAPI writes, garbage-collection cascades), pods actually scheduling, and an OCI registry reachable from every side of the topology. It stands up a kind management cluster with CAPI core + CAPD initialized into it, one CAPD workload cluster, and a ghcr.io/distribution/distribution:3 registry on the kind docker network, then runs the suite in the separate test/e2e module against all of it.

go run ./magefiles/core e2e:up     # kind + clusterctl init + CAPD workload cluster + registry
go run ./magefiles/core e2e:run    # the suite, against the running topology
go run ./magefiles/core e2e:down   # removes everything, including the CAPD machine containers

e2e:up is idempotent and resumable - a failed run is re-runnable and picks up where it stopped. The suite does not tear the topology down; iterate on tests against a long-lived topology and run e2e:down when finished.

The forbidden invocation: a bare go test inside test/e2e/. The suite talks to a live topology through E2E_KUBECONFIG, which only e2e:run sets - without it every test skips, and a fully-skipped suite reads as green while asserting nothing. test/e2e is its own Go module precisely so the root go test ./... can never reach it; it is also deliberately unvendored, see the exception note in magefiles/AGENTS.md.

Host prerequisites

docker, kind, and kubectl on PATH, network access (kind node images, the clusterctl binary, provider manifests), and one pair of kernel settings that is easy to miss:

Raise the inotify limits before the first e2e:up

kind’s own known-issues page documents this, and this repository has hit it: on a stock Linux host, fs.inotify.max_user_instances (often 128) is exhausted by a kind cluster running beside anything else that watches files - another local cluster, an editor, a file sync. The failure does not name inotify: pods on the fresh management cluster crashloop, and kubectl logs on kube-proxy (or cert-manager, or local-path-provisioner) shows

"command failed" err="failed complete: too many open files"

The fix, once per boot:

sudo sysctl -w fs.inotify.max_user_watches=524288 fs.inotify.max_user_instances=512

To make it survive reboots, persist it as a sysctl drop-in:

printf 'fs.inotify.max_user_watches = 524288\nfs.inotify.max_user_instances = 512\n' | sudo tee /etc/sysctl.d/99-kind-inotify.conf
sudo sysctl --system

The crashlooped pods recover on their own next restart once the limits are raised - no need to recreate the cluster.

New repository checklist

Generating a repository from a template copies files, not settings. Everything in this template is a file, so it all arrives; everything in the Settings tab does not, and several of the files that arrive are inert until a matching setting exists. A CODEOWNERS that requires nothing and a workflow that goes green while the site 404s both look fine from the file list.

Two more things about generation, both easy to be surprised by: the new repository starts with a single initial commit - no history, tags, releases, or issues - and there is no ongoing link to the template. Nothing syncs a later template improvement forward; it has to be copied by hand.

First run, in order

Each step fails in a way that looks like the one before it, so do them in this order:

  1. Push to main. This is what first runs scorecard.yaml and deploy-book.yaml, and what gives the badges something to resolve against.
  2. Dispatch Renovate with dryRun: true. The log lists every update it resolved without touching the repository - see renovate.md. A bad customManagers regex matches nothing and reports success, so this is the run that tells you.
  3. Open a throwaway pull request. Five checks should appear: Validate Lint, Validate pre-commit hooks, CodeQL, PR Title Check, Check for go mod changes. A check that does not appear is a workflow whose trigger or filename is wrong, not a flake.
  4. Mark the checks required, once they pass. Until then commitlint.yaml’s merge_group branch does nothing, and CODEOWNERS is a suggestion.
  5. Let release-please open its first pull request. Merging it pushes the first tag, which is what release.yaml fires on, and what turns the Latest Release badge from no releases into a version.

Check for go mod changes

.github/workflows/check-go-mod.yaml is what makes the vendored, offline build a requirement rather than a convention. It runs on every pull request and on the merge queue, and it fails for one reason: go.mod, go.sum and vendor/ do not agree with each other.

The two steps

  • go mod tidy, go mod vendor, then git diff --exit-code go.mod go.sum vendor/. Re-resolves the graph and re-vendors from scratch, then fails if the result differs from what was committed. This catches a dependency added without running mage dev:vendor, and a vendor/ left behind by a hand-edited go.mod.
  • go run ./magefiles/core dev:verifyVendor. Runs go mod verify, then builds with GOFLAGS=-mod=vendor GOPROXY=off - the invocation a release has to survive. This catches a vendor tree that is internally consistent but incomplete.

The go run ./magefiles/core form rather than mage: same targets, builds from vendor/, needs no mage binary on the runner.

Why both

They fail on different mistakes, and the second is the one that costs an afternoon. A vendor/ missing a file still builds locally, because the file is on disk - it is only a fresh clone that notices. The commonest cause is not a forgotten go mod vendor at all, but a .gitignore pattern that quietly excluded part of the vendor tree; see “A new .gitignore pattern can silently empty part of vendor/” in magefiles/AGENTS.md.

That check is one command, and it is worth running by hand when a pattern changes:

git ls-files --others --ignored --exclude-standard -- vendor/

It should print nothing.

When it fails on a bot’s pull request

A dependency update re-vendors as part of the change, so the first step passes. Where it does not - a module that moved import paths, say - the fix is a human running mage dev:vendor on the branch, not a rerun.

CodeQL

.github/workflows/codeql.yaml runs GitHub’s CodeQL analysis on pushes to main, on pull requests, on the merge queue, and weekly. Results land in the repository’s Security tab. The weekly run is not redundant: it picks up queries and advisories published after a commit landed.

Two languages are analyzed, with different build modes:

LanguageBuild modeWhat that means
gomanualThe workflow’s own go build decides which packages get extracted
actionsnoneThe workflow files themselves are scanned, no build involved

The Go build step is the package list

This is the part that needs maintaining. Because Go is analyzed by building it, CodeQL’s paths-ignore setting does not apply - it has no effect on Go - so every exclusion has to be expressed as the set of packages the build step names.

Today that is ./magefiles/pkg/... and nothing else, because magefiles/*.go is package main behind //go:build mage and mage supplies the main function at runtime, so go build cannot compile it at all. ./... would pick it up and fail.

Widen the list one package at a time as the repository grows - ./cmd/..., ./internal/..., ./pkg/..., and . for a root package. A pattern matching no package fails the build step, so adding a path before the package exists breaks the scan rather than skipping it.

It builds offline, like everything else

GOFLAGS=-mod=vendor, GOPROXY=off, GOSUMDB=off, GOTOOLCHAIN=local. Everything the build needs is vendored, so an accidental network access fails fast rather than quietly succeeding on a runner and failing in an air-gapped build. This matches the environment check-go-mod.yaml enforces.

Permissions

security-events: write to upload the results, actions: read for the actions language to read workflow files, and packages: read for any private module the build resolves. All three are on the job, not the file - see .github/AGENTS.md, where a top-level write zeroes Scorecard’s Token-Permissions check.

PR Title Check

.github/workflows/commitlint.yaml lints the pull request title against conventional commits. It is a standard across the organization, and it is load-bearing rather than cosmetic: pull requests are squash-merged, so the title becomes the commit message on main, and release-please reads those messages to decide the next version and to write CHANGELOG.md. A title with the wrong type produces a release with the wrong version number.

This is why the job lints the title and not the commits. wagoid/commitlint-github-action lints commit messages, which are the ones squashing throws away, so it is not a drop-in replacement for this step.

The two configs

FileApplies toDifference
.github/commitlint/.commitlintrc.yamlHuman authorsheader-max-length of 100
.github/commitlint/.commitlintrc.bot.yamlAny author whose login ends [bot]header-max-length off

A bot cannot shorten a module path, and build(deps): bump <module> from X to Y runs past 100 characters for any dependency with a long import path. Turning the rule off for everyone would lose the one thing it buys - a readable git log - so it is off for bots only, and every other rule still applies to them.

The two files must stay in step on every rule but that one. Commitlint cannot extend a YAML sibling, so there is no shared base and the duplication is real; a rule added to one and not the other is a rule humans or bots quietly escape.

Why the bot match is a suffix, not a name

The author switch matches *[bot] rather than a list of names. Self-hosted Renovate opens pull requests as whichever GitHub App minted its token - see renovate.md - so the name is not knowable from inside this file, and a hard-coded one fails by silently linting a bot’s title against the strict config. The suffix is assigned by GitHub and cannot be spoofed by a human account.

It reports success on merge_group

The job is intended to be a required status check, which means the merge queue waits for a title_check result on the merge_group ref as well. There is no pull request under that event, so every step is skipped and the job passes - the title was already linted on the pull request that got queued. Skipping the whole job instead would leave the check with no result at all, which blocks the queue forever.

The same reasoning applies to bots: the job runs for them with a laxer config rather than being skipped, because a skipped job produces no result for a required check.

Bumping commitlint

package.json and package-lock.json in .github/commitlint/ pin @commitlint/cli and @commitlint/config-conventional, and the workflow runs npm ci, so the lockfile is what is installed. Renovate’s npm manager owns both - there is no bump procedure to follow by hand.

Validate pre-commit hooks

.github/workflows/pre-commit.yaml runs the hooks from .pre-commit-config.yaml over the whole tree with prek, on every pull request and on the merge queue.

It exists because the root AGENTS.md tells everyone to run the hooks before committing and nothing otherwise checks that they did. It also closes a gap the hooks have by design: a hook that reads the staged diff only sees uncommitted changes, so a clean local run says nothing about code that is already committed. --all-files here does.

What it skips, and why

HookWhy it is skipped
docs-generatorIt regenerates files rather than checking them, so in CI it would report a diff it created itself
golangci-lintAlready covered by Validate Lint, at the same pinned version. Running it twice doubles the slowest job

markdown-table-padding and verify-vendor are deliberately not skipped. Both are checks rather than rewrites, and the table check is not covered anywhere else.

setup-go before prek is not optional

The repo: local hooks are language: system and shell out to the Go toolchain. Without Go on PATH they fail as “command not found”, which reads like a broken hook rather than a missing toolchain - so the workflow installs Go from go-version-file: go.mod before prek runs.

Reproducing a failure

The same command, locally:

prek run --all-files --skip docs-generator --skip golangci-lint

prek and pre-commit read the same config, so either works; prek is faster. Several of the hooks rewrite files, so re-stage after a run - and if the failure is only in CI, check the hook versions in the config are the ones installed locally.

Release Please

.github/workflows/release-please.yaml runs on every push to main and keeps one open pull request - the release PR - with the next version number, the regenerated CHANGELOG.md, and the bumped version in .release-please-manifest.json. Merging that pull request is what cuts a release: release-please then pushes the vN.N.N tag, which is what release.yaml fires on.

Nothing here decides the version. Conventional commit types in the pull request titles do, by way of the changelog-sections in release-please-config.json.

Why the app token

The tag is the whole reason. A tag pushed with the default GITHUB_TOKEN does not trigger another workflow, by design, so release.yaml would never fire and a release would be cut with no artifacts attached to it. An app installation token has no such restriction.

That is also why the top-level permissions: is contents: read and nothing else: every write is done with the app token, so GITHUB_TOKEN is only along for the ride.

SecretWhat it is
RELEASE_PLEASE_GITHUB_APP_IDThe app’s client ID
RELEASE_PLEASE_GITHUB_APP_SECRETThe app’s private key

The same credentials drive renovate.yaml, so there is one installation to grant and one key to rotate.

The two config files

FileWhat it holds

Any file outside the manifest that pins this project’s own version - an install snippet, a collection manifest, an image tag in a guide - has to be listed there and annotated in place, or release-please does not touch it. Both halves are required; see the “A pinned release version is release-please’s to update” section of docs/AGENTS.md.

Release-please rewrites it wholesale on every run. Editing it by hand - including to resolve a merge conflict - is lost on the next release and shows up as a diff nobody authored. Let the bot win the conflict.

goreleaser

.github/workflows/release.yaml builds and publishes the release artifacts. It fires on any pushed tag, and in practice that tag comes from release-please.yaml merging its release pull request.

What it produces, from .goreleaser.yaml:

  • one binary per goos/goarch pair, version and commit baked in via -ldflags -X
  • a tar.gz per platform, zip on Windows, named to match uname output
  • the controller image ghcr.io/colonel-byte/cluster-api-addon-provider-zarf-controller, built for linux/amd64 and linux/arm64 from containers/manager/Dockerfile and cosign-signed (docker_signs:) - which is why the workflow sets up QEMU, Buildx, and a ghcr.io login before goreleaser runs, and why the job holds packages: write
  • out/addon-components.yaml and out/metadata.yaml - the component manifest and provider metadata clusterctl fetches by name from the release assets, rendered by the release:manifests before hook at the release version and checked for presence after publish
  • checksums.txt, an SBOM per archive, a cosign bundle per archive and for the checksums file
  • a build provenance attestation over checksums.txt, uploaded to the release

After goreleaser succeeds on a v* tag, two more jobs call the air-gapped publish workflows as reusable workflows with secrets: inherit: publish-oci-artifact.yaml (the Cluster API Operator artifact) and then publish-zarf-package.yaml (the Zarf package, which embeds that artifact and so waits for it). needs: is what sequences them - the release event fires before the images they pull exist.

What it needs

SecretWhat it is
COSIGN_KEYThe private half of the keypair published as cosign.pub at the root
COSIGN_PASSThat key’s password

Those are the secret names. The workflow maps them onto the environment variables .goreleaser.yaml reads, COSIGN_PRIVATE_KEY and COSIGN_PASSWORD, which are cosign’s own and are not renameable. Changing one side without the other produces an unsigned-key error at the signing step, not a missing-secret error.

Both are required. The signs: blocks have no “unsigned if the key is missing” fallback, deliberately - a release that is quietly unsigned is worse than one that did not happen - so a missing secret fails the run rather than producing unsigned archives.

Three things that fail quietly rather than loudly

  • fetch-depth: 0 is required, not a precaution. Goreleaser reads tag history for the version and the changelog, and a shallow clone gives it neither.
  • The -ldflags -X symbol paths have to exist. A -X naming a variable the code does not declare is silently ignored, and the binary reports the zero value for its own version. Check with go doc <module>/config rather than from memory after moving or renaming those variables.
  • Syft is installed before goreleaser runs, because the sboms: block shells out to it. Remove the sboms: block or the setup step together; the leftover half is an error in the middle of a release.

Running it against a tag that does not exist

goreleaser release --snapshot --clean builds everything locally without publishing, signing, or needing a tag, and --skip=sign drops the cosign steps if the key is not to hand. That is the way to check a .goreleaser.yaml change before it is a release.

Renovate

.github/workflows/renovate.yaml runs Renovate against this repository and nothing else, every four hours and on demand. It replaces the hosted renovate[bot] GitHub App: the bot is not installed, and the config in .github/renovate.json5 is read by this run rather than by Mend’s servers.

Why it runs self-hosted

The hosted app is simpler and needs no workflow. What it cannot do is use this organization’s own GitHub App credentials, and that matters for two reasons:

  • Pull requests opened with an app installation token trigger other workflows. A pull request opened with the default GITHUB_TOKEN does not, by design, so a dependency branch would sit with no checks on it - and an update nothing has tested is not something a reviewer can act on.
  • One app, one audit trail. The same app that release-please uses opens these, so there is one installation to grant, one private key to rotate, and one bot in the repository’s audit log.

The cost is that the workflow is now a thing to maintain, and that the Renovate version is pinned - the renovate-version input in the workflow, which Renovate bumps itself via its datasource comment - rather than tracking the hosted service.

What it needs

SecretWhat it is

RELEASE_PLEASE_GITHUB_APP_SECRETThe app’s private key, shared with release-please

The app’s installation needs four permissions. Three are obvious and one is not:

Self-hosted under this app, pull requests are authored by the app’s own bot rather than by renovate[bot]. Anything keyed on the author has to be told the new name, and each of these fails by quietly doing nothing:

Running it by hand

workflow_dispatch takes two inputs: logLevel, for a debug run when a dependency is not being picked up, and dryRun, which resolves every update and logs what it would open without touching the repository. Start with a dry run after changing renovate.json5 - a bad customManagers regex matches nothing and reports success.

Bringing it up the first time

In this order, because each step fails in a way that looks like the one before it:

  1. The two secrets exist on the repository, or at the organization with this repository in scope. Without them create-github-app-token fails on the first step with an authentication error, which is the one unambiguous failure in the list.
  2. The app is installed on this repository, with the four permissions in the table above. A missing install looks like Renovate reporting the repository as not found; a missing permission looks like Renovate ignoring one manager.
  3. The labels in renovate.json5 exist. GitHub drops an unknown label from a pull request without reporting it, so the branch arrives unlabelled and nothing says why - the same trap the issue forms have. README.md has the gh label create lines.
  4. Dispatch with dryRun: true first. The log lists every update Renovate resolved and what it would have opened. This is the run that tells you whether the custom-manager regexes match anything, and it cannot leave a half-made branch behind.
  5. Then dispatch for real and read the dependency dashboard, not the pull request list. The dashboard is the proof the run completed and had write access; an empty pull request list on its own is ambiguous between “working” and “found nothing”.

Two things to expect on a repository that has only this workflow in it:

  • gomod, pre-commit and docker find nothing, because there is no go.mod, no .pre-commit-config.yaml and no Dockerfile yet. Those managers reporting zero dependencies is correct, not a misconfiguration. Only github-actions has anything to read.
  • The first real run should open exactly one pull request: actions/create-github-app-token is pinned at v3.3.0 here and v3.4.0 is out. That is a deliberately useful starting state - it means the first run has one unambiguous thing to do, and a run that opens nothing is a signal rather than a shrug. Do not bump that pin by hand before testing.

Validate Lint

.github/workflows/scan-lint.yaml runs golangci-lint over the module on every pull request and on the merge queue, against .golangci.yaml.

The version is read, not written

This is the part worth understanding before changing the workflow. golangci-lint-action installs the latest release when given no version, so CI can lint with a newer golangci-lint than the hooks pin - and a new release that adds a check produces a failure that reproduces nowhere locally.

So the workflow reads the version out of .pre-commit-config.yaml with awk and passes it to the action. One pin, in one place:

  • Renovate’s pre-commit manager bumps the rev: in that file.
  • Renovate’s github-actions manager updates uses: references - not inputs inside a with: block.

A second pin written into the workflow is therefore one that nothing keeps in step with the first, which is exactly the drift this avoids. The awk fails the job if it cannot find the rev, rather than silently falling through to the next repo: entry and reporting some other tool’s version back.

What .golangci.yaml excludes, and why it has to

magefiles/*.go and magefiles/core/ are excluded. Those files are package main behind //go:build mage, and mage supplies the main function at runtime, so the linter cannot build them - with or without -tags mage. Everything under magefiles/pkg/ is ordinary Go and is linted like the rest of the module.

Two settings worth knowing before adding a //nolint:

  • nolintlint is on with require-specific: true, so a bare //nolint fails. Name the linter.
  • errcheck has check-blank: true, so _ = f() is an error too. The house answer is an entry in errcheck.exclude-functions for a function whose error is never actionable, not a suppression at each call site.

Dockerfiles

Cargoship’s version of this workflow carries a second containers job, one matrix entry per Dockerfile, running hadolint. It is left out here as a TEMPLATE: comment because there are no Dockerfiles yet. Note when adding it that hadolint’s action takes a single path and its recursive mode globs from the repository root, which drags in the vendored Dockerfiles under vendor/ - so the paths are listed explicitly.

Scorecards supply-chain security

.github/workflows/scorecard.yaml runs OpenSSF Scorecard over the repository and publishes the result three ways: to the public API behind the README.md badge, to GitHub’s code-scanning dashboard as SARIF, and as a run artifact kept for five days.

It fires on pushes to main, weekly on Saturday at 01:30 UTC, and whenever a branch protection rule changes - that last trigger exists because the Branch-Protection check reads settings rather than files, so a protection change is the only thing that would otherwise move the score with no commit behind it.

It only works on the default branch

Scorecard scores main and nothing else. A pull request cannot move the published score, and the score a reviewer sees is always the last merge’s. To check a change before it lands, score the working tree by hand instead - .github/AGENTS.md has the --local invocation and the handful of checks worth running.

publish_results: true is what the badge needs

The workflow can run, fill in the code-scanning dashboard, and leave the badge reading unknown indefinitely - that is what publish_results: false produces. Publishing is what writes the score to api.scorecard.dev, which is the endpoint the badge image comes from.

Two further conditions, neither of which the workflow can satisfy on its own:

  • The repository has to be public. The public API holds no score for a private repository, so the badge cannot resolve.
  • The first score takes a run. Until the workflow has completed once on main, the badge reads unknown, and that is not a misconfiguration.

Annotating a check that is wrong rather than fixing it

Some findings are correct about the file and wrong about the project - a vendored dependency’s own CI script tripping Pinned-Dependencies, say, which no build here ever invokes. Those go in .github/scorecard.yml, which this template deliberately does not ship, because an annotation with no reason behind it is worse than a lower score.

The shape, when one is needed:

annotations:
  - checks:
      - pinned-dependencies
    reasons:
      # Why this finding does not apply here. Name the file, say what it is, and say why
      # nothing in this repository's build or CI path runs it.
      - reason: not-applicable

Two rules about that file, both learned the hard way:

  • Every annotation carries its reason as a comment, not just the enum. not-applicable on its own tells the next reader nothing, and the finding will look like an oversight to be cleaned up.
  • An annotation outlives what justified it. When the dependency goes or the script stops being vendored, the entry is still there, still suppressing a real finding. The root AGENTS.md treats removing one as the operator’s call rather than a documentation change - flag it, do not quietly delete it.

docs/agent/

The record of decisions that are not recoverable from the code. Everything here answers a question of the form “why is this odd thing the way it is”, asked by someone - a person or an agent - who is about to change it back.

choice-*.md are constraints, not history

This is the convention the root AGENTS.md leans on, and the reason the directory exists. A choice-*.md file records a tradeoff that was made deliberately and that looks, from the code alone, like an oversight waiting to be cleaned up: a suppression in a scanner config, a dependency pinned below its latest version, a backend selected by one property rather than the obvious one, a test fixture that duplicates something upstream.

Three rules follow from that:

  • Write one when the code cannot carry the reasoning. A comment is better than a document whenever it fits. What goes here is the decision too long for a comment and too load-bearing to lose - typically one where the alternative was tried, or where the cost of the choice is paid somewhere far from where it was made.
  • Read before reversing. The root AGENTS.md names three or four things that look reversible and are not. If a change here would undo something a choice-*.md argues for, the document is the first thing to read and the argument is the thing to answer - not the code.
  • A superseded choice is marked, not deleted. When the thing a document justified goes away, the reasoning usually still explains something that is still here: a Dependabot ignore entry, a Scorecard annotation, the shape of a package. Mark it superseded, name what superseded it, and leave the argument in place. Deleting it loses the answer to “why is this still configured”.

What else belongs here

  • AI usage disclosure. How agents are used in this repository and what review they are subject to. Where a release publishes a disclosure manifest, this is the page it is a snapshot of.
  • Design notes an agent wrote for itself - an investigation, a measurement, a survey of three approaches - where the conclusion is worth keeping but is not a decision. Name these something other than choice-*, so the constraint files stay findable.

What does not

An internal note is not a guide. If an operator would ever run the commands in it, it belongs in docs/guides/; if a contributor would, it belongs in docs/dev/. The distinction matters because the checking standard is different - a wrong count in a note here costs a reader a minute, and a wrong command in a guide costs an operator an afternoon.

The controller reads Clusters through CAPI’s typed API module

The controller imports sigs.k8s.io/cluster-api/api - the types-only module CAPI split out at v1.11 - and reads Cluster objects as clusterv1.Cluster from api/core/v1beta2. It does not read Clusters as unstructured.Unstructured or PartialObjectMetadata, and it does not import the main sigs.k8s.io/cluster-api module. Decided 2026-11-21, before the first functional reconcile milestone, which this gates. The pin is v1.14.4, matching cluster-api-provider-cargoship.

Why typed rather than unstructured

  • The v1beta2 contract is a set of field paths, and hand-encoding them is the failure mode the contract pass just fixed. The architecture doc moved from status.controlPlaneReady (v1beta1) to status.initialization.controlPlaneInitialized (v1beta2) precisely because a string path written from memory had drifted across contract versions. Unstructured access re-encodes every such path as a string literal (NestedBool(obj.Object, "status", "initialization", "controlPlaneInitialized")) that compiles against any contract, wrong or right. The typed struct makes the next contract migration a compile error instead of a silent false.
  • The sister repo has already validated the exact pin combination. cluster-api-provider-cargoship pins sigs.k8s.io/cluster-api/api v1.14.4 against the same controller-runtime v0.25.3 and apimachinery v0.37.2 this module pins, so the compatibility question the vendored build makes expensive to discover late is already answered in production next door. Mirroring its pin also keeps the two providers’ Renovate upgrades in lockstep.
  • The surface only grows from here. The reconcile core starts with labels, controlPlaneInitialized, and ownerReferences, but §6 already commits to reading conditions (ControlPlaneInitialized), status.phase for deletion handling, and the concurrent-deploys annotation - and envtest needs the real types to build fixture Clusters. An unstructured shim that is tolerable for three fields is not tolerable for the full §6/§7 read set, and converting mid-implementation would churn every reconciler layer above it.

What it costs: a vendored dependency carried by every clone. The types-only module bounds that - its dependency graph is apimachinery-sized, not the main module’s (which links the full CAPI controller machinery, webhooks, and feature gates). go list -deps the import before widening it.

The boundary: types module yes, main module not yet

Only sigs.k8s.io/cluster-api/api is imported. The main sigs.k8s.io/cluster-api module’s util/* helpers (patch, conditions, predicates) are genuinely useful and cargoship imports them - but each is a separate, later decision with its own vendor delta, taken when a reconciler actually wants the helper, not pre-emptively. Nothing here forecloses adding it; this file records that its absence today is deliberate, not an oversight.

A deploy runs in its own Kubernetes Job, and verification precedes it

Every package deploy (and removal) runs in a Kubernetes Job the controller stamps - one per ZarfPackageRelease - never in the controller process. The controller resolves the package’s tag to a digest and verifies its Cosign signature at resolution time, before any Job exists; the Job pulls that verified digest. Both halves were decided together, on 2026-11-20/21, and constrain the deploy subcommand, the resolver, and the manager deployment manifests. The user-facing contract is docs/dev/architecture.md §6 steps 4 and 6; this file is the why.

Why a Job rather than the in-process SDK

  • Zarf’s deployer selects its target cluster from the process environment. packager.Deploy (zarf v1.0.1, src/pkg/packager/deploy.go) takes no cluster handle: the unexported deployer calls cluster.NewWithWait, which resolves via clientcmd.NewDefaultClientConfigLoadingRules() - the KUBECONFIG environment variable. In-process, the only multi-cluster workaround is swapping a process-global variable under a mutex, which serializes every deploy fleet-wide and races anything else reading client-go loading rules. In a Job, “process environment” is a per-pod property: mount the <cluster-name>-kubeconfig secret, point KUBECONFIG at it, done. Parallelism across clusters is pods, not a scheduler we maintain.
  • Package actions are arbitrary command execution on the deploying machine. In-process, every package author gets code execution inside the pod whose service account can read every cluster’s kubeconfig secret. In a Job, the blast radius is one pod holding one cluster’s kubeconfig and a minimal service account.
  • Deploy lifetime decouples from controller lifetime. Packages are routinely tens of gigabytes and deploys run for tens of minutes; actions can legitimately block. A controller restart, leader-election flip, or OOM no longer kills in-flight deploys - the reconciler observes the Job it finds.
  • The package cache becomes a Job-pod concern. The largest-package disk mount moves off the controller and onto deploy pods, which spec.deployJob.nodeSelector can target at big-disk nodes.

What it costs: a deploy subcommand in the controller’s own image (no separate zarf binary to ship or pin), result plumbing from Job to release status, per-deploy spec handoff, and worse default cache reuse (per-Job emptyDir; a zarf-cache PVC volume is the escape hatch). The retry owner is the reconciler - Jobs carry backoffLimit: 0 - so the release stays the single record of attempts.

This forecloses the in-process SDK path. If zarf later grows a cluster-injection API (unchecked past v1.0.1), reasons two through four still stand; do not unwind this for that alone.

Why verification sits in the controller, not the Job

The two candidate orderings were: the Job pulls and verifies (verification code lives beside the cache it needs), or the controller verifies first and the Job pulls what was verified. The second won, with one refinement that removes its apparent cost:

  • Verifying a Cosign signature needs the manifest and the signature artifact, not the package layers. The controller already resolves tag → digest (status.resolvedDigest); verifying against that digest is a small registry read. The controller therefore needs no package-sized disk, which was the only reason to prefer in-Job verification.
  • Content addressing closes the gap between verify and deploy. The Job pulls repository@digest - never a tag - so the artifact that was verified and the artifact that is deployed are the same bytes by construction. There is no re-push window between the controller’s check and the Job’s pull.
  • The trust boundary lands where it should. Unverified content never reaches a pod holding a cluster’s admin kubeconfig; refusal happens before a Job is stamped, as a condition on the release, where an operator looks - not inside a Job log. A pull-in-Job-then-verify ordering would rely on the subcommand sequencing pull, verify, extract correctly inside the same process that later executes package actions.

The deploy subcommand may re-verify on load (LoadOptions.VerifyBlobOptions) as cheap defense in depth; that is an implementation choice, not part of this contract. What is part of it: the rendered spec handed to the Job carries a digest reference, never a tag, and a Job must never be stamped from an unresolved or unverified proxy.

The pod is a pure operator: files in, termination message out

Decided with the verification placement, for the same trust-boundary reason: the deploy pod knows nothing of the management cluster beyond the files on its disk. Its inputs are three mounts - the rendered deploy spec (a per-release Secret the controller writes: digest-pinned package reference, rendered values and variables, component selection), the target cluster’s kubeconfig, and the cache volume. It holds no management-cluster credentials, its service account grants nothing, and it makes no management-cluster API calls - which also settles where rendering runs (the controller, which can read Cluster metadata; the pod cannot and must not). Results return in the pod termination message; the controller reads the finished Job and patches release status. The alternative - the pod patching its own release status - would hand every deploy pod, and therefore every package action, a management-cluster write credential, re-opening the blast radius the Job model exists to close.

The Zarf package is built from out/, and pins its version everywhere it appears

This repository ships a Zarf v1beta1 package definition, zarf.yaml, for management clusters with no route to ghcr.io - the same environments this provider deploys into are the ones it has to be delivered through. The file mirrors cluster-api-provider-cargoship’s zarf.yaml, and its docs/agent/choice-zarf-package.md is the original of this argument. Two things about it look like oversights and are not.

It deploys out/addon-components.yaml, not the kustomization

Zarf can run kustomize itself - a manifest takes kustomize.files as readily as files - so the package could point at config/default and skip release:manifests entirely. It does not, because then the provider would be assembled two ways: once by release:manifests for the operator who installs with clusterctl, and once by Zarf for the operator in an air gap. Both would be correct on the day they were written and free to drift afterwards. Pointing at the release artifact means the air-gapped install is the same artifact, and release:zarfPackage builds it first so there is nothing to forget.

The one kustomization Zarf does run, manifest/turtle/addon, assembles nothing a second way: it wraps that same out/addon-components.yaml (staged beside it by release:zarfPackage, gitignored there) into the ConfigMap the Cluster API Operator reads a provider out of.

The version and image tags are literals, repeated

###ZARF_PKG_TMPL_...### does not reach an image reference in a v1beta1 package: Zarf parses the reference during validation, which runs before --set is applied, and the create fails with an invalid-reference error - zarf dev lint . reports the same thing, so this is cheap to re-confirm.

So the version is written out as a literal in every file that needs it - zarf.yaml (once as the package version, twice as image tags), manifest/turtle/capi-provider-addon.yaml, manifest/turtle/addon/kustomization.yaml - and release-please rewrites all of them on a release: each file is in extra-files in release-please-config.json, and each pinned line carries the x-release-please-version comment it looks for. Removing one of those comments is silent - the package still builds, pinning a tag a release ago.

release:zarfPackage reads the version back out of zarf.yaml and renders the component manifest at it, rather than taking a tag like release:manifests does. A tag parameter there would produce a package whose manifest names one version and whose image carries another, which fails at deploy time against the in-cluster registry rather than at build time.

What it deliberately leaves out

Core Cluster API, Rancher Turtles, and every Zarf package this provider itself deploys. Each is somebody else’s artifact with its own cadence, and bundling any of them would make this package a mirror of the whole air gap rather than of this provider. The rancher-turtle-artifacts component is optional: true for the related reason recorded inline: its CAPIProvider fails on a cluster without the Turtles CRDs, and the default deploy has to work for the clusterctl-shaped cluster too.
