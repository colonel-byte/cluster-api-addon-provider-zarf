cluster-api-addon-provider-zarf

A Cluster API add-on provider for Zarf packages (CAAPZ). It automates the deployment, day-2 lifecycle, and one-time initialization (“seed”) of self-contained Zarf packages onto CAPI workload clusters in air-gapped enterprise environments - the Zarf analogue of cluster-api-addon-provider-helm, whose HelmChartProxy / HelmReleaseProxy split it follows.

Status: early development. The CRDs and controller are being built; nothing is released yet.

How it works

CAAPZ runs as a controller in the management cluster. A platform team declares a ZarfPackageProxy naming a package in an internal OCI registry and a clusterSelector; for every matching CAPI Cluster, the controller resolves the package to a digest, verifies its Cosign signature, and stamps a deploy Job that mounts the cluster’s kubeconfig secret, pulls the verified digest, and deploys it over the wire via Zarf’s Go SDK - the result is recorded in a per-cluster ZarfPackageRelease owned by that Cluster. The controller itself never pulls or deploys a package. The full design - dependency ordering, ApplyOnce seed packages, auto-init, non-blocking cluster deletion - is in docs/dev/architecture.md.

strategy: Reconcile keeps matching clusters converged on the declared version; strategy: ApplyOnce deploys exactly once per cluster and never re-executes, for bootstrap and seed payloads.

deletionPolicy: Delete (the default) uninstalls the package from each cluster when its release is deleted - a proxy deletion or a selector un-match; deletionPolicy: Retain orphans it there, left running and operator-owned. ApplyOnce proxies always behave as Retain - a seed cannot be un-run. Note the default’s reach: deleting a Delete proxy uninstalls its package fleet-wide.

Installation

Each release publishes the provider three ways, all carrying the same component manifest:

  • clusterctl: addon-components.yaml and metadata.yaml on the release page, fetched by name.
  • Rancher Turtles / Cluster API Operator: a CAPIProvider of type addon, from the release page, from in-cluster ConfigMaps, or from the OCI artifact at ghcr.io/colonel-byte/turtle/addon-zarf - see the Rancher Turtles guide.
  • Air-gapped: a Zarf package at ghcr.io/colonel-byte/zarf/cluster-api-addon-provider-zarf, carrying the controller image and the manifest, cosign-signed. Its optional rancher-turtle-artifacts component pre-renders the Turtles install.

The controller image is ghcr.io/colonel-byte/cluster-api-addon-provider-zarf-controller, and everything is verifiable against cosign.pub at the repository root.

Report privately through GitHub: open a draft advisory. Do not open a public issue, and do not include a working exploit against a third party’s system.

Bootstrap order

The order a first install has to follow, and why. If you deploy one package to one already-initialized cluster, you do not need this page. If you are standing up clusters from nothing - which is the case this provider exists for - the ordering is the part that fails, and it fails by waiting rather than by erroring.

This page is the declarative counterpart to zarf-bundle-order.yml in the Ansible collection, which performs the same ordering imperatively against a single cluster. The constraint is identical; what differs is that you describe the end state and the controller sequences it, across every matching cluster, instead of you sequencing it once per cluster.

The constraint

Zarf’s own internal registry wants persistent storage. Your storage provider is a package, and a package’s images are pulled from a registry. On a cluster with neither, that is a cycle:

zarf init ──needs──> a StorageClass ──provided by──> a storage package ──needs──> a registry ──provided by──> zarf init

Nothing reports this as an error. zarf init stands up its injector and a temporary seed registry, then the permanent registry’s PersistentVolumeClaim goes Pending and stays there, because nothing in the cluster provisions volumes yet. Meanwhile every other package you declared sits in Pending with reason WaitingForZarfState, because the init-first gate holds non-init packages until the cluster has Zarf state. The cluster looks busy and is stuck.

Check whether you actually have the cycle before solving it. It assumes two things: that the registry is backed by a PersistentVolumeClaim, and that your storage provider needs storage to start. Two designs break it without any sequencing:

  • Storage that consumes raw devices. Rook-Ceph with useAllNodes: true / useAllDevices: true needs no StorageClass to come up - it is the thing that provides one.
  • A registry that is not volume-backed. Point the registry at object storage - a Ceph ObjectBucketClaim, or any S3 the cluster can reach - and it never wants a PVC.

With both, what is left is an ordering problem rather than a cycle, and ordering between packages is what dependsOn is for. You still cannot order it entirely inside the init package, for a reason that is measured rather than argued: see Why the init package cannot be split.

You break the cycle in one of five ways. They are listed cheapest-first, and the first one is the right answer far more often than it looks.

Option 1: give the cluster a registry it does not have to build

A registry the cluster does not have to build is the end of the whole problem: zarf init needs no storage, there is no seed-to-permanent handover to sequence, and your storage driver becomes an ordinary day-two package with no special position in the order.

zarf init --registry-url=registry.internal --registry-push-username=... --registry-push-password=...

Through this provider, that is the init package’s own values rather than a flag, and the registry address Zarf records in state is what every package’s image references are rewritten to - so a package built to pull from {{ .State.Registry.Address }} works unchanged in this mode.

Two things it needs, and they are both about the workload cluster rather than the management cluster. Every node must be able to reach that registry, because the node is what pulls; and Zarf writes a pull secret into each namespace it deploys into, which is where those credentials come from. If the registry is behind credentials or a private CA, the controller side of that is pullSecretRef, caBundleConfigMapRef and friends on the package source - see Getting started.

This is the right answer whenever a registry the workload cluster can reach already exists. Do not assume one does: an air gap is a topology, not a single pattern, and a management cluster holding the packages does not imply the workload clusters may pull from it - the segment may be routed, firewalled, or physically separate. Where that is the case this option is simply unavailable, and options 2 through 5 are the whole menu.

Option 2: provide storage outside the package system

If a StorageClass already exists when zarf init runs, there is no cycle and no ordering problem. Nothing to sequence, nothing to stage, one proxy.

This is the right answer whenever the storage is something your cluster images or your infrastructure provider can carry: local-path on a single-node or lab cluster, a CSI driver your node image already ships, a cloud provider’s default class, or a Cluster API ClusterResourceSet that applies the provisioner as the cluster comes up.

Then the whole Zarf side is one proxy, because by the time it runs there is storage:

apiVersion: addons.colonel-byte.dev/v1alpha1
kind: ZarfPackageProxy
metadata:
  name: baseline
  namespace: default
spec:
  clusterSelector:
    matchLabels:
      zarf: enabled

    repository: registry.internal/packages/baseline
    version: "1.0.0"
    api: v1beta1
  init:
    autoInit: true
    package:
      repository: registry.internal/packages/init-slim
      version: "v1.0.1"
      api: v1beta1
    components:
      - name: zarf-injector
      - name: zarf-seed-registry
      - name: zarf-registry
      - name: zarf-agent

Two details in that init block that are easy to get wrong:

  • init.components is not optional in practice. An init package built to bring a cluster up in stages marks every component optional, so the default selection - required components only - is empty, and the init deploys nothing while reporting success. Name the components you want.
  • autoInit is keyed on observed cluster state, never on a name. The controller probes for Zarf state and only initializes a cluster that has none, so this commutes with a fleet that manages init through its own proxy. Whoever gets there first wins, and the other no-ops.

Two things local-path will want on a real cluster, both learned by running it rather than reading about it. Its volume-provisioning helper pod mounts a hostPath, which the baseline Pod Security standard forbids - so its namespace needs pod-security.kubernetes.io/enforce: privileged. And a single-node cluster whose only node carries a control-plane NoSchedule taint has nowhere to put the registry: Zarf’s injector treats any NoSchedule or NoExecute taint as disqualifying and reports no suitable injector image or node exists.

Option 3: let the whole thing wait on a seeded registry

If your storage provider can run from an ephemeral registry, you can order the pieces with dependsOn and let the controller sequence them. The seed registry that zarf init stands up before the permanent one is enough to pull from:

apiVersion: addons.colonel-byte.dev/v1alpha1
kind: ZarfPackageProxy
metadata:
  name: zarf-init
  namespace: default
spec:
  clusterSelector:
    matchLabels:
      zarf: enabled
  strategy: Reconcile
  deletionPolicy: Retain
  package:
    repository: registry.internal/packages/init-slim
    version: "v1.0.1"
    api: v1beta1
  components:
    - name: zarf-injector
    - name: zarf-seed-registry
    - name: zarf-registry
    - name: zarf-agent
---
apiVersion: addons.colonel-byte.dev/v1alpha1
kind: ZarfPackageProxy
metadata:
  name: storage
  namespace: default
spec:
  clusterSelector:
    matchLabels:
      zarf: enabled
  dependsOn:
    - name: zarf-init
  package:
    repository: registry.internal/packages/local-path
    version: "0.0.37"
    api: v1beta1

The init package is declared as a package in its own right here, not through init.autoInit. It resolves as ZarfInitConfig, which makes it init-capable, so the gate lets it take the cluster’s deploy slot while everything else waits. dependsOn then holds storage until that release reports deployed, and Retain keeps a later deletion of the proxy from uninstalling the thing the cluster is built on.

Whether this works depends on your storage provider tolerating a registry that is about to be replaced. If it does not, you are in option 2 or option 5.

Option 4: stage it in two passes, like the Ansible playbook

The Ansible flow deploys the init package twice: once with seed components only, then the storage package, then init again with the full component set - because the permanent registry cannot come up until storage exists, and storage cannot be pulled until the seed registry does.

You can do the same here, with one proxy and two commits. Declare it with the seed components:

spec:
  components:
    - name: zarf-injector
    - name: zarf-seed-registry

let the storage proxy land, then edit the same proxy to the full set:

spec:
  components:
    - name: zarf-injector
    - name: zarf-seed-registry
    - name: zarf-registry
    - name: zarf-agent

Editing the component list re-renders the deploy and the package redeploys with the wider selection, which is Zarf doing an in-place upgrade of a package it already has a record for.

What you cannot do is split those two passes across two packages, one per proxy. The reason is not this provider’s missing takeOwnership knob, which is what it looks like; it is that the seed registry and the permanent registry are the same Helm release, so two packages that each carry one of them fight over it - measured in Why the init package cannot be split. So the staging is a sequence of edits - a GitOps commit each - rather than something the DAG performs for you. If your bootstrap genuinely needs two passes with nobody in between, option 1 removes the need and option 5 is the one that performs it.

Option 5: put the storage inside a custom init package

Zarf’s component import mechanism composes a ZarfInitConfig that carries your storage provider’s components alongside the registry’s. One package, one proxy, no ordering - the cycle is resolved inside the package instead of between packages.

This is the documented escape hatch for exactly this constraint, and it is the only option that performs the whole bootstrap with nobody in between. It is listed last because its cost is higher than it looks, and part of that cost is measurable.

Each fleet segment needing different storage carries its own init package - that is the obvious half. The half worth knowing is that you then cannot also manage that storage driver with a proxy of its own on the same cluster. The bundled init and the standalone driver package would install the same Helm releases, which is the shared-release collision below: whichever ran last owns the resources, removing either uninstalls them, and re-running the other reverts their values. So bundling genuinely forfeits independent storage updates rather than merely being untidy.

Worth it when storage cannot exist before init and no reachable registry exists. Otherwise prefer options 1 through 4.

Why the init package cannot be split

It is tempting to cut the init package in two - zarf-injector + zarf-seed-registry in one package, zarf-registry + zarf-agent in another - and let dependsOn sequence storage between them. It looks like the clean answer: three packages, three proxies, no commit in the middle, and each piece versioned on its own.

It does not work, and the way it fails is quiet. Two ZarfInitConfigs composed from one upstream set, deployed in order onto a bare cluster:

StepWhat happens
Deploy the seed halfSucceeds. Helm release zarf-docker-registry at revision 1, its objects labelled zarf.dev/package: <seed package>
Deploy the registry halfSucceeds, with no warning - Zarf logs performing Helm upgrade and exits 0
…but the ownership labelsilently flips to zarf.dev/package: <registry package>, and both deployed-package records now claim that chart
Remove the seed halfDestroys the live registry. The deployment and the release secrets go, and the other record is left claiming a dead chart
Re-run the seed half, as a version bumpReverts the shared release. helm get values shows the permanent settings replaced by the seed’s

The cause is that zarf-seed-registry and zarf-registry are not two deployments of two things. They are one Helm release lineage - the seed is revision 1 of zarf-docker-registry and the permanent registry is revision 2. Zarf never objects, because the release name matches and it simply re-labels what it finds. Two packages each carrying one revision therefore both believe they own the registry, and the last writer wins at every event.

The last row is the one that matters, because independent versioning is the whole reason to split: bumping the seed half downgrades the permanent registry to seed configuration. With upstream’s seedRegistry.persistence.enabled: false, that revert strips the registry’s storage configuration, not merely its autoscaling.

The general rule, which reaches further than init: two Zarf packages that install the same Helm release cannot both be managed on one cluster. Nothing refuses the second deploy, so the collision shows up later - as a removal that takes a live component with it, or a redeploy that reverts another package’s configuration. When you split a package, cut between Helm releases, never through one. zarf-agent and git-server are safely separable for exactly this reason: separate charts, separate releases, no shared lineage.

If you do end up with two packages over one release, deletionPolicy: Retain on both is not optional - the default Delete runs precisely the removal that destroyed the registry above.

If you package a storage driver, make it prove itself ready

Whatever comes next in the order starts when your package’s deploy Job exits zero, and that Job exits when Zarf says the deploy succeeded. The controller does not inspect your driver. So if your package reports success while its controller pods are still starting, the next thing in the order runs against a StorageClass that cannot yet provision - and the failure surfaces somewhere else entirely, as a PersistentVolumeClaim stuck Pending in a package that is not at fault.

Zarf installs charts with a readiness wait of its own, so the common case is handled: a chart whose Deployment never becomes available fails the deploy. That is not the same as the driver working, which is what the next stage depends on. Add a wait that only a functioning provisioner can satisfy.

In a zarf.dev/v1beta1 package that is a component action. healthChecks is not available - it is a v1alpha1 field, and v1beta1 rejects it - so use actions.onDeploy.onSuccess with a wait.cluster:

components:
  - name: registry-bucket
    manifests:
      - name: registry-bucket
        namespace: zarf
        files:
          - manifests/obc-registry-bucket.yaml
    actions:
      onDeploy:
        onSuccess:
          - wait:
              cluster:
                kind: ObjectBucketClaim
                name: registry-bucket
                namespace: zarf
                condition: "'{.status.phase}'=Bound"
            maxTotalSeconds: 2700
            description: Waiting for ceph bucket to be created and bound

That is Rook-Ceph’s, and it is the right shape because a Bound ObjectBucketClaim cannot exist unless the operator, the Ceph cluster, the object store and the provisioner are all genuinely working. Pick the equivalent for your driver:

DriverA wait that proves the chart is installedA wait that proves the driver works
Rook-Cephthe operator Deployment is availablean ObjectBucketClaim, or a CephCluster whose .status.phase is Ready
Longhornthe longhorn-manager DaemonSet rolled outa PersistentVolumeClaim against its StorageClass reaching Bound
vSphere CSIthe controller Deployment is availablea CSINode per node, which only appears once the node plugin registers
AWS EBS CSIthe ebs-csi-controller Deployment is availablea Bound claim - it is the only thing that proves the credentials work too
local-paththe provisioner Deployment is availablea Bound claim, which also proves the helper pod’s hostPath is permitted

The second column is the one that matters, and for most drivers the honest answer is a claim that actually binds, because that exercises the credentials, the node plugin and the backing storage in one go. A small PersistentVolumeClaim plus a wait for Bound, deleted again by a later action, costs seconds and removes a whole class of ordering bug.

Two things to get right:

  • maxTotalSeconds is the real bound on how long your package can take, and it is invisible to whoever declares the order. Ceph forming quorum on slow disks is minutes, not seconds; the 2700 above is not paranoia.
  • Keep it under the deploy Job’s timeout. A package that waits longer than the Job is allowed to run fails the stage, and the pod log is the only place that says why.

Day two

Once a cluster has Zarf state, none of the above applies to it again. The gate is open, autoInit no-ops because it probes and finds state, and packages deploy in whatever order dependsOn describes.

The Ansible playbook distinguishes bootstrap from convergence by inspecting what is installed and branching. Here that distinction does not exist, because the controller re-derives it on every pass: a release that is already on the declared digest is left alone, a release whose proxy moved to a new version redeploys, and ApplyOnce packages adopt zarf’s existing record rather than re-running. You declare the end state once and the same declaration is correct on day one and day two.

What still needs a person:

  • A new version - bump spec.package.version. Nothing moves on its own, including a re-pushed tag, which raises TagDrift and waits.
  • A failed deploy - the controller does not yet retry on a timer. Editing the spec is what re-runs it.
  • A failed init - the release holds with InitFailed and the failing Job is kept as evidence. Nothing deploys onto a half-initialized cluster, which is deliberate: a cluster with Zarf state and no registry is indistinguishable from a properly initialized one from the outside, so the provider refuses to guess.

Migrating a management cluster

clusterctl move carries a Cluster to a new management cluster. It does not carry your ZarfPackageProxy objects, and that is not a defect: a proxy is owned by nothing on purpose - it selects clusters by label and spans a fleet - so it is in no cluster’s object graph and clusterctl has no reason to associate it with the cluster being moved. The ZarfPackageRelease objects do not survive either; they are owner-referenced to the Cluster, so Kubernetes garbage-collects them when the move deletes the source Cluster at the end.

What is left untouched is the part that matters. Zarf’s record of what is deployed lives on the workload cluster, not on the management cluster, so a migration loses bookkeeping, not state. Verified by moving one: the deployed content and zarf-package-<name> secrets are exactly as they were.

So the runbook is:

  1. clusterctl move --to-kubeconfig=... as normal. The clusters arrive.
  2. Re-apply your proxies to the new management cluster. They are declarations and should already be in Git, which is the whole reason this step is cheap.
  3. The controller re-stamps a release per matching cluster and converges.

Step 3 behaves differently by strategy, and it is worth knowing which you have:

spec.strategyWhat happens after the proxies are re-applied
ApplyOnceThe rebuilt release probes the cluster, finds Zarf’s existing record, and completes with reason AdoptedExistingRecord. Nothing re-runs
ReconcileThe rebuilt release has no deploy history to compare against, so it deploys the declared digest again - a redeploy per cluster, not a no-op

That Reconcile row is the one to plan around. The redeploy is of the same digest, so it converges on the state the cluster is already in, but on a large fleet it is a burst of deploy Jobs and registry pulls immediately after a migration. One deploy Job runs per cluster at a time, so it is paced rather than simultaneous - but pace it further if that matters: move in batches, or re-apply the proxies in batches rather than all at once.

Checking where a cluster is

kubectl get zarfpackagerelease -o custom-columns='NAME:.metadata.name,CLUSTER:.spec.clusterRef.name,PHASE:.status.phase,READY:.status.conditions[?(@.type=="Ready")].reason'

A fleet mid-bootstrap reads as a column of Pending/WaitingForZarfState with one Deploying - the init package holding its cluster’s slot. That is the system working; one deploy or removal Job runs per cluster at a time, so the ordering you declared is an invariant rather than a race.

To see whether a cluster is initialized at all, ask the cluster:

kubectl --kubeconfig ./workload.kubeconfig get secret -n zarf zarf-state

And what Zarf believes is deployed there:

kubectl --kubeconfig ./workload.kubeconfig get secret -n zarf -o name | grep zarf-package-

Those secrets, not the objects on the management cluster, are what ApplyOnce adoption and uninstall both key on. Deleting a release does not delete them; that is why a recreated release adopts instead of re-running a seed.

Getting started

What you end up with: this provider running in a Cluster API management cluster, and one Zarf package deployed to a workload cluster because you declared that it should be.

Every command here was run against v0.2.0.

Nothing in this guide reaches the public internet from the workload cluster. The packages come from a registry you stage them in, which is the point of the thing.

What you need first

  • A Cluster API management cluster with core Cluster API installed and at least one Cluster whose control plane is up. clusterctl init is what puts core Cluster API there; this provider installs beside it.
  • An OCI registry the management cluster and the workload clusters can both reach, holding the packages you want to deploy. In an air gap this is the registry you staged everything into.
  • A Zarf-initialized workload cluster, or a plan for getting one - read Bootstrap order before you deploy anything real, because the order is the part that bites.

Install the provider

clusterctl learns about a provider it does not ship with from your own configuration file. Add this provider to ~/.config/cluster-api/clusterctl.yaml:

providers:
  - name: zarf
    url: https://github.com/colonel-byte/cluster-api-addon-provider-zarf/releases/v0.2.0/addon-components.yaml
    type: AddonProvider

Then install it:

clusterctl init --addon zarf:v0.2.0

clusterctl fetches addon-components.yaml and metadata.yaml from that release, so pinning the version in the URL and on the command line is what keeps an install reproducible. To check what it would apply without applying it:

clusterctl generate provider --addon zarf:v0.2.0

Confirm the controller is up:

kubectl -n caapz-system wait --for=condition=Available deploy/caapz-controller-manager --timeout=180s

Air-gapped installs

The release also publishes the same component manifest as an OCI artifact and as a Zarf package, so the install itself can cross an air gap the same way everything else does. Rancher Turtles covers the OCI artifact path.

Declare a package

A ZarfPackageProxy says what should be deployed and where. The controller matches it against Cluster objects by label, and stamps one ZarfPackageRelease per matching cluster to track that cluster’s own outcome.

apiVersion: addons.colonel-byte.dev/v1alpha1
kind: ZarfPackageProxy
metadata:
  name: podinfo
  namespace: default
spec:
  clusterSelector:
    matchLabels:
      zarf: enabled
  package:
    repository: registry.internal/packages/podinfo
    version: "1.0.0"
    api: v1beta1

Label a cluster to opt it in:

kubectl label cluster my-cluster zarf=enabled

Only Cluster objects in the proxy’s own namespace match, unless the controller was started with --cluster-namespaces naming others. That default is deliberate: a label on a cluster in another team’s namespace cannot pull your package onto it.

Watch what happens

The proxy reports what it resolved; each release reports what happened on its own cluster.

kubectl get zarfpackageproxy,zarfpackagerelease

kubectl get zarfpackageproxy podinfo -o jsonpath='{range .status.conditions[*]}{.type}={.status} {.reason}{"\n"}{end}'

Three things on the proxy are worth reading before anything else:

FieldWhat it tells you
status.resolvedDigestThe digest the tag resolved to, pinned on first resolution. Every pull and deploy uses this, never the tag
status.packageKindZarfPackageConfig, or ZarfInitConfig for an init package
PackageResolvedFalse here means nothing was deployed; the message says whether the registry, the signature, or the API claim refused

And on a release:

kubectl get zarfpackagerelease podinfo-my-cluster -o jsonpath='{.status.phase}{"\n"}'

PendingWaiting on something - read the Ready condition’s reason, which names it
DeployingA deploy Job is running
DeployedThe declared digest is on the cluster
CompletedAn ApplyOnce package ran its one deploy
FailedThe Job failed; the Ready condition carries the error the pod reported

A Pending release is the normal case worth understanding rather than worrying about. The usual reasons:

ReasonWhat to do
WaitingForZarfStateThe cluster is not Zarf-initialized. See Bootstrap order
WaitingForActiveDeployAnother deploy or removal Job holds that cluster’s slot; one runs at a time
WaitingForDependencyA dependsOn package has not deployed to this cluster yet
DependencyNotFoundA dependsOn entry names no proxy in this namespace - usually a typo

Each deploy runs in its own Job rather than in the controller, so when something fails the pod’s logs are the record:

kubectl logs job/podinfo-my-cluster-deploy

Verify the signature

A package’s signature is only verified if you name a key to verify it against. Put the Cosign public key in a Secret and reference it:

kubectl create secret generic cosign-pubkey --from-file=cosign.pub=cosign.pub

spec:
  package:
    repository: registry.internal/packages/podinfo
    version: "1.0.0"
    signatureKeySecretRef:
      name: cosign-pubkey

Naming a key makes verification a precondition: an unsigned package, a bad signature, or one that cannot be checked is refused in the controller before any Job exists, so unverified content never reaches a pod holding a cluster’s kubeconfig. Verification binds to the pinned digest, so a re-pushed tag never inherits an earlier verification.

Leaving it unset verifies nothing, and the controller says so in its log rather than pretending otherwise. The PackageSignatureVerified condition is absent in that case, not True.

Reach a registry that needs credentials or a private CA

An air-gapped registry usually wants both: a pull credential, and a certificate authority nothing public signed. Both are named per package, beside the repository they apply to.

kubectl create secret docker-registry registry-creds \
  --docker-server=registry.internal \
  --docker-username=zarf-pull \
  --docker-password="$REGISTRY_PASSWORD"
kubectl create configmap registry-ca --from-file=ca.crt=internal-ca.crt

spec:
  package:
    repository: registry.internal/packages/podinfo
    version: "1.0.0"
    pullSecretRef:
      name: registry-creds
    caBundleConfigMapRef:
      name: registry-ca
FieldWhat it names
pullSecretRefA kubernetes.io/dockerconfigjson Secret, exactly what kubectl create secret docker-registry writes. Unset means anonymous
caBundleConfigMapRefA ConfigMap holding PEM under ca.crt. A CA is not a secret, so this is the usual form
caBundleSecretRefThe same from a Secret, because cert-manager writes its CAs into Secrets. One or the other, not both
fromZarfStateBoth, read from this management cluster’s own Zarf deployment, for the common case where the registry is the one Zarf installed
insecureSkipTLSVerifySkips certificate verification. The escape hatch, and per-package, so one unfixable registry cannot lower the fleet’s bar

Three things are worth knowing before you use them:

  • The CA is added to the system roots, not substituted for them. A mirror sitting in front of a public registry keeps working.
  • Every reference resolves in the proxy’s own namespace unless the operator started the controller with --secret-namespaces naming another. A refused cross-namespace reference says so, with reason CrossNamespaceNotEnabled.
  • fromZarfState supplies the credentials and the CA, so naming it alongside pullSecretRef or either CA reference is refused by the API server rather than silently half-applied.

The same fields exist on spec.init.package, and an init package in a different registry from the one it installs is a normal arrangement - so set them there too rather than assuming the main package’s apply.

Choose how it behaves over time

spec.strategyBehaviour
Reconcile (default)Tracks the declared version. Bump spec.package.version and the package redeploys
ApplyOnceDeploys exactly once per cluster and never re-executes, even if the spec changes later. For seeds
spec.deletionPolicyOn deleting the proxy or release
Delete (default)Runs a removal Job that uninstalls the package, then releases the finalizer
RetainThe release goes away immediately and the deployed package keeps running, owned by nobody

Retain is the honest choice for large or foundational packages, where an orphaned-but-working package beats a half-removed one. An ApplyOnce package always behaves as Retain - a seed cannot be un-run.

Deleting a workload Cluster never waits on any of this. A cluster being torn down is infrastructure going away, so the controller drops its removal work rather than blocking the teardown on a cluster that can no longer answer.

Updating a package

Edit spec.package.version. The controller re-resolves, re-verifies, and redeploys, and status.resolvedDigest moves to the new digest.

It will not move on its own. If someone re-pushes the same tag with different content, the proxy raises TagDrift with reason TagContentChanged, keeps running the digest it pinned, and waits for you - because a tag that changed under you is news, not an instruction.

Installing the provider with Rancher Turtles

Rancher Turtles installs Cluster API providers through the Cluster API Operator rather than through clusterctl, so on a Turtles management cluster the install path is one CAPIProvider object. Everything else about the provider - the CRDs, the controller, the flags - is the same install; this guide mirrors cluster-api-provider-cargoship’s Turtles guide, adapted to a single addon provider.

Declare the provider

The namespace is not created for you, and the operator installs the provider into the namespace of the object that asked for it. Using the one this repository’s manifests already name keeps log commands portable:

kubectl create namespace caapz-system

apiVersion: turtles-capi.cattle.io/v1alpha1
kind: CAPIProvider
metadata:
  name: addon-zarf
  namespace: caapz-system
spec:
  name: zarf
  type: addon
  version: v0.2.0
  fetchConfig:
    url: https://github.com/colonel-byte/cluster-api-addon-provider-zarf/releases

Three things in there are easy to get wrong:

  • spec.name is the provider name, not metadata.name. Turtles resolves the provider from spec.name and falls back to metadata.name only when it is unset.
  • spec.type is addon, lower-case. The ClusterctlConfig spelling below is AddonProvider instead.
  • spec.version must be semver with a leading v, and it names the release tag. A CEL rule on the CRD rejects the bare form. With fetchConfig.url pointing at the releases page, it is also the only thing telling the operator which release to read, including the metadata.yaml beside the components that carries the contract version.

Or register it centrally

Where the provider should be known to the whole cluster - or where the components come from a mirror rather than from GitHub - put the URL in Turtles’ ClusterctlConfig and drop fetchConfig from the object above:

apiVersion: turtles-capi.cattle.io/v1alpha1
kind: ClusterctlConfig
metadata:
  name: clusterctl-config
  namespace: cattle-turtles-system
spec:
  providers:
    - name: zarf
      type: AddonProvider
      url: https://github.com/colonel-byte/cluster-api-addon-provider-zarf/releases/v0.2.0/addon-components.yaml

The name and namespace are not free: Turtles merges this object into the clusterctl-config ConfigMap it ships and looks it up at that ConfigMap’s own name and namespace - cattle-turtles-system by default, rancher-turtles-system on older installs. One created anywhere else is read by nothing, and nothing says so. Ask the cluster rather than guessing: kubectl get configmap clusterctl-config --all-namespaces.

Air-gapped, from ConfigMaps

fetchConfig takes a selector instead of a url, and then the operator reads the components and the metadata out of a ConfigMap in the cluster - no route to GitHub, no mirror standing in for it. On the connected side, download addon-components.yaml and metadata.yaml from the release; inside:

kubectl create configmap v0.2.0 --namespace caapz-system \
  --from-file=components=addon-components.yaml \
  --from-file=metadata=metadata.yaml
kubectl label configmap v0.2.0 --namespace caapz-system provider-components=addon-zarf

Then the CAPIProvider loses fetchConfig.url and gains the selector:

  fetchConfig:
    selector:
      matchLabels:
        provider-components: addon-zarf
  • The ConfigMap’s name is the version the operator offers, unless a provider.cluster.x-k8s.io/version label says otherwise - and it has to match the CAPIProvider’s spec.version.
  • The label is yours. provider-components is only the convention the operator’s examples use; nothing reads the key, the selector just has to match.
  • The components still name a ghcr.io image. Mirror the controller image and override the registry through the CAPIProvider’s configSecret, whose images key the operator reads as a clusterctl image override.

Or let the Zarf package carry it

The ConfigMap and the CAPIProvider are pre-rendered into the air-gapped Zarf package as its rancher-turtle-artifacts component - nothing to assemble on the inside:

zarf package deploy zarf-package-cluster-api-addon-provider-zarf-amd64-0.2.0.tar.zst \
  --components rancher-turtle-artifacts

It is optional, so it has to be named - zarf package deploy --confirm skips every optional component without a word, and a cluster installing with clusterctl wants exactly that. And Rancher Turtles has to be on the cluster first: a CAPIProvider applied where the Turtles CRDs are missing fails the component, and with it the deploy.

Air-gapped, from a registry

fetchConfig.oci is the third option, for the air gap that already has a registry: the operator pulls metadata.yaml and the components out of one OCI artifact. Every release publishes it at ghcr.io/colonel-byte/turtle/addon-zarf, tagged with the release’s own tag and cosign-signed by digest. Mirror it with oras cp, or - where the connected side cannot reach the mirror either - build it as a file to carry in:

go run ./magefiles/core release:ociArtifact v0.2.0

That writes an OCI image layout to out/oci and tars it beside it; nothing is pushed, deliberately. Fill the mirror on the inside with oras cp --from-oci-layout, then point the CAPIProvider at it:

  fetchConfig:
    oci: registry.internal/caapz/capi-provider

A reference with no tag takes spec.version as the tag. A registry served over plain HTTP needs an http:// prefix, which is how the operator decides to skip TLS. Registry credentials come from the configSecret’s OCI_USERNAME/OCI_PASSWORD variables, not from a pull secret. The layer names inside the artifact are the operator’s typed lookups - addon-components.yaml, metadata.yaml - carried in each layer’s title annotation, which is the only thing the operator reads a layer by.

Check it came up

kubectl get capiproviders --all-namespaces

The row reaches Ready in Phase, with zarf as ProviderName and the release tag as InstalledVersion. A row stuck in Provisioning is the operator failing to fetch or apply the components, and its reason is in the Turtles controller’s log rather than on the object.

What this does not solve

clusterctl and Turtles are two ways to install the same component manifest, and installing with one leaves the other unaware. If the provider was installed with the Zarf package’s default component instead, Turtles does not manage it and kubectl get capiproviders shows nothing - deploy the next package to upgrade, or delete it and declare the CAPIProvider to hand it over. On a Turtles cluster, the selector or OCI routes above are the better air-gapped options, because what they install is still a provider Turtles manages.

What belongs here

Say what was measured, with what flags, against what baseline - and re-measure rather than quoting an earlier run, since toolchain and dependency drift move absolute numbers with nobody editing a file.

Six workflows ship with this template: check-go-mod, codeql, commitlint, pre-commit, scan-lint, and scorecard, plus the two release workflows. Nothing runs the tests, because a test workflow for a repository with no tests is a green check that means nothing.

  1. The workflow, under .github/workflows/.
  2. A page under docs/workflows/ named after it - required by .github/AGENTS.md, then go run ./magefiles/core generate:document to put it in the summary.
  3. The Which CI job dropdown in .github/ISSUE_TEMPLATE/01-failing-build.yml, which lists the name: a workflow shows in the checks list. That one goes stale silently.

Unit tests

Triggers on pull_request and merge_group, checks out, setup-go with go-version-file: go.mod, and runs the suite. Four decisions to make deliberately:

  • Name the packages, or name the exclusion. go test ./... picks up magefiles/ at the root, which cannot build outside mage. Either list the package paths or pass -short and let the suites gate themselves.
  • -short is not optional once there are e2e suites in the module. Without it, a unit-test job pulls in suites that want Docker or a cluster and either hangs or fails for reasons that have nothing to do with the change. This is the rule the TEMPLATE: stub in the root AGENTS.md is waiting for - write it there too, naming the forbidden invocation.
  • Build offline, like every other job. GOFLAGS=-mod=vendor, GOPROXY=off. A test run that silently reaches a proxy hides a vendor tree that is missing a file.
  • Replay the fuzz seed corpus if there are fuzz targets. go test -run=Fuzz replays the committed corpus without fuzzing, which is cheap and catches a regression on an input that already found a bug once. It is not the same as a fuzzing run, and should not be confused for one in the job name.
# The shape, not the whole file.
- name: Run unit tests
  run: go test -short -mod=vendor ./cmd/... ./internal/... ./pkg/...
  env:
    GOFLAGS: -mod=vendor
    GOPROXY: "off"

End-to-end tests

Worth writing only once there is something to drive end to end, and worth treating as the most expensive workflow in the repository - cargoship’s is 154 lines and provisions a fleet.

  • Decide what provisions the fixture, and make the job’s name say which. A suite that brings up containers, a suite that brings up VMs, and a suite that runs against hosts that already exist are three different workflows’ worth of setup, and a result is only as good as the backend that produced it.
  • Check what skipped, not just what failed. A skip on an e2e suite usually means a capability the environment does not have, and a run with fifteen of them read as a pass is the commonest way this kind of suite misleads. Make the job surface the skip count.
  • Do not make it a required status check until it is reliable. An e2e job that flakes becomes a job people merge past, which is worse than not having it.
  • Upload diagnostics on failure. actions/upload-artifact with the suite’s logs is the difference between a reproducible report and “it failed in CI”. The flaky-test issue form asks for exactly that artifact.

If the suite needs credentials or a registry, give it its own workflow rather than adding secrets to the unit-test job - a fork pull request cannot see secrets, and a unit-test job that silently degrades on forks is a check that means different things depending on who opened the pull request.

Architecture Proposal: Cluster API Add-on Provider for Zarf (CAAPZ)

Inspired by the design of cluster-api-addon-provider-helm (CAAPH), this document proposes a declarative Cluster API Add-on Provider for Zarf packages: cluster-api-addon-provider-zarf (CAAPZ).

The goal of CAAPZ is to automate the deployment, day-2 lifecycle, and one-time initialization (“seed”) of self-contained Zarf packages onto CAPI workload clusters across air-gapped enterprise environments.

1. High-Level Architecture

CAAPZ operates in the management cluster as an add-on controller. It watches CAPI Cluster resources, resolves and verifies packages in an internal OCI registry by digest, and stamps one Kubernetes deploy Job per cluster - the Job mounts that cluster’s kubeconfig and drives Zarf deployment via Zarf’s Go SDK against the workload cluster API (§6 step 6). The controller itself never deploys.

2. Declarative CRD Design

CAAPZ separates cluster selection and configuration templates from per-cluster release status tracking, following CAAPH’s HelmChartProxy / HelmReleaseProxy pattern.

A. Cluster-Wide Proxy: ZarfPackageProxy

Managed on the management cluster to declare desired package states across matching clusters:

apiVersion: addons.colonel-byte.dev/v1alpha1
kind: ZarfPackageProxy
metadata:
  name: security-baseline
  namespace: fleet-default
spec:
  # Cluster matching
  clusterSelector:
    matchLabels:
      environment: production
      cargoship.colonel-byte.dev/profile: mission

  # Package source specification
  package:
    repository: zarf-docker-registry.zarf.svc.cluster.local:5000/packages/security-baseline
    version: "1.4.2"
    # Cosign signature verification before extracting/applying
    signatureKeySecretRef:
      name: cosign-pubkey

  # Deployment strategy: Reconcile (continuous) vs ApplyOnce (seed)
  strategy: Reconcile

  # Explicit dependency ordering across ZarfPackageProxies
  dependsOn:
    - name: zarf-init
    - name: csi-ceph

  # Zarf initialization parameters if target cluster is not initialized
  init:
    autoInit: true
    # The init package to deploy - a full package source, resolved, digest-pinned, and
    # signature-verified exactly like spec.package. Required when autoInit is true.
    package:
      repository: zarf-docker-registry.zarf.svc.cluster.local:5000/packages/init
      version: "v1.0.1"
      signatureKeySecretRef:
        name: cosign-pubkey
    # Variables for the init deploy, same semantics as spec.set (v1alpha1 packages only; the
    # upstream init package published at v1.0.1 is v1alpha1). A v1beta1 init package takes
    # init.values instead - e.g. registry.persistence.storageClass.
    set:
      REGISTRY_STORAGE_CLASS: "ceph-bucket"

  # Component filtering
  components:
    - name: agent
    - name: logging
    - name: security-rules
      flavor: enterprise-linux

  # Native zarf.dev/v1beta1 structured values override (supports CAPI templating)
  values:
    logging:
      retentionDays: 30
      storage:
        storageClassName: "{{ .Cluster.metadata.annotations['storage.infra/class'] }}"

(spec.set, the legacy variable mechanism, applies only to v1alpha1 packages and requires declaring spec.package.api: v1alpha1 - see §4C.)

C. Cross-Namespace Selection Is Flag-Gated, Same-Namespace by Default

By default a proxy’s clusterSelector matches only Clusters in the proxy’s own namespace, and every object reference resolves in the referrer’s namespace. This diverges from CAAPH deliberately: the controller reads and deploys with a cluster-wide role, so a cross-namespace selection is a request the controller performs with its permission, not the proxy author’s - allowing it by default would let anyone who can create a ZarfPackageProxy in a namespace they own deploy arbitrary packages onto clusters in namespaces they do not. (This mirrors cargoship’s --secret-namespaces design; see its docs/agent/choice-cross-namespace-secrets.md for the full argument.)

Two manager flags open it up, each a comma-separated namespace list where * permits any, empty (the default) permits none:

  • --cluster-namespaces - namespaces beyond its own that a proxy may select Clusters in. When a release is created in another cluster’s namespace, its packageProxyRef.namespace points back at the proxy.
  • --secret-namespaces - namespaces a proxy may name its signatureKeySecretRef in besides its own, matching cargoship’s flag of the same name.

A selection or reference into a namespace the flags do not permit is an error surfaced as a condition with reason: CrossNamespaceNotEnabled - never a quiet fallback to the local namespace, because resolving a different object than the one named is worse than refusing: it succeeds. Opening up later is a flag value; closing down later breaks every fleet that relied on it, which is the asymmetry the default follows from.

Two operational caveats, documented rather than startup-validated (a permitted-but-unused configuration should not refuse to start):

  • clusterctl move moves what a Cluster owns; a proxy or secret in another namespace is not that, and arrives missing on the new management cluster.
  • A manager whose cache is scoped to one namespace reads every cross-namespace referent as NotFound, whatever the flags permit.

3. The “Seed” Package Pattern (ApplyOnce)

An ideal capability for this architecture is supporting Seed Packages that run strictly once per imported or provisioned cluster:

Motivation

Certain foundational packages perform initialization tasks that must not be continuously reconciled or reverted on subsequent reconciliation loops, such as:

  1. One-time cluster credential seeding or bootstrap tokens.
  2. Initial root user/admin setup.
  3. Foundational certificate generation or initial storage class bindings.
  4. One-time registration or enrollment jobs.

Implementation via strategy: ApplyOnce

Borrowing from core CAPI’s ClusterResourceSet.spec.strategy, CAAPZ supports two strategies:

  1. strategy: Reconcile (Continuous Lifecycle):

    • Reacts to changes in spec.package.version, values, and variables by redeploying the package to converge the workload cluster to the new state. The package content itself is pinned by digest (see “Package identity” below); following a mutable tag is an explicit per-proxy opt-in, polled rather than watched - there is no OCI watch primitive.
    • “Drift repair” is periodic idempotent redeploy of the pinned digest on the controller’s resync interval; the Zarf SDK has no drift detection.

  2. strategy: ApplyOnce (Seed / Initialization Package):

    • When a new cluster matching the selector is discovered or imported, a deploy Job (§6 step 6) pulls and applies the Zarf package.
    • Once the deployment succeeds, the ZarfPackageRelease is marked phase: Completed and applied: true.
    • The controller will never re-execute this package against that cluster, even if the proxy’s spec or variables change.
    • Ideal for Day-0/Day-1 cluster bootstrap hooks and registration payloads.

Package identity: a tag resolves once to a digest

spec.package.version is an OCI tag, and tags are mutable; the deployed fleet must not be. So the tag is an input to resolution, not the package’s identity:

  • On first resolution - proxy creation, or any edit to spec.package.repository/version - the controller resolves the tag to its digest and records it in status.resolvedDigest. Every subsequent pull, Cosign verification, and deploy uses the digest, not the tag (Zarf resolves digest references natively), and each release records the digest it actually deployed. A re-pushed tag therefore cannot change what the fleet runs, even in principle.
  • The controller still re-checks the tag on reconcile. When the registry’s tag no longer matches the pinned digest, the proxy gets a warning condition with reason: TagContentChanged, naming both digests. Pinned deploys continue untouched; the new content is not adopted. The update path is the one that already exists: bump spec.package.version, which re-resolves and re-pins.
  • In an air-gapped registry that is periodically re-staged, a re-push of the same tag trips TagContentChanged on every re-stage. That is working as intended: the operator’s move is a version bump (or the opt-in below), never silent adoption.

Following a mutable tag is an explicit, per-proxy opt-in via annotations - an operational/dev toggle for connected test environments, deliberately kept out of the GitOps-owned spec:

AnnotationMeaning
addons.colonel-byte.dev/follow-tag: "true"Re-resolve the tag on a timer; a digest change re-pins status.resolvedDigest and triggers redeploy
addons.colonel-byte.dev/follow-tag-intervalPoll interval as a Go duration. Default 15m; meaningless without follow-tag; invalid values fall back to the default with a warning event

ApplyOnce proxies take no part in re-resolution or tag-following: their one deploy pinned what it pinned.

The ZarfPackageRelease is a cache of the guarantee, not the guarantee itself: it is deliberately garbage-collected with its owning Cluster (§7), and a Cluster object is deleted without the infrastructure being wiped during clusterctl move and de-import/re-import - exactly the imported-cluster flows seed packages target. The durable record is the one Zarf itself writes on the workload cluster: every deploy stores a zarf-package-<name> secret (labeled package-deploy-info) in the zarf namespace, which survives management-cluster churn because it lives on the physical cluster being guarded.

So the seed check is two-tier:

  • status.applied: true on an existing release short-circuits the reconcile with no workload-cluster round trip.
  • When the release is missing or not yet applied - the only states in which a deploy would fire - the controller first probes the workload cluster for the package’s deployed-package secret. If present, the release is marked Completed/applied: true without re-executing (adoption); only a cluster with no record is seeded.

Consequences, all deliberate:

  • Re-importing a live cluster re-creates its releases but does not re-run its seed packages.
  • Hand-deleting a ZarfPackageRelease does not re-run the seed; the recreated release adopts the existing record.
  • Intentionally re-seeding takes two deletions, record first: remove the package’s record on the workload cluster (zarf package remove, or deleting the zarf-package-<name> secret), then delete the ZarfPackageRelease. The release alone is not enough - the recreated release adopts the surviving record - and the record alone is not enough either, because status.applied: true short-circuits without probing. Deleting the release before the record just re-adopts.
  • Wiping and rebuilding infrastructure behind the same Cluster object re-seeds, because the rebuilt cluster carries no record. That is the desired reading of “once per physical cluster”.

One restriction follows: Zarf only stores the deployed-package record when the package has at least one cluster-touching component, so an ApplyOnce package must include one. A pure-actions package would leave no durable record, silently degrading the guarantee to the garbage-collectable release; the controller surfaces a condition on the release when a completed seed deploy left no record behind.

Seed-then-manage handoff, and the package name as identity

A supported pattern (used by the sister ansible-collection-zarf tooling): an ApplyOnce proxy seeds a package - zarf-init, say - and a Reconcile proxy later takes over the same package name for day-2 lifecycle. This works by construction: the Reconcile path never consults the seed record, Zarf treats a same-name deploy as an in-place upgrade updating the same record, and on re-import the seed proxy adopts whatever version the successor last deployed. Two properties to hold on to:

  • Adoption is keyed on the Zarf package name on the cluster - nothing else. Not the proxy’s name, not the declared version or digest. Any ApplyOnce proxy whose package carries that name adopts the record, even if its spec declares different content. Package names are therefore an identity namespace the fleet’s conventions must own; two unrelated packages sharing a name will silently satisfy each other’s seed checks.
  • A successor proxy for a seeded package must be deletionPolicy: Retain (§8). Under the default Delete, deleting the successor runs zarf package remove on the shared package name - destroying both the package and the deployed-package record the seed’s guarantee rests on, while the seed’s release still reports Completed and its applied cache suppresses any re-seed. The cluster loses the package; nothing notices. Retain on the successor keeps the handoff safe.

Composition guidance: separate packages by default, bundle into init only for storage bootstrap

Heterogeneous fleets (one segment wants vsphere CSI, another rook-ceph) are the reason foundational packages stay separate from the init package by default - the layout the CRDs already express with no extra machinery:

  • One shared init proxy (or autoInit), identical fleet-wide; per-variant proxies (csi-vsphere, csi-rook-ceph) with disjoint clusterSelectors keyed on the cluster’s existing labels, each with dependsOn: [zarf-init]. The DAG and the init-first eligibility gate (§6) order everything; a cluster gets the variant its labels declare. Where variants share most content, Zarf flavors via spec.components let two thin proxies select from one package.
  • Bundling components into a custom init package is the escape hatch for one constraint only: storage that must exist before init can finish - Zarf’s internal registry needing a real StorageClass with nothing provisioning one pre-init. Zarf’s component import mechanism composes this (a custom ZarfInitConfig importing, say, rook-ceph’s components); the cost is per-variant init packages, paid knowingly by the fleet segment that needs it. The decision rule per segment: can init complete on this cluster’s day-zero storage? Yes - shared init, selector-driven variants. No - that segment carries a variant init package. The init package’s own storage-class knob (init.set’s REGISTRY_STORAGE_CLASS, or its v1beta1 value equivalent) bridges the two where a StorageClass exists at provision time.
  • Day-2 handoff of bundled components follows the package name, per the handoff rules above. The clean path is one Retain Reconcile proxy managing the custom init package itself - same name, same record, in-place upgrades. Splitting a bundled component out to its own proxy later changes the package name: no adoption, no shared record, and the first deploy collides with Helm releases the init components own. Zarf’s DeployOptions.TakeOwnership exists for exactly that adoption, which implies a proxy-level takeOwnership knob - not in the API today; decide whether to add it before v1alpha1 ships to real users, since the name-discontinuous handoff is impossible without it.

4. Native zarf.dev/v1beta1 Package Support

CAAPZ natively implements the modern zarf.dev/v1beta1 Zarf package schema while maintaining backward compatibility with zarf.dev/v1alpha1:

A. Native Deployment, No Conversion

  • When pulling a package from an OCI registry, CAAPZ inspects the apiVersion. A proxy may assert it up front via spec.package.api (v1alpha1 or v1beta1); when the declared version does not match the pulled artifact, the release fails with a condition before any deploy runs.
  • Packages deploy as their native schema version - CAAPZ performs no in-memory conversion. Converting a v1alpha1 package to v1beta1 before deploy would trip Zarf’s rejection of deploy-time variables on v1beta1 packages and silently break spec.set; Zarf’s deployer handles both versions natively.
  • Deprecation: v1alpha1 package support exists for compatibility and will be dropped when upstream Zarf drops v1alpha1 support. New packages should be authored as v1beta1 and configured through spec.values.

B. Hierarchical Structured Values (spec.values)

In v1beta1, Zarf supports structured values maps (analogous to Helm values.yaml). CAAPZ exposes spec.values directly on ZarfPackageProxy:

  • Values accept full YAML trees rather than only string scalars (spec.set).
  • Supports Go template substitution referencing CAPI Cluster metadata and annotations (e.g. {{ .Cluster.metadata.name }}).
  • Merged with the package’s internal defaults at deployment time.

Deferred, additive later: sourcing values from a Secret or ConfigMap (valuesFrom, CAAPH/Flux-style). The seam already exists - the deploy Job reads only the rendered deploy-spec Secret, never the proxy - so a future valuesFrom is purely a controller-side resolution step at render time, merged into the same Values/Set fields; the deploy pod and subcommand need no change, and a changed source changes the rendering, so the spec-hash redeploy path picks it up for free. Adding the optional field later is API-compatible (no version bump), and signatureKeySecretRef’s CrossNamespaceNotEnabled refusal is the reference-shape and namespace-policy precedent to reuse. The future change owes three things: ConfigMap get/list/watch RBAC (Secrets are already covered), an answer for “the referenced source changed but the proxy didn’t” (the lazy version is the periodic resync re-render, consistent with the drift-repair item owed from M3; immediate reaction needs a watch plus mapping), and precedence semantics between inline and referenced values (Flux’s “later entries win, inline wins last” is the boring default).

C. Legacy Variables (spec.set) Are Gated on a Declared v1alpha1 Package

Zarf rejects deploy-time variables (SetVariables) for v1beta1 packages, so spec.set is only valid against v1alpha1 packages - and the CRD enforces that at admission:

  • spec.package.api is an optional enum (v1alpha1 | v1beta1). Unset means “detect from the artifact”.
  • Using spec.set requires declaring spec.package.api: v1alpha1. A CEL validation rule on the CRD rejects the object at kubectl apply otherwise, turning a deploy-time Zarf error buried in a Job log into an immediate admission message. (CEL CRD validation is GA from Kubernetes 1.29, the management-cluster floor this sets.)
  • The declaration is a claim: the controller verifies it against the pulled artifact’s actual apiVersion and fails the release with a condition on mismatch, before stamping a deploy Job.
  • spec.set values support the same Go templating as spec.values, and the field is deprecated on the same schedule as v1alpha1 support itself (§4A).

D. Architecture & Flavor Auto-Detection

v1beta1 formalizes component selectors with flavor and architecture. CAAPZ automatically extracts the target cluster’s architecture from CAPI Machine specifications (amd64, arm64) and selects the appropriate component variants automatically unless explicitly overridden in spec.components.

5. Dependency Management & Execution Ordering (dependsOn)

Foundational platform services require strict execution ordering. For example, workloads cannot schedule PersistentVolumeClaims before storage drivers exist, and Zarf packages cannot deploy before the cluster has a running registry or injector:

[ zarf-init ] ──► [ csi-ceph (CSI Driver) ] ──► [ logging / monitoring ]

A. Declarative Ordering via spec.dependsOn

A ZarfPackageProxy can declare dependencies on other objects in its namespace:

apiVersion: addons.colonel-byte.dev/v1alpha1
kind: ZarfPackageProxy
metadata:
  name: logging-stack
  namespace: fleet-default
spec:
  dependsOn:
    - name: zarf-init
    - kind: ZarfPackageProxy
      name: csi-ceph

Each entry is a {kind, name} reference rather than a bare name. kind defaults to ZarfPackageProxy, which is the only kind the enum admits today, so the short form above is the ordinary one. It is typed because ordered bundles will be a second kind a package can wait for, and a bare string cannot say which of two kinds a name means; taking the break while the API is v1alpha1 is cheaper than a second field later. A dependency carries no namespace - the graph resolves in the referring object’s own namespace, because one that spans namespaces is one no single author can read.

B. Dependency Resolution & Reconcile Gating

For each workload cluster, every entry in dependsOn is resolved to a verdict. The rule that prevents deadlock: a dependency that cannot be satisfied on this cluster is a named error condition, never a silent wait. Waiting is reserved for the one case where progress is actually coming.

Dependency state on this clusterVerdictDependenciesSatisfied reason

  • The dependent release holds in phase: Pending with DependenciesSatisfied: False and the reason above; the message names the offending dependency.
  • DependencyNotApplicable is deliberately an error rather than auto-satisfied: declaring “X needs Y here” when Y’s selector will never match this cluster is a configuration contradiction, and silently skipping the ordering would hide exactly the label mistake the admin needs to see.
  • All verdicts are level-triggered: fixing labels, creating the missing proxy, or the dependency deploying re-evaluates the dependent with no operator intervention. Re-evaluation is watch-driven - the proxy reconciler watches ZarfPackageRelease phase changes and maps them back to dependents - with the periodic resync as backstop; there is no requeue polling loop.
  • A dependency proxy deleted after its ApplyOnce package seeded a cluster reports DependencyNotFound, even though the package is on the cluster. This is strict on purpose - keep proxies that the dependency graph references. (Softening it by probing the workload cluster’s deployed-package record (§3) is a possible later relaxation, not a commitment.)

C. Circular Dependency Detection

Directed Acyclic Graph (DAG) validation runs at reconcile time, not admission - cross-object graph checks cannot be expressed in CEL, and a validating webhook is not worth its cert plumbing in air-gapped installs when admission-time validation can be invalidated by the very next edit to a different proxy anyway. Each reconcile builds the dependency graph from the namespace’s proxies (informer cache, no API round trips) and runs a cycle check; every proxy in a detected cycle gets DependenciesValid: False, reason: DependencyCycle and deploys nothing until the cycle is broken.

6. Reconcile Workflow

  1. Cluster Discovery: The controller watches for CAPI Cluster resources reaching status.initialization.controlPlaneInitialized == true (the v1beta2 initialization signal, surfaced by the ControlPlaneInitialized condition) and matching spec.clusterSelector.

  2. Kubeconfig Resolution: CAAPZ retrieves the cluster’s administrative kubeconfig secret (<cluster-name>-kubeconfig) using CAPI’s cluster client cache.

  3. Seed Check: If spec.strategy == ApplyOnce, skip execution when the release is already applied: true. Otherwise probe the workload cluster for the package’s zarf-package-<name> deployed-package secret in the zarf namespace; if present, mark the release Completed without deploying (see §3, “Where the ‘never re-execute’ record actually lives”).

  4. Digest Resolution & Signature Verification: The controller resolves the tag to its pinned digest (status.resolvedDigest, §3) and, if signatureKeySecretRef is set, verifies the Cosign signature against that digest in the controller, at resolution time - a manifest-and-signature read against the registry, not a package pull, so the controller needs no package-sized disk. The deploy Job later pulls that verified digest: content addressing makes the verified artifact and the deployed artifact the same bytes. Verification binds to the digest, so a re-pushed tag never inherits a prior verification. See docs/agent/choice-deploy-job.md for why verification sits here rather than in the Job.

  5. Auto-Init Check: If spec.init.autoInit == true, the controller probes the target cluster for Zarf state (zarf-state secret in the zarf namespace) at deploy-prep, and only an absent state triggers an init deploy. Auto-init is keyed on observed cluster state, never on a package or proxy name - so it commutes with a fleet that manages init through its own proxy (the §3 seed-then-manage handoff): whoever initialized first, the probe finds the state and auto-init no-ops. When both are declared, dependsOn naming the init proxy is the deterministic ordering; the remaining concurrent-first-deploy race is closed structurally by step 6’s one-Job-per-cluster rule. Init-first is an eligibility gate, not a priority: on a cluster with no Zarf state, the only releases eligible for a Job slot are init-capable ones - a package that resolves as an init package (kind: ZarfInitConfig, read at resolution) or a proxy with autoInit: true; everything else holds in Pending with condition reason WaitingForZarfState rather than failing inside a Job. With step 6’s one-Job-per-cluster rule, “the init package deploys first” is therefore an invariant, not a scheduling preference.

    The auto-init deploy path. spec.init.package names the init package - a full package source (repository, version, optional api claim and signatureKeySecretRef), required when autoInit: true. The controller resolves and verifies it exactly as step 4 does the main package - pinned to status.initResolvedDigest/initResolvedRef, surfaced on the InitPackageResolved condition - and additionally refuses an artifact that does not resolve to kind: ZarfInitConfig. On a state-less cluster, an autoInit release stamps an init Job: the step 6 Job contract verbatim (same image, kubeconfig, cache volume, deploy subcommand) with an -init name suffix, reading init-spec.yaml rendered into the release’s deploy-spec Secret beside the main spec. The init Job takes the one-Job-per-cluster slot like any other Job, so two autoInit proxies racing on a fresh cluster serialize, and the loser’s next probe finds the state and no-ops - the commuting property above, preserved. Success leaves no status record beyond the probe finding state (the zarf-state secret is the record, and Zarf keeps its own deployed-package record for the init package); the controller deletes the finished Job and the release proceeds to its normal deploy on the next pass. Failure surfaces as Ready: False, reason: InitFailed with the pod’s error, and retry is edit-to-retry via the init spec hash - the same stance as deploys. The proxy’s own package never takes the slot while state is absent: autoInit makes the init Job eligible, not the main package. A proxy whose main package itself resolves as ZarfInitConfig needs no autoInit - it is init-capable as-is, and deploying it initializes the cluster. An init package whose components are optional deploys nothing until they are named. Component selection is spec.init.components, with spec.components’ semantics - and it is not the edge case it sounds like: an init package built to bring a cluster up in stages marks every component optional, so the default selection (required components only) is empty. spec.init.values and spec.init.set pass through to the init deploy exactly as the proxy-level fields do to the main one - same {{ .Cluster... }} templating, same v1alpha1-only rule for set (keyed on init.package.api) - so there is no dedicated storage-class field: it is the REGISTRY_STORAGE_CLASS variable in the v1alpha1 init package upstream publishes at v1.0.1, or the registry.persistence.storageClass value in a v1beta1 one. CAAPZ never removes an init package it auto-deployed - deletionPolicy governs spec.package only.

  6. Deploy Execution (the deploy Job): Render values and variables ({{ .Cluster.metadata.name }}) and stamp one Kubernetes Job per release - a deploy never runs in the controller process. The Job’s contract, which §4C, the Signature Trust Model, and §8A reference:

    • It runs the controller’s own image (or spec.deployJob.image) with a deploy subcommand. The pod acts as a pure operator: its entire input is files on disk - a rendered deploy spec the controller writes to a per-release Secret and mounts (package repository pinned by digest, rendered values and variables, component selection), the kubeconfig, and the cache. It holds no management-cluster credentials and makes no management-cluster API calls; the subcommand assembles packager.DeployOptions from the spec file alone.
    • Results return in the pod’s termination message; the controller reads the finished Job and patches ZarfPackageRelease.status. The deploy pod’s service account grants nothing.
    • The target cluster’s <cluster-name>-kubeconfig secret is mounted and KUBECONFIG points at it - the Zarf SDK resolves its target from the process environment, so the pod’s environment is what selects the cluster. No mutex, no serialization: deploys to different clusters are different pods.
    • The package is pulled inside the Job by the verified digest from step 4 (repository@digest, never a tag) into the Job’s zarf-cache volume (default emptyDir, PVC-replaceable via spec.deployJob.volumes).
    • The pod runs a restricted security profile by default; spec.deployJob exposes the knobs (service account, security contexts, volumes and mounts, node selector, tolerations). A package action - arbitrary command execution - is thereby contained to a pod holding one cluster’s kubeconfig, not the fleet-wide controller.
    • backoffLimit: 0: the controller owns retries, so the release stays the single record of attempts. The Job is controller-owned by its release and garbage-collects with it; a removal Job (§8) reuses this same contract with a remove subcommand.
    • One Job per cluster at a time. Upstream Zarf recommends a single package operation per cluster with current tooling, so the controller stamps at most one deploy or removal Job per target cluster; further ready releases hold in phase: Pending with condition reason WaitingForActiveDeploy until the slot frees. This holds even where the dependency DAG (§5) would permit parallelism - the DAG decides who goes next, never simultaneity - and it is what closes step 5’s double-init race without naming conventions. Parallelism across clusters is unaffected. A CAPI Cluster annotated addons.colonel-byte.dev/concurrent-deploys: "true" opts that cluster out of the serialization, for when tooling or operator confidence allows it; the annotation lives on the Cluster because concurrency tolerance is a property of the target, not of any one proxy. Bounded concurrency - the annotation carrying a slot count rather than a boolean - is deliberately deferred to a later phase of the controller; "true" is specified to leave room to grow into an integer without breaking existing annotations. Why a Job rather than the in-process SDK - and why verification precedes it - is recorded in docs/agent/choice-deploy-job.md.

  7. Status Update: Update ZarfPackageRelease.status and surface condition Ready: True on the release and proxy objects.

Registry Reachability

Verification is about what the artifact is. Reachability is the separate question of whether the controller can get to the registry at all, and in an air gap the answer usually involves a credential and a certificate authority nothing public signed.

Five fields on spec.package - and on spec.init.package, which is the same type - cover it:

FieldWhat it supplies
pullSecretRefA kubernetes.io/dockerconfigjson Secret. Empty means anonymous, which was the only option before it
caBundleSecretRefPEM certificates under ca.crt, trusted in addition to the system roots - the cert-manager shape
caBundleConfigMapRefThe same, from a ConfigMap. A CA is not secret; the Secret form exists because cert-manager writes one
fromZarfStateBoth of the above, read from the management cluster’s own Zarf deployment instead of from an operator’s Secret
insecureSkipTLSVerifyAccepts the certificate unverified. Per-package, so one unfixable registry cannot lower the fleet’s bar

Every reference resolves through the same --secret-namespaces gate as signatureKeySecretRef (§2C), so a proxy author can only name material their own namespace holds unless the operator widened it.

The material reaches two consumers by two routes, and that is deliberate. The controller resolves and verifies the package itself, and passes credentials and a root pool per call - so two proxies naming two registries with two credentials never see each other’s. The deploy pod pulls by digest through an upstream API that carries neither, so there the credentials and the CA arrive as files mounted from the release’s deploy-spec Secret, with the pod’s environment pointing at them. The pod holds no management-cluster access and could not look a Secret up; one pod also serves exactly one package, so a file scoped to the pod is scoped to the pull. docs/agent/choice-registry-credentials.md records why, and what would have to change upstream for the pod to use the same hook the controller does.

fromZarfState reads the management cluster, not the workload cluster, which is the opposite of every other Zarf-state read in this controller. The init gate, probe-and-adopt, and removal all probe a workload cluster through its CAPI kubeconfig; this one reads the controller’s own cluster, because that is where the registry being pulled from lives. A workload cluster’s internal Zarf registry is not a package source - its recorded address is node-local, and nothing in the management cluster can route to it.

No client certificate is presented, measured rather than assumed: Zarf’s registry serves clients that offer none, and the certificate it issues belongs to the per-node registry proxy. A registry that genuinely requires one needs an upstream change before this provider can carry it.

Signature Trust Model

signatureKeySecretRef adopts the sister cargoship repository’s semantics verbatim (its signatureKeySecretRef field and the reasoning in its doc comment):

  • The reference names a Secret whose cosign.pub key holds the Cosign public key. It resolves in the proxy’s namespace unless --secret-namespaces permits another (§2C), which is what bounds “anyone who can edit the proxy picks the key”: a proxy author can only name keys their own namespace holds.
  • Empty verifies nothing. A signature with no key to check it against is not verification, so the controller logs that it could not verify and deploys anyway - for a signed package exactly as for an unsigned one. The PackageSignatureVerified condition is absent, not True.
  • Naming a key makes verification a precondition. An unsigned package, a signature the key does not verify, and a signature in a form that cannot be checked are all refused, and the refusal comes out of digest resolution in the controller (§6 step 4) - before a deploy Job is ever stamped, so unverified content never reaches a pod holding a cluster’s kubeconfig. The Job then pulls the verified digest; content addressing makes what was verified and what is deployed the same bytes. Verification binds to the pinned digest (§3), so a re-pushed tag never inherits a prior verification.
  • Rotation is a Secret edit. Verification runs on the passes that deploy, against the key as it currently reads, so a rotated key takes effect on the next reconcile and a Secret deleted under a converged fleet is reported as a failed precondition rather than noticed the next time something changes.
  • Fleet-wide enforcement is deliberately deferred. Per-proxy keys match the sister repository’s model; a controller-level --require-signature flag (refuse any proxy with no key named) is the natural later addition if an environment needs “no unverified package, ever” as policy rather than convention.

7. Non-Blocking Cluster Deletion & Lifecycle Safety

A critical architectural pitfall in add-on controllers (including earlier versions of CAAPH) is hanging or blocking cluster deletion when a workload cluster is destroyed. CAAPZ explicitly avoids blocking cluster deletion:

A. Non-Blocking Finalizer Policy

  • No Blocking Finalizer on the CAPI Cluster: CAAPZ does not install a finalizer on the CAPI Cluster resource itself. When an operator or automation deletes a CAPI Cluster, CAPI begins tearing down the infrastructure and VMs immediately.
  • Immediate Reconcile Termination on Deletion: If Cluster.DeletionTimestamp.IsZero() == false, CAAPZ immediately halts any pending deployments, releases any local mutexes or downloads, and exits without attempting to connect to the dying cluster.
  • Cascade via Kubernetes ownerReferences: The per-cluster ZarfPackageRelease CR carries a standard ownerReferences pointing to the CAPI Cluster. When the Cluster is deleted, Kubernetes garbage-collects the ZarfPackageRelease automatically via background cascading deletion.

B. Graceful Degradation on Unreachable Clusters

  • When an infrastructure provider tears down VMs (or when connectivity to the workload API drops), attempts to uninstall or communicate will fail (connection refused or context deadline exceeded).
  • CAAPZ treats cluster deletion as an infrastructure-level wipe for teardown purposes: attempting an orderly Zarf uninstall over the wire is neither necessary nor desirable, and the controller discards its state without blocking CAPI or Machine deletion. But Cluster-object deletion is not always an infrastructure wipe - clusterctl move and de-import/re-import delete the object while the cluster lives on - which is why the ApplyOnce guarantee is anchored on the workload cluster itself rather than on anything garbage-collected in this cascade (§3).

8. Uninstall Semantics & Deletion Policy

§7 covers the cluster going away; this section covers the declaration going away while the cluster lives on: a ZarfPackageProxy is deleted, or a cluster’s labels change so the selector no longer matches it.

A. spec.deletionPolicy: Delete | Retain

The proxy declares what happens to its deployed packages when their release is deleted:

  • Delete (the default, matching CAAPH): the package is uninstalled from the workload cluster - via packager.Remove, run in a removal Job on the same plumbing as deploys (§6’s deploy Job: same image, kubeconfig mount, cache volume, and deployJob knobs) - before the release object is allowed to go away.
  • Retain: the release object is deleted immediately and the deployed package is orphaned on the workload cluster, left running and operator-owned from then on. The honest choice for large or foundational packages, where an in-place uninstall is unreliable and an orphaned-but-working package beats a half-removed one.
  • ApplyOnce proxies ignore the policy and always behave as Retain: a seed cannot be un-run, and its durable record lives on the workload cluster (§3) regardless of what happens to management-cluster objects.
  • A Reconcile proxy managing a package an ApplyOnce proxy seeded must also be Retain: Delete on the successor removes the shared package name’s deployed-package record along with the package, silently voiding the seed guarantee while the seed’s release still reports Completed - see §3’s seed-then-manage handoff.

B. Mechanics: a finalizer only where a removal is owed

  • Releases under Delete carry a CAAPZ finalizer; the controller runs the removal Job and drops the finalizer on success. Releases under Retain (and all ApplyOnce releases) carry no finalizer at all, so their deletion can never block on anything.
  • The finalizer’s presence tracks the proxy’s current policy: flipping a proxy between Delete and Retain adds or strips the finalizer on its releases on the next reconcile, so the policy is live-editable and acts as the declarative break-glass for a stuck removal.
  • Proxy deletion: a finalizer on the proxy deletes its releases (found via spec.packageProxyRef) and waits for them to finish their own finalization before the proxy goes away. Releases are deliberately not owner-referenced to the proxy: Kubernetes garbage collection only deletes a dependent once all of its owners are gone, so a second ownerRef would stop Cluster deletion from collecting releases and quietly break §7’s cascade. The Cluster stays the sole owner.
  • Selector un-match: the controller deletes the no-longer-matching release, and the same finalizer path decides whether that is an uninstall (Delete) or an orphan (Retain).

C. The §7 override: cluster teardown always wins

If the release’s owning Cluster has a deletion timestamp, no longer exists, or is unreachable, the finalizer is dropped without attempting removal. Uninstall semantics never block or delay cluster deletion; §7 outranks this section wherever they conflict.

When removal fails while the Cluster is alive and reachable, the controller requeues with backoff and surfaces a RemovalFailed condition on the release. The operator’s escape hatches, in preference order: flip the proxy to Retain (declarative, affects all its releases), or remove the finalizer by hand (surgical, one release).

D. Known limitation: shrinking spec.components

Removing an entry from spec.components does not remove that component from the workload cluster - a redeploy with fewer components leaves the extras running. Removed components are orphaned until the package is removed and redeployed. Per-component removal choreography is deliberately out of scope until a real need arrives.

9. Clusterctl Provider Contract

CAAPZ ships as a clusterctl-manageable provider, the same way the sister cargoship repository does:

  • metadata.yaml at the repository root maps each release series to its Cluster API contract (v1beta2). Release-please owns the current series entry via x-release-please-major/-minor markers; past series are appended as releases are cut so clusterctl upgrade can map an installed version. Without this file, clusterctl init refuses to install the provider.
  • Provider labels - clusterctl.cluster.x-k8s.io: "" and cluster.x-k8s.io/provider: addon-zarf - go on every manifest in the release bundle, so clusterctl can find and manage what it installed. They land with the manager deployment manifests.
  • clusterctl move: ZarfPackageProxy and ZarfPackageRelease carry the clusterctl.cluster.x-k8s.io/move label so a pivot carries the declarations to the new management cluster. Releases are re-derivable (the controller re-stamps them from proxies and Clusters), but moving them preserves status history and avoids a re-deploy window; proxies are not re-derivable and must move. The ApplyOnce guarantee survives either way - it lives on the workload cluster (§3), not in anything being moved. The §2C caveat stands: a cross-namespace secret is outside what move carries.

10. Enterprise & Air-Gap Advantages

  • Air-gap Compliant: Zarf packages bundle container images, Helm charts, and manifests together in an OCI artifact, eliminating out-of-band image syncing.
  • Supply Chain Security: Cosign signature verification occurs on the management plane before any package payload touches the remote workload cluster.
  • Native CAPI Integration: Works across all CAPI infrastructure providers (vSphere, AWS, Azure, bare-metal) and bootstrap providers (Cargoship, RKE2, Kubeadm).

The problem

Both packages appear twice. Today the only way to express that through this provider is an operator editing a component list between passes - a GitOps commit per stage, which has to land when every matched cluster is ready for it. That is acceptable for one cluster and wrong for a fleet.

The proxy is already a two-stage pipeline

The first draft argued a new kind was needed. It is not, because the concept already exists in this codebase - hardcoded at two stages. Everything a sequence needs is there, in pairs:

ConceptAlready there, twice
A package sourcespec.package and spec.init.package
A resolution result in statusstatus.resolvedDigest and status.initResolvedDigest, with their refs
A document in the deploy-spec Secretdeploy-spec.yaml and init-spec.yaml, in one Secret
A Job per releasebuildJob(..., "-init"), "-deploy", "-remove"
Sequencing between themconvergeInit stamps the init Job and settleInitJob holds the deploy until it settles

spec.init plus spec.package is a two-stage sequence: deploy this package with these components first, then that one. So stages are not a new concept to add. They are an existing concept with the 2 taken out.

Two things follow that the first draft got wrong. Per-stage Job names are not a new pattern - a release already has three Jobs - so <release>-<stage>-deploy is the same trick with a wider suffix. And ordering is not wholly unimplemented either: init-before-deploy exists, it is simply not a loop.

The shape

Two additions, both to types that already exist.

On ZarfPackageProxy: the sources hoisted so a version is declared once, and an ordered list of stages over them.

Hoisting the sources is not cosmetic. A stage list of near-complete sources means a version bump is edited in two places, and a half-finished edit produces two digests of one package name - two revisions of one Helm release lineage with disagreeing values, which is the measured revert in bootstrap-order.md reintroduced inside a single object. A packageRef makes that disagreement structurally impossible.

On ZarfPackageRelease: status.stages[], one entry per stage that has run on this cluster, carrying the stage name, the applied identity and when. The release is already the per-cluster object, already owner-referenced to the Cluster, and already carries the per-cluster phase - so per-cluster stage progress belongs here and nowhere new.

And spec.package becomes sugar for a single Reconcile stage, spec.init for a preceding ApplyOnce one. That is what keeps this one API rather than two dialects: internally everything is a stage list, and every proxy written before this existed is the one- or two-stage case. There is no oneOf for a reader to learn, and no second code path to keep in step.

What this reuses literally

Not “mirrors” - reuses, with no second expression to drift:

  • matchClusters, stampReleases, findRelease, the finalizers, the removal path
  • dependsOn, including the cycle walk, because every edge stays proxy-to-proxy
  • the per-cluster deploy slot
  • the Ready roll-up, the cluster counts, the printer columns, the Events
  • all four watches, and the release-to-proxy fan-out
  • resolution, digest pinning, signature verification, the api claim check, and every registry reachability field, per stage
  • the deploy-spec Secret, which already holds more than one document, and the deploy Job, which already has more than one name

A separate kind would have needed each of those a second time, plus a second reconciler, RBAC surface, CRD, status aggregation, docs chapter and e2e harness - and a cross-kind dependsOn resolver and cycle walk, which is a silent-hang bug rather than extra typing: proxyDependencies filters by kind, so a proxy-to-bundle-to-proxy cycle would be invisible and every member would report WaitingForDependency forever.

The honest objections to a field

  • kubectl get zarfpackageproxy mixes two lifecycles. A four-stage bootstrap and an ordinary one-package proxy appear in one list, and the Version column reads .spec.package.version, which a staged proxy does not have. Needs a STAGES column (4/6) and a Version that means the last stage’s.
  • spec.strategy becomes ambiguous. Per-stage strategy is the point, so the top-level field has to be refused when stages is set. More validation, and a reason a reader has to learn.
  • “A sequence is a different noun” is a legitimate taste argument. kubectl get zarfbundles reads better than filtering proxies. It costs a cross-kind cycle walk, a cross-kind conflict detector and a second reconciler, which is what this design judges too expensive for the ergonomics.

Per-stage state, not a cursor

A cursor integer - “this cluster reached stage 3” - cannot answer the question an operator has, which is what happens when I bump one thing. Recording an applied identity per stage answers it:

ChangeRe-runs
csi version bumpedstorage-final, which carries its plain charts; storage-seed is ApplyOnce and stays put
init version bumpedregistry; init-seed is ApplyOnce and stays put
A stage’s components or values editedthat stage
Nothingnothing - a converged proxy is quiet

The identity has to be the controller’s own hash of the rendered spec, not a value the pod reported back. status.deployedDigest is parsed from the pod’s termination message, and jobabsorb.go already tolerates its absence - “the completed deploy pod left no readable result; deployedDigest stays unset” - because a pod evicted or deleted by hand leaves nothing to read. Today that is cosmetic, since the re-run trigger is the Job’s spec-hash annotation. Keying stage identity on the reported digest would make a lost termination message permanent: the recorded identity stays empty, mismatches forever, and the stage hot-loops under Reconcile or records nothing under ApplyOnce. The existing specHash over the rendered deploy spec already covers the digest, components, values and set, so it is the thing to compare; the pod’s digest stays a status field for display.

Which stages need ApplyOnce, precisely

A stage must be ApplyOnce exactly when re-running it would re-apply values that a later stage supersedes on the same Helm release.

StageCarriesStrategyWhy
init-seedinjector, seed registryApplyOnceSame release as registry, with values that stage supersedes - re-running reverts it
storage-seedimages, seed charts, bucketApplyOnceSame releases as storage-final, whose plain charts supersede these
registrypermanent registry, agentReconcileThe convergent half of the init package
storage-finalimages, plain charts, bucketReconcileThe end state, and where storage upgrades flow

The last stage must apply the plain charts, not merely re-push images. The reference bundle as originally written gets this wrong - its final stage selects images and the bucket but no charts, so the driver runs on seed values forever.

Both forms resolve, which is why the mistake is quiet: src/pkg/images/push.go pushes every image twice, once as <registry>/<path>:<tag>-<crc32>, which is what the agent’s rewrite produces, and once as <registry>/<path>:<tag>, which is what a hand-templated address asks for. What a cluster left on seed values loses is that the agent re-evaluates image references on every pod admission, while templated values were evaluated once - so the release hard-codes the registry address, and a mode switch, a port change or a move to an external registry leaves every pod in it pointing somewhere that no longer serves. The seed flavour exists because during the seed stage the agent is not running yet; it is scaffolding for one stage, and leaving it in place is leaving the scaffolding up.

Re-running a stage

  • Only changed stages re-run. Bumping one package does not re-deploy the others.
  • Re-runs happen in stage order. If two stages changed, the earlier goes first.

Those do not conflict, because the feared case - a changed early stage reverting a later one - is a stage that should have been ApplyOnce, which is a property of the package rather than of the ordering algorithm.

Ordering is the reconciler’s job, and the deploy slot does not provide it. clusterSlotHolder refuses to stamp a second Job while one runs on that cluster; nothing in it says stage 2 wins the slot before stage 4. It is also opt-out-able per Cluster through the concurrent-deploys annotation, so a stage list cannot lean on it as an invariant at all. What does carry over is settleInitJob’s shape: hold until the previous stage’s Job has settled, then proceed.

The hazard this leaves

A stage can be correct only because of an earlier stage’s side effect, and the controller cannot see that. storage-final needs its images in the registry registry stood up; if a re-run of registry ever recreated that registry’s storage rather than upgrading it in place, the images would be gone and storage-final would need to re-run even though its own identity did not change. The operator’s lever is to bump both. A per-stage rerunAfterEarlierStages flag is the obvious later addition if real sequences need it; a flag nobody has needed yet is not.

Readiness is the package’s job

A stage completes when its deploy Job completes, and the controller makes no attempt to decide whether the workload it installed is working. A per-stage readiness probe in the spec would put a second health model beside Zarf’s own and would have to be generic enough for every driver anybody packages. Zarf can already wait inside the package, where the author knows what ready means, so a package that reports success before its workload can serve is a bug in the package.

What that obliges of a package author is written up for operators in bootstrap-order.md. Two consequences here: a stage’s timeout is the Job’s timeout, and maxTotalSeconds inside the package is the real bound on how long a stage can take - invisible from the proxy, and usually the explanation for a stage that appears hung.

Dependencies stay between objects

Any dependsOn edge between whole proxies is allowed, and no edge may point at a stage. A stage list is its own and only order.

This is now a reuse rather than an extension: every edge is proxy-to-proxy, so the existing per-cluster evaluation and the existing cycle walk apply unchanged. A proxy depending on a staged proxy is satisfied when every stage has been applied on that cluster - all-or-nothing, which is what makes a sequence a single node rather than a sub-graph somebody can reach into.

Three reasons the stage-level edge stays out: it would be a second ordering mechanism over one object; cycle detection would have to span (object, stage) pairs rather than objects; and a half-run sequence has no sane answer for status or the deploy slot. The restriction costs nothing - a sequence needing something external in the middle is two proxies with a dependency between them, which object-level edges already express.

Two managers of one package

A package managed by two objects on one cluster is the shared-record collision: both own zarf-package-<name>, so whichever ran last owns it, removing either uninstalls it, and re-running the other reverts it.

The refusal has to be narrower than “two managers”, because one such pair is already a supported pattern. architecture.md’s seed-then-manage handoff is exactly two managers of one package name: an ApplyOnce proxy seeds zarf-init and a Reconcile proxy takes over the same name for day-two lifecycle, which “works by construction”. A symmetric refusal keyed on “two managers, one package, one cluster” would hold both sides of every fleet using it, fleet-wide, with no obvious fix.

So the conflict is two managers that will both re-execute. A manager whose release is Completed with applied set will never deploy again and cannot collide with anything; excluding it leaves the handoff alone and still catches what stages introduce, which is a stage and a separate Reconcile proxy both converging one package name. The successor must still be deletionPolicy: Retain, for the reason §3 gives.

Where it does apply, both sides hold rather than just the newcomer: there is no ordering between two live declarations that makes one the intruder, and holding only the second would let whichever reconciled first deploy over the other’s work.

What counts

  • The same resolved package name, not the same repository or object name - the record is keyed on the name the artifact declares, which the controller learns at resolution.
  • On the same cluster. Selectors that never overlap are not in conflict.
  • Between distinct managers that can still deploy. One proxy naming one package across several stages is the entire point and must never trip this.

Keying on the resolved name means this cannot be an admission check - no CEL rule can see a name that only exists after a registry read - so it is a reconciler-time hold, level-triggered like every other verdict here. The scan is also not single-namespace: with --cluster-namespaces, proxies elsewhere may select the same cluster.

Status and columns

The fleet roll-up stages reuse is internal/controller/aggregate.go, which lands in the same series of changes as this design rather than being something stages have to build: a Ready condition plus clusterCount, readyClusterCount and supersededClusterCount, with the reason taken from the first cluster that is not done, in selector order rather than the worst by severity, because every hold is equally a reason the fleet has not converged and a stable choice beats one that churns. Condition Events come from the single status-write choke point, so any new condition emits on transition with no extra wiring.

What stages still owe:

  • A STAGES column, 4/6, which needs integer status fields for the same reason readyClusterCount does - a printer column cannot take the length of a list.
  • A Version column that means something for a staged proxy, since it currently reads .spec.package.version.
  • Per-stage resolution status on the proxy. Resolution is fleet-level and cached per (ref, digest), so the proxy needs status.stages[] of its own carrying resolvedRef, resolvedDigest, packageName, packageKind and the signature and drift conditions. That is a second status list, distinct from the release’s applied-identity list.

Adopting a cluster the stages have not run on

Clusters will arrive that were bootstrapped by hand, by the Ansible collection, or before a clusterctl move discarded per-cluster state. Something has to decide whether each ApplyOnce stage already happened there.

The two ways of being wrong are not symmetric, and that decides the bias. Deciding “not satisfied” when a stage did run re-applies seed values over a converged cluster - measured to revert the permanent registry and, with upstream’s seedRegistry.persistence.enabled: false, to strip its storage configuration. Deciding “satisfied” when it did not run means a later stage fails loudly with its Job kept as evidence. Destruction versus a recoverable error, so ambiguity leans towards satisfied.

OptionCostWhy it is or is not enough
A. Zarf state exists on the clusternothing - hasZarfState already existsToo coarse: state is evidence about the init package, yet would satisfy every ApplyOnce stage, including a storage seed that never ran
B. Zarf’s record for that stage’s own packagenothing - hasDeployedPackage already existsPer-stage evidence from the cluster itself. Cannot tell two stages of one package apart, which does not matter here: if the init package was deployed at all, re-running its seed stage is the dangerous act
C. An explicit operator declarationa field or a Cluster annotationUnambiguous and auditable, but per-cluster toil, and forgetting it is the destructive direction
D. Refuse and hold until tolda condition and a runbookNever silently wrong, which is the house style - but every migrated cluster then needs a human touch where a single-package proxy needs none
E. Keep the stage record on the workload clustera secret the deploy pod writesSolves move, re-creation and adoption at once, and matches the principle that Zarf’s record of what is deployed lives on the workload cluster, not on the management cluster. The most robust and the most work

B is where to start, and it is also the cheapest thing that is not wrong. hasDeployedPackage(ctx, workload, <stage's package name>) is the probe a proxy’s ApplyOnce already uses. Two holes it leaves, neither arguing for a different start: a driver installed by something that is not Zarf leaves no record, so the seed stage collides with the existing Helm release - the takeOwnership gap, which already exists for proxies; and a half-finished init can leave state without a registry, where B skips the seed stage and the next one fails, which is the recoverable direction.

One thing to verify before committing to B: whether Zarf writes zarf-package-<name> on a partially-failed deploy. Nothing in this tree establishes it either way.

Editing a stage list that clusters have already run

A stage’s identity is its name, which is why stages are named rather than positional - and that is the hazard: a rename reads as a removal plus an insertion. The new name has never been applied, so it runs. On a Reconcile stage that is an idempotent redeploy; on an ApplyOnce seed stage it is the destructive case this design spends most of its decisions avoiding.

EditThe question it raises
Append at the endNone. A new stage has never run, so it runs. The only unambiguous edit
Insert in the middleDoes it run after stages declared after it? If yes the declared order was a lie for this cluster; if no the declaration is a lie about this cluster
RemoveWhat it deployed stays - nothing uninstalls. Is the record kept as history or pruned?
ReorderThe applied order is a historical fact and cannot be changed retroactively
RenameIndistinguishable from remove-plus-insert unless something says otherwise
  • A. Forward-only. Applied stage names are the state; anything else runs in declared order relative to other unapplied stages. Never destructive, and still exactly right for clusters that join later - the cost is that one document means two things depending on when a cluster arrived.
  • B. Refuse structural divergence. Applied names must remain a prefix of the declared list; otherwise hold with a condition naming the first divergence. Never silently wrong, and rigid enough that an append for new clusters can block a converged fleet.
  • C. Immutable stages, versioned objects. Reject edits other than appends. Strongest guarantee, worst fit for GitOps.
  • D. Split the list by strategy. ApplyOnce stages are history and immutable once applied - edits and renames refused as in B. Reconcile stages are desired state, where inserting, removing and reordering are free and order matters only among those needing to run, as in A.

D is the one worth building, because the per-stage strategy already divides the list into exactly those two halves, and it closes the rename hazard precisely where it bites. Two sub-questions it leaves: whether a removed stage’s record is pruned or kept - keeping it, marked undeclared, is safer, since it is the evidence an ApplyOnce decision rests on - and that the refusal is reconciler-time rather than admission, because CEL cannot see a per-cluster record.

What CEL can enforce, and should, is spec-only: stage names unique, and a stage’s strategy immutable once declared, since flipping ApplyOnce to Reconcile turns a history stage into a convergent one and re-runs it. A full validating webhook is not worth it for the rest: the precise check needs per-cluster state, this repo has no webhook infrastructure at all, and a webhook adds an outage mode where it being down blocks every edit - to replace a hold that clears itself.

What a first implementation needs that this does not cover

Found by review rather than by building. Each is a prerequisite rather than a nice-to-have, and none of them is cheaper under a separate kind.

  • A retry that is not a fleet-wide edit. BackoffLimit: 0 means one pod attempt and there is no retry timer, so a single node eviction fails a stage. The documented lever - edit the spec - changes the stage’s identity on every cluster, redeploying hundreds of healthy ones to retry one. At several stages across a large fleet, at least one eviction per rollout is the expected case. Either a bounded per-release retry with backoff, which the removal path already models, or a way to re-run one stage on one cluster.
  • A bound on how much deploys at once. The deploy slot is per cluster and nothing limits clusters in flight, so every cluster of a fleet created from one template enters stage 1 together - correlated bursts of multi-gigabyte pulls against one registry, which single-package proxies never produce. A --max-concurrent-deploys or a per-proxy maxConcurrentClusters is worth having on its own.
  • spec.paused is not honoured anywhere today. clusterctl move pauses objects before moving them; this controller keeps resolving, stamping and creating Jobs regardless. With a sequence in flight, a move can leave the source cluster’s Job deploying one stage while the destination’s rebuilt release starts the same stage again against the same workload cluster. A provider-conformance gap with or without stages.
  • Stage 1 has to be init-capable, and nothing says so. The init gate holds any package whose kind is not ZarfInitConfig on a cluster with no Zarf state. A sequence whose first stage is an ordinary package holds forever with reason WaitingForZarfState, naming the symptom rather than the mistake.
  • A test plan. The four-stage Ceph case is not reproducible in the CAPD-plus-local-registry e2e topology, so as specified it can never be regression-tested. A synthetic four-stage sequence over two trivial packages that deliberately share one Helm release would exercise every decision here and does fit the existing topology.
  • Per-stage Job and deploy-spec naming. <release>-<stage>-deploy plus a stage label on the Job, making Job creation the commit point with status read back off the labelled Job - otherwise a controller restart between creating a Job and writing status leaves a running Job whose stage nothing can recover, and for an ApplyOnce seed stage guessing wrong is the destructive direction. The 63-character name limit goes on the budget alongside a release name that is already proxy-plus-cluster derived.

Out of scope for a first version

Named so they are not mistaken for oversights: rollback, parallel stages, retry on a timer, per-stage architecture selection, deletionPolicy: Delete over a staged proxy - removal of a bootstrap sequence should not be something anybody gets by deleting an object - and generating a stage list from a uds-bundle.yaml.

Open questions

  1. How is an ApplyOnce stage satisfied on a cluster the proxy has not seen before? Punted deliberately, with the option space recorded above. Nobody has asked for adoption yet; option B is what a first implementation should do, costs nothing, and is not the destructive direction.
  2. What does editing the stage list mean? Open, with option D recommended above.

Everything else is decided: readiness is the deploy Job only; dependencies at object level and never at stage level; conflict refusal narrowed to managers that can both re-execute; changed stages only, in stage order; the final stage applies the plain charts; per-stage ApplyOnce by the superseded-values criterion; status shape settled and reused rather than redesigned; and the shape itself is a field rather than a kind.

One measurement that makes the last stage make sense

In nodeport mode the registry’s address in Zarf state is the same before and after the handover - the spike observed 127.0.0.1:31999 and a NodePort:31999 service after the seed stage and after the permanent one. That is why stage 2’s seed charts, whose image references are templated to {{ .State.Registry.Address }}, remain resolvable after stage 3 replaces the registry behind that address, and why stage 4 has to re-install the plain charts for the agent to take over rather than merely re-push images.

E2E testing: the kind + CAPD topology

The end-to-end suite runs the things test:envtest structurally cannot: real CAPI lifecycle machinery (a control-plane provider flipping ControlPlaneInitialized, the <cluster-name>-kubeconfig secrets CAPI writes, garbage-collection cascades), pods actually scheduling, and an OCI registry reachable from every side of the topology. It stands up a kind management cluster with CAPI core + CAPD initialized into it, one CAPD workload cluster with a CNI, and a ghcr.io/distribution/distribution:3 registry on the kind docker network, then runs the suite in the separate test/e2e module against all of it.

The workload cluster needs a CNI, and CAPD ships none

Worth knowing because it is invisible until something tries to run: a cluster CAPD creates has no CNI at all. Its node stays NotReady reporting cni plugin not initialized, coredns sits Pending forever, and nothing can be scheduled - while ControlPlaneInitialized is true, the kubeconfig secret exists, and the API server answers perfectly well. Phase 0’s spike assertions needed none of that, so the gap only surfaced when a deploy had somewhere to land.

e2e:up therefore applies Calico and waits for the node to go Ready. Calico because the Cluster API quick start pairs it with CAPD: its default pod CIDR is the 192.168.0.0/16 the development flavor hands out, so the manifest applies with nothing to reconfigure. The same step writes the workload cluster’s host-reachable kubeconfig to dist/e2e/workload.kubeconfig - the localhost/port-map variant clusterctl get kubeconfig rewrites, not the pod-reachable one in the secret - and e2e:run passes it to the suite as E2E_WORKLOAD_KUBECONFIG so assertions can read what a deploy actually left on the target cluster.

A second thing that cluster does not have is a StorageClass, so anything wanting a PVC there has to say otherwise - for the Zarf init package, init.set’s REGISTRY_PVC_ENABLED: "false".

go run ./magefiles/core e2e:up     # kind + clusterctl init + CAPD workload cluster + registry
go run ./magefiles/core e2e:run    # the suite, against the running topology
go run ./magefiles/core e2e:down   # removes everything, including the CAPD machine containers

e2e-walkthrough.md is the companion page: what each of those targets does step by step, what it leaves in dist/e2e/, and how to drive the suite from a terminal - running a single test, reading a failure, and starting genuinely clean.

e2e:up is idempotent and resumable - a failed run is re-runnable and picks up where it stopped. The suite does not tear the topology down; iterate on tests against a long-lived topology and run e2e:down when finished.

The forbidden invocation: a bare go test inside test/e2e/. The suite talks to a live topology through E2E_KUBECONFIG, which only e2e:run sets - without it every test skips, and a fully-skipped suite reads as green while asserting nothing. test/e2e is its own Go module precisely so the root go test ./... can never reach it; it is also deliberately unvendored, see the exception note in magefiles/AGENTS.md.

A test may only destroy what it created

One assertion in the suite has to delete a workload cluster - §8C, that destroying a cluster is never blocked by a package deployed to it - and the shared topology is sitting right next to it. The mistakes available here are all the same shape: a test aimed at one object reaches another, nothing complains, and the damage is done before any assertion reports it. This one has already happened once, by building the throwaway cluster from a deep copy of the standing cluster’s whole Spec: a Cluster spec carries controlPlaneRef and infrastructureRef, the topology controller fills them in with the objects it created, and deleting a Cluster deletes whatever those refs name - so the copy pointed the throwaway cluster at the standing cluster’s control plane, and its cleanup would have destroyed it.

So the rule, enforced rather than remembered:

  • Infrastructure the suite creates carries e2e.addons.colonel-byte.dev/owned-by: caapz-e2e-suite, and requireSuiteOwned refuses to delete anything without it. The standing topology belongs to e2e:up and carries no such label, which makes it undeletable from a test.
  • Build a throwaway cluster from the standing one’s topology and clusterNetwork only, never its whole spec. Carrying the topology over is what avoids hand-maintaining a CAPD topology and the ClusterClass variables it requires; carrying the refs over is what breaks it.
  • A delete of a Cluster checks its refs first, and bails if either names something outside that cluster.

The same reasoning applies to anything else expensive the suite might reach for - the registry container, the management cluster, the initialized Zarf state on the standing cluster. If a test needs to destroy one, it creates its own first.

Host prerequisites

docker, kind, and kubectl on PATH, network access (kind node images, the clusterctl binary, provider manifests), and one pair of kernel settings that is easy to miss:

Raise the inotify limits before the first e2e:up

kind’s own known-issues page documents this, and this repository has hit it: on a stock Linux host, fs.inotify.max_user_instances (often 128) is exhausted by a kind cluster running beside anything else that watches files - another local cluster, an editor, a file sync. The failure does not name inotify: pods on the fresh management cluster crashloop, and kubectl logs on kube-proxy (or cert-manager, or local-path-provisioner) shows

"command failed" err="failed complete: too many open files"

The fix, once per boot:

sudo sysctl -w fs.inotify.max_user_watches=524288 fs.inotify.max_user_instances=512

To make it survive reboots, persist it as a sysctl drop-in:

printf 'fs.inotify.max_user_watches = 524288\nfs.inotify.max_user_instances = 512\n' | sudo tee /etc/sysctl.d/99-kind-inotify.conf
sudo sysctl --system

The crashlooped pods recover on their own next restart once the limits are raised - no need to recreate the cluster.

What the suite covers today, and does not

Phases 0 and 1 of the plan. Phase 0 is the two spike assertions the deploy-Job model rests on in this topology - the server address written in the CAPD-generated kubeconfig secret is reachable from a management-cluster pod, and one registry name (caapz-e2e-registry:5000) resolves and pulls from management pods and workload nodes alike. Phase 1 is the controller running in the cluster: e2e:run builds the manager with the release Dockerfile, kind-loads it, and installs it through a workdir kustomize overlay over config/default (adding --registry-plain-http for the HTTP test registry), then asserts pure matching behavior on real CAPI objects - a release stamped Cluster-owned on selector match and deleted on un-match, a foreign-namespace proxy reconciling to zero matches without --cluster-namespaces, and the three dependsOn hold verdicts as live conditions. It does not yet deploy any Zarf package or exercise uninstall - those arrive with their phases (fixtures and the Cosign keypair first).

Every version the topology pins - clusterctl/CAPD, the workload Kubernetes version, the node/registry/test image digests - lives as annotated constants in magefiles/pkg/e2e/e2e.go, each with its Renovate annotation or written bump procedure per the pin-ownership rule in magefiles/AGENTS.md.

e2e-testing.md is the overview - what the suite is for, the topology, the host prerequisites, and the rule about what a test may destroy. This page is the other half: exactly what each target does step by step, what it leaves on disk, and how to work with it at a terminal rather than watching a CI log.

Read this before changing magefiles/pkg/e2e/, and before trusting a failure you did not cause.

The three targets

go run ./magefiles/core e2e:up     # build the topology (slow, idempotent, resumable)
go run ./magefiles/core e2e:run    # build and install the controller, then run the suite
go run ./magefiles/core e2e:down   # remove everything e2e:up built

Plus the pivot, which is separate because it roughly doubles the topology:

go run ./magefiles/core e2e:move      # second management cluster, then migrate onto it
go run ./magefiles/core e2e:moveDown  # remove only that second cluster

e2e:up and e2e:run are deliberately separate. Building the topology is minutes; running the suite is a couple of minutes. You build once and run the suite as many times as it takes.

What e2e:up does

Thirteen steps, each printed as ==> <name> so a failure names its own step. Every one is idempotent, so re-running after a failure continues rather than starting over.

14app fixture in the secure registryCopies the app fixture from the plain registry into the secure one with oras - the SDK’s publish takes no credentials
15init package mirrorCopies the v1beta1 init package into the local registry, registry to registry. The one large transfer; skipped when already present
16zarf in the management clusterZarf-initializes the management cluster itself through the SDK, in proxy mode so Zarf issues a registry certificate - what fromZarfState reads. Labels the node for the registry’s affinity, and every existing namespace zarf.dev/agent=ignore, first

Step 10 is where four CAPD facts live, each of which is invisible until something needs it. A CAPD cluster has no CNI, no StorageClass, a control-plane taint that disqualifies every node from Zarf’s injector, and a baseline Pod Security standard that forbids the storage provisioner’s hostPath helper pod. All four are documented at the code.

Step 16 is the only step that changes the management cluster rather than adding to it. Zarf’s agent webhook is failurePolicy: Fail over every pod CREATE and rewrites image references, and its namespace selector excludes only kube-system - so CAPI’s, CAPD’s, cert-manager’s, the controller’s and every deploy Job’s images would be rewritten to a registry that does not hold them. Two things prevent it: the init sets MutationPolicyLabeled, so nothing is mutated that has not asked to be, and every existing namespace is labelled zarf.dev/agent=ignore, so the webhook is not even called for them and an unhealthy agent cannot block a pod from starting. Do not remove either without reading zarfstate.go’s comment on why they fail differently.

What e2e:run does

3controller manifestsRenders a workdir kustomize overlay over config/default, applies it, restarts the rollout, waits for it

Then it runs go test in test/e2e with the environment the suite reads:

VariablePoints at
E2E_KUBECONFIGThe management cluster
E2E_WORKLOAD_KUBECONFIGThe workload cluster, host-reachable variant
E2E_KEY_DIRThe fixture keypairs, so a test can name a public key a proxy verifies against

The rollout restart in step 3 is not redundant. A reinstall with an unchanged manifest changes nothing, so the rollout wait would pass against the pod still running the old image - which is how a code change appears to have no effect.

Driving it by hand

First run

go run ./magefiles/core e2e:up
go run ./magefiles/core e2e:run

Expect roughly ten to fifteen minutes for e2e:up on a cold cache - most of it pulling the CAPI provider images, the kind node image, and the init package - and a little over three minutes for e2e:run. A warm e2e:up that only has to re-check things is well under two minutes.

If e2e:up fails, read the ==> line above the error: that is the step, and every step is safe to re-run. Just run e2e:up again.

Iterating on controller code

e2e:run rebuilds and reinstalls the controller every time, so the loop is just:

# edit internal/controller/...
go run ./magefiles/core e2e:run

No teardown, no reinstall by hand. The topology outlives the controller.

Running one test

The suite is a normal Go test binary, so -run works - but it has to be given the environment, and a bare go test in test/e2e silently skips everything rather than failing. Export what the target would:

cd test/e2e
export E2E_KUBECONFIG="$PWD/../../dist/e2e/mgmt.kubeconfig"
export E2E_WORKLOAD_KUBECONFIG="$PWD/../../dist/e2e/workload.kubeconfig"
export E2E_KEY_DIR="$PWD/../../dist/e2e/keys"
go test -count=1 -v -run TestAutoInitAndDeploy ./...

This skips e2e:run’s controller rebuild, so it runs whatever is already installed. After changing controller code, run e2e:run once to reinstall, then iterate with -run.

-count=1 matters: without it a passing result can come from the test cache rather than from the cluster.

Watching it work

The suite logs progress while it waits, which go test only shows with -v or on failure. Watching the cluster directly is usually faster:

watch 'kubectl --kubeconfig dist/e2e/mgmt.kubeconfig get zarfpackageproxy,zarfpackagerelease,jobs'

watch 'kubectl --kubeconfig dist/e2e/workload.kubeconfig get pods -n zarf'

Starting genuinely clean

A clean run is the only thing that proves e2e:up encodes every step rather than depending on something applied by hand earlier. Three of the bugs in that table above were found exactly this way, and could not have been found any other way.

go run ./magefiles/core e2e:moveDown
go run ./magefiles/core e2e:down
rm -rf dist/e2e
go run ./magefiles/core e2e:up
go run ./magefiles/core e2e:run

Removing dist/e2e is the part that matters. e2e:down removes clusters and containers; the workdir is what holds cached manifests, generated fixtures, and keys, and a cached manifest is how a stale pin stays invisible.

Do this before trusting the harness after any change to magefiles/pkg/e2e/.

The pivot

go run ./magefiles/core e2e:run    # the pivot carries what this deployed
go run ./magefiles/core e2e:move
go run ./magefiles/core e2e:moveDown

e2e:move reuses the controller image and rendered manifest e2e:run produced rather than rebuilding, so the two management clusters are running the same binary - which is the situation a real migration is in.

It leaves the topology pivoted onto the target: the workload cluster is managed by caapz-e2e-target, and the proxies are still on caapz-e2e. That is the behaviour under test, not a mess to clean up - but it does mean a subsequent e2e:run against the source has no cluster to match. Tear down and rebuild after a pivot.

Things that will catch you out

  • A bare go test in test/e2e skips everything and exits 0. It is a separate module precisely so the root go test ./... cannot reach it, and every test skips without E2E_KUBECONFIG. A fully-skipped suite reads as green; e2e:run is the invocation that means anything.
  • The suite shares one topology across tests. Tests clean up after themselves and establish their own preconditions - the auto-init test de-initializes the cluster first, for instance - but an interrupted run leaves state behind. If results stop making sense, start clean.
  • test/e2e is its own module and is deliberately unvendored. Running go mod tidy there is part of changing it; CI checks it separately from the root module.
  • Only one deploy or removal Job runs per cluster at a time. A row of releases sitting in Pending/WaitingForActiveDeploy while one is Deploying is the design working, not a stall.

New repository checklist

Generating a repository from a template copies files, not settings. Everything in this template is a file, so it all arrives; everything in the Settings tab does not, and several of the files that arrive are inert until a matching setting exists. A CODEOWNERS that requires nothing and a workflow that goes green while the site 404s both look fine from the file list.

Two more things about generation, both easy to be surprised by: the new repository starts with a single initial commit - no history, tags, releases, or issues - and there is no ongoing link to the template. Nothing syncs a later template improvement forward; it has to be copied by hand.

Do this first

The placeholder sweep is the first section of the root AGENTS.md, and it comes before anything below. A badge or a book.toml URL left on the template’s slug reports another repository’s state as this one’s.

The parts that can be scripted

REPO=colonel-byte/cluster-api-addon-provider-zarf

# Labels the issue forms name.
for l in bug ci test-flake enhancement documentation stack-task; do
  gh label create "$l" --repo "$REPO"
done

# Labels renovate.json5 names.
for l in renovate/oci renovate/action renovate/gomod renovate/npm renovate/pre-commit security; do
  gh label create "$l" --repo "$REPO"
done

# Secrets. The app credentials are shared with release-please; the cosign pair signs the
# release archives. Omit any that are already org-level secrets visible to this repository -
# but see the note below before omitting the cosign pair.
gh secret set RELEASE_PLEASE_GITHUB_APP_ID --repo "$REPO"
gh secret set RELEASE_PLEASE_GITHUB_APP_SECRET --repo "$REPO" < path/to/app-private-key.pem
gh secret set COSIGN_KEY --repo "$REPO" < path/to/cosign.key
gh secret set COSIGN_PASS --repo "$REPO"

COSIGN_KEY and COSIGN_PASS are the secret names; release.yaml maps them onto COSIGN_PRIVATE_KEY and COSIGN_PASSWORD, which are cosign’s own variable names and are not renameable. Renaming one side only produces an error at the signing step rather than a missing-secret error.

The cosign pair is the one secret that cannot just be inherited

cosign.pub at the repository root is the public half of whatever COSIGN_KEY signs with, and it is the inverse of everything above: a file, so generation copies it, which is exactly the problem. Omitting the secret because an org-level COSIGN_KEY is visible leaves the template’s cosign.pub in place beside a different key, and the two no longer belong to the same pair.

Nothing reports that. goreleaser and publish-oci-artifact.yaml sign without verifying, so they go green while publishing artifacts that cannot be verified with the cosign.pub the docs point a consumer at. The only step that verifies is publish-zarf-package.yaml’s publish, which fetches cosign.pub from the release tag and fails with invalid signature when validating ASN.1 encoded signature - a signing-key error reported at the last step of the release, several minutes after the key that caused it was used.

So pick one, and do it before the first release:

  • Inherit the org pair - replace cosign.pub with the public half of the org key. Do not keep the file that arrived with the template.
  • Override it per repository - gh secret set COSIGN_KEY --repo "$REPO" shadows the org secret, and cosign.pub stays as it is. This needs the private half of the committed key to actually exist somewhere.

Either way the pair can only be checked against something already signed, so the check is the first thing to run after the first release rather than part of the setup above - the controller image goreleaser pushed is the earliest artifact there is:

cosign verify --key cosign.pub ghcr.io/colonel-byte/cluster-api-addon-provider-zarf-controller:0.1.0

Verifying it rather than assuming it

Each of these answers one row of the table, and each has a failure mode that is silent otherwise:

gh label list --repo "$REPO"                                               # every label the forms and renovate name
gh secret list --repo "$REPO"                                              # repo-level only; org secrets do not appear here
gh api "repos/$REPO/actions/organization-secrets" --jq '.secrets[].name'   # the org ones that will be used
gh api "repos/$REPO/rules/branches/main"                                   # [] means nothing is enforced on main
gh api "repos/$REPO/pages" --jq .html_url                                  # 404 until Pages is enabled

Then open https://github.com/colonel-byte/cluster-api-addon-provider-zarf/issues/new/choose on a branch after changing an issue form. A malformed form is reported as a banner on that page and nowhere else - parsing as YAML is not enough to know it renders.

First run, in order

Each step fails in a way that looks like the one before it, so do them in this order:

  1. Push to main. This is what first runs scorecard.yaml and deploy-book.yaml, and what gives the badges something to resolve against.
  2. Dispatch Renovate with dryRun: true. The log lists every update it resolved without touching the repository - see renovate.md. A bad customManagers regex matches nothing and reports success, so this is the run that tells you.
  3. Open a throwaway pull request. Five checks should appear: Validate Lint, Validate pre-commit hooks, CodeQL, PR Title Check, Check for go mod changes. A check that does not appear is a workflow whose trigger or filename is wrong, not a flake.
  4. Mark the checks required, once they pass. Until then commitlint.yaml’s merge_group branch does nothing, and CODEOWNERS is a suggestion.
  5. Let release-please open its first pull request. Merging it pushes the first tag, which is what release.yaml fires on, and what turns the Latest Release badge from no releases into a version.

Still to write, per repository

adding-ci.md covers the two workflows this template deliberately does not ship - unit tests and end-to-end - and the three things that change in the same pull request when you add either.

Check for go mod changes

.github/workflows/check-go-mod.yaml is what makes the vendored, offline build a requirement rather than a convention. It runs on every pull request and on the merge queue, and it fails for one reason: go.mod, go.sum and vendor/ do not agree with each other.

The three steps

  • go mod tidy, go mod vendor, then git diff --exit-code go.mod go.sum vendor/. Re-resolves the graph and re-vendors from scratch, then fails if the result differs from what was committed. This catches a dependency added without running mage dev:vendor, and a vendor/ left behind by a hand-edited go.mod.

  • go run ./magefiles/core dev:verifyVendor. Runs go mod verify, then builds with GOFLAGS=-mod=vendor GOPROXY=off - the invocation a release has to survive. This catches a vendor tree that is internally consistent but incomplete.

  • go mod tidy then git diff --exit-code go.mod go.sum, inside test/e2e. That suite is a separate module and deliberately unvendored, so a nested module is invisible to the root’s ./... and the first step cannot reach it. It drifts anyway, and not because anyone edits it: it requires this repository’s own module through a replace ../.., so every dependency the root module moves changes what the e2e module’s graph resolves to. Tidy only - vendoring it would bloat every clone to protect an offline-build invariant that does not apply to a dev/CI-only surface.

The go run ./magefiles/core form rather than mage: same targets, builds from vendor/, needs no mage binary on the runner.

Why both

They fail on different mistakes, and the second is the one that costs an afternoon. A vendor/ missing a file still builds locally, because the file is on disk - it is only a fresh clone that notices. The commonest cause is not a forgotten go mod vendor at all, but a .gitignore pattern that quietly excluded part of the vendor tree; see “A new .gitignore pattern can silently empty part of vendor/” in magefiles/AGENTS.md.

That check is one command, and it is worth running by hand when a pattern changes:

git ls-files --others --ignored --exclude-standard -- vendor/

It should print nothing.

The e2e module was unmanaged as well as unchecked

Worth knowing because the two halves hid each other: config:recommended ships an ignorePaths that includes **/test/**, so Renovate never saw test/e2e/go.mod either. Nothing updated it and nothing checked it, and the drift surfaced only when go vet inside that directory began refusing to run. renovate.json5 now restates ignorePaths without that entry, keeping **/vendor/** - a vendored module’s own go.mod is upstream’s, not ours to bump.

When it fails on a bot’s pull request

A dependency update re-vendors as part of the change, so the first step passes. Where it does not - a module that moved import paths, say - the fix is a human running mage dev:vendor on the branch, not a rerun.

CodeQL

.github/workflows/codeql.yaml runs GitHub’s CodeQL analysis on pushes to main, on pull requests, on the merge queue, and weekly. Results land in the repository’s Security tab. The weekly run is not redundant: it picks up queries and advisories published after a commit landed.

Two languages are analyzed, with different build modes:

LanguageBuild modeWhat that means
gomanualThe workflow’s own go build decides which packages get extracted
actionsnoneThe workflow files themselves are scanned, no build involved

The Go build step is the package list

This is the part that needs maintaining. Because Go is analyzed by building it, CodeQL’s paths-ignore setting does not apply - it has no effect on Go - so every exclusion has to be expressed as the set of packages the build step names.

Today that is ./magefiles/pkg/... and nothing else, because magefiles/*.go is package main behind //go:build mage and mage supplies the main function at runtime, so go build cannot compile it at all. ./... would pick it up and fail.

Widen the list one package at a time as the repository grows - ./cmd/..., ./internal/..., ./pkg/..., and . for a root package. A pattern matching no package fails the build step, so adding a path before the package exists breaks the scan rather than skipping it.

It builds offline, like everything else

GOFLAGS=-mod=vendor, GOPROXY=off, GOSUMDB=off, GOTOOLCHAIN=local. Everything the build needs is vendored, so an accidental network access fails fast rather than quietly succeeding on a runner and failing in an air-gapped build. This matches the environment check-go-mod.yaml enforces.

Permissions

security-events: write to upload the results, actions: read for the actions language to read workflow files, and packages: read for any private module the build resolves. All three are on the job, not the file - see .github/AGENTS.md, where a top-level write zeroes Scorecard’s Token-Permissions check.

PR Title Check

.github/workflows/commitlint.yaml lints the pull request title against conventional commits. It is a standard across the organization, and it is load-bearing rather than cosmetic: pull requests are squash-merged, so the title becomes the commit message on main, and release-please reads those messages to decide the next version and to write docs/misc/CHANGELOG.md. A title with the wrong type produces a release with the wrong version number.

This is why the job lints the title and not the commits. wagoid/commitlint-github-action lints commit messages, which are the ones squashing throws away, so it is not a drop-in replacement for this step.

The two configs

FileApplies toDifference
.github/commitlint/.commitlintrc.yamlHuman authorsheader-max-length of 100
.github/commitlint/.commitlintrc.bot.yamlAny author whose login ends [bot]header-max-length off

A bot cannot shorten a module path, and build(deps): bump <module> from X to Y runs past 100 characters for any dependency with a long import path. Turning the rule off for everyone would lose the one thing it buys - a readable git log - so it is off for bots only, and every other rule still applies to them.

The two files must stay in step on every rule but that one. Commitlint cannot extend a YAML sibling, so there is no shared base and the duplication is real; a rule added to one and not the other is a rule humans or bots quietly escape.

Why the bot match is a suffix, not a name

The author switch matches *[bot] rather than a list of names. Self-hosted Renovate opens pull requests as whichever GitHub App minted its token - see renovate.md - so the name is not knowable from inside this file, and a hard-coded one fails by silently linting a bot’s title against the strict config. The suffix is assigned by GitHub and cannot be spoofed by a human account.

It reports success on merge_group

The job is intended to be a required status check, which means the merge queue waits for a title_check result on the merge_group ref as well. There is no pull request under that event, so every step is skipped and the job passes - the title was already linted on the pull request that got queued. Skipping the whole job instead would leave the check with no result at all, which blocks the queue forever.

The same reasoning applies to bots: the job runs for them with a laxer config rather than being skipped, because a skipped job produces no result for a required check.

Bumping commitlint

package.json and package-lock.json in .github/commitlint/ pin @commitlint/cli and @commitlint/config-conventional, and the workflow runs npm ci, so the lockfile is what is installed. Renovate’s npm manager owns both - there is no bump procedure to follow by hand.

GitHub Pages

.github/workflows/deploy-book.yaml builds the mdBook from docs/ on every push to main and pushes the result to the gh-pages branch, which is what serves https://colonel-byte.github.io/cluster-api-addon-provider-zarf/.

It needs no secrets: GITHUB_TOKEN is enough to push to gh-pages, and contents: write is granted on the job rather than at the top of the file.

It publishes, it does not regenerate

mdbook build renders whatever docs/ holds at that commit. Three of those pages are generator output - docs/index.md, docs/security.md and docs/SUMMARY.md - and nothing here runs the generator, so a page that was not regenerated before merging is published stale rather than rebuilt.

That is deliberate: a deploy that regenerates would publish content that is not in the repository, so the committed tree and the published site would disagree. The docs-generator pre-commit hook is what keeps them in step, and check-go-mod.yaml is the model - catch it before the merge, not after.

Pages has to be enabled, and that is not in the repository

This is the one part the template cannot carry. The workflow pushes to gh-pages whether or not Pages is configured, so it goes green while the site 404s. In the repository’s Settings, under Pages, set the source to Deploy from a branch, branch gh-pages, folder /. See new-repo-checklist.md for the rest of the settings that do not travel from a template.

Until that is done, every https://colonel-byte.github.io/cluster-api-addon-provider-zarf/ link - in README.md, the issue chooser, and docs/AGENTS.md’s redirect rules - points at nothing.

The redirect rule matters here

Because the site is published, renaming or moving a page breaks whatever already links to it from outside the repository, and mdBook does not notice - the old URL simply 404s. A move comes with an [output.html.redirect] entry in book.toml. docs/AGENTS.md has the exact form, including why the value is resolved relative to the key’s own directory rather than the site root.

Building it locally

mdbook build && mdbook serve

mdbook serve watches docs/ and reloads, which is the quick way to check a redirect actually resolves - the redirect file appears at the old path and names the new one.

Install smoke test

install-smoke.yaml proves, on every pull request, that the provider actually installs through clusterctl init and the controller comes up - the Cluster API contract rather than the Go code, mirroring cluster-api-provider-cargoship’s workflow of the same name.

Everything it catches is silent elsewhere. A CRD missing the cluster.x-k8s.io/<contract> label is ignored rather than rejected, so the provider installs, the controller starts, and nothing ever reconciles. A metadata.yaml that does not name the contract makes clusterctl init refuse outright. RBAC one verb short fails at the first reconcile, in a log nobody reads. No unit test, lint run, or kustomize build fails on any of those.

The job builds the controller image with release:image (the release Dockerfile against goreleaser’s context layout, under the offline GOPROXY=off flags a release has to survive), kind-loads it, renders out/addon-components.yaml with release:manifests, lays the result out as a local clusterctl provider repository (addon-zarf/{version}/, version read from metadata.yaml’s release-please markers so it never goes stale), and runs clusterctl init --infrastructure docker --addon zarf:<version> --wait-providers. It then asserts the two CRDs are Established and carry cluster.x-k8s.io/v1beta2: v1alpha1, the caapz-controller-manager deployment is Available, and the manager log reaches its start line without a fatal setup error.

It deploys no Zarf package - that is the e2e suite’s job (e2e-testing.md), which needs CAPD workload clusters and a registry. Installing and coming up is a different and much cheaper question, which is why this one can gate every pull request.

goreleaser

.github/workflows/release.yaml builds and publishes the release artifacts. It fires on any pushed tag, and in practice that tag comes from release-please.yaml merging its release pull request.

What it produces, from .goreleaser.yaml:

  • one linux binary per goarch, version and commit baked in via -ldflags -X
  • a tar.gz per architecture, named to match uname output
  • the controller image ghcr.io/colonel-byte/cluster-api-addon-provider-zarf-controller, built for linux/amd64 and linux/arm64 from containers/manager/Dockerfile and cosign-signed (docker_signs:) - which is why the workflow sets up QEMU, Buildx, and a ghcr.io login before goreleaser runs, and why the job holds packages: write

Those are the secret names. The workflow maps them onto the environment variables .goreleaser.yaml reads, COSIGN_PRIVATE_KEY and COSIGN_PASSWORD, which are cosign’s own and are not renameable. Running it against a tag that does not exist

Renovate

.github/workflows/renovate.yaml runs Renovate against this repository and nothing else, hourly and on demand. It replaces the hosted renovate[bot] GitHub App: the bot is not installed, and the config in .github/renovate.json5 is read by this run rather than by Mend’s servers.

Why it runs self-hosted

The hosted app is simpler and needs no workflow. What it cannot do is use this organization’s own GitHub App credentials, and that matters for two reasons:

  • Pull requests opened with an app installation token trigger other workflows. A pull request opened with the default GITHUB_TOKEN does not, by design, so a dependency branch would sit with no checks on it - and an update nothing has tested is not something a reviewer can act on.
  • One app, one audit trail. The same app that release-please uses opens these, so there is one installation to grant, one private key to rotate, and one bot in the repository’s audit log.

The cost is that the workflow is now a thing to maintain, and that the Renovate version is pinned - the renovate-version input in the workflow, which Renovate bumps itself via its datasource comment - rather than tracking the hosted service.

The run is cached, which is what makes it hourly

Renovate resolves every dependency from the registry on each run, and on a 540-module vendored tree that is most of the wall clock - an uncached run takes upwards of twenty minutes. The workflow restores a RENOVATE_REPOSITORY_CACHE of resolved versions and changelogs before the Renovate step, which is the only reason an hourly cron is affordable rather than a way to spend the Actions budget re-asking the module proxy the same questions.

Two things follow. The cache key carries github.run_id, so every run writes a new entry and restore-keys picks up the newest previous one; a fixed key would be written once and then never updated. And the renovate concurrency group holds cancel-in-progress: false, so a run that outlasts its hour queues the next one instead of overlapping it - the schedule degrades to “as often as a run takes” rather than breaking.

How often this fires is not how many pull requests arrive. That ceiling is prHourlyLimit and prConcurrentLimit in .github/renovate.json5; the cron only decides how quickly a new release is noticed.

Bringing it up the first time

In this order, because each step fails in a way that looks like the one before it:

  1. The two secrets exist on the repository, or at the organization with this repository in scope. Without them create-github-app-token fails on the first step with an authentication error, which is the one unambiguous failure in the list.
  2. The app is installed on this repository, with the four permissions in the table above. A missing install looks like Renovate reporting the repository as not found; a missing permission looks like Renovate ignoring one manager.
  3. The labels in renovate.json5 exist. GitHub drops an unknown label from a pull request without reporting it, so the branch arrives unlabelled and nothing says why - the same trap the issue forms have. README.md has the gh label create lines.
  4. Dispatch with dryRun: true first. The log lists every update Renovate resolved and what it would have opened. This is the run that tells you whether the custom-manager regexes match anything, and it cannot leave a half-made branch behind.
  5. Then dispatch for real and read the dependency dashboard, not the pull request list. The dashboard is the proof the run completed and had write access; an empty pull request list on its own is ambiguous between “working” and “found nothing”.

Two things to expect on a repository that has only this workflow in it:

  • gomod, pre-commit and docker find nothing, because there is no go.mod, no .pre-commit-config.yaml and no Dockerfile yet. Those managers reporting zero dependencies is correct, not a misconfiguration. Only github-actions has anything to read.
  • The first real run should open exactly one pull request: actions/create-github-app-token is pinned at v3.3.0 here and v3.4.0 is out. That is a deliberately useful starting state - it means the first run has one unambiguous thing to do, and a run that opens nothing is a signal rather than a shrug. Do not bump that pin by hand before testing.

Validate Lint

.github/workflows/scan-lint.yaml runs golangci-lint over the module on every pull request and on the merge queue, against .golangci.yaml.

The version is read, not written

This is the part worth understanding before changing the workflow. golangci-lint-action installs the latest release when given no version, so CI can lint with a newer golangci-lint than the hooks pin - and a new release that adds a check produces a failure that reproduces nowhere locally.

So the workflow reads the version out of .pre-commit-config.yaml with awk and passes it to the action. One pin, in one place:

  • Renovate’s pre-commit manager bumps the rev: in that file.
  • Renovate’s github-actions manager updates uses: references - not inputs inside a with: block.

A second pin written into the workflow is therefore one that nothing keeps in step with the first, which is exactly the drift this avoids. The awk fails the job if it cannot find the rev, rather than silently falling through to the next repo: entry and reporting some other tool’s version back.

What .golangci.yaml excludes, and why it has to

magefiles/*.go and magefiles/core/ are excluded. Those files are package main behind //go:build mage, and mage supplies the main function at runtime, so the linter cannot build them - with or without -tags mage. Everything under magefiles/pkg/ is ordinary Go and is linted like the rest of the module.

Two settings worth knowing before adding a //nolint:

  • nolintlint is on with require-specific: true, so a bare //nolint fails. Name the linter.
  • errcheck has check-blank: true, so _ = f() is an error too. The house answer is an entry in errcheck.exclude-functions for a function whose error is never actionable, not a suppression at each call site.

Dockerfiles

Cargoship’s version of this workflow carries a second containers job, one matrix entry per Dockerfile, running hadolint. It is left out here as a TEMPLATE: comment because there are no Dockerfiles yet. Note when adding it that hadolint’s action takes a single path and its recursive mode globs from the repository root, which drags in the vendored Dockerfiles under vendor/ - so the paths are listed explicitly.

Annotating a check that is wrong rather than fixing it

Some findings are correct about the file and wrong about the project - a vendored dependency’s own CI script tripping Pinned-Dependencies, say, which no build here ever invokes. Those go in .github/scorecard.yml, which this template deliberately does not ship, because an annotation with no reason behind it is worse than a lower score.

The shape, when one is needed:

annotations:
  - checks:
      - pinned-dependencies
    reasons:
      # Why this finding does not apply here. Name the file, say what it is, and say why
      # nothing in this repository's build or CI path runs it.

Two rules about that file, both learned the hard way:

  • Every annotation carries its reason as a comment, not just the enum. not-applicable on its own tells the next reader nothing, and the finding will look like an oversight to be cleaned up.
  • An annotation outlives what justified it. When the dependency goes or the script stops being vendored, the entry is still there, still suppressing a real finding. The root AGENTS.md treats removing one as the operator’s call rather than a documentation change - flag it, do not quietly delete it.

docs/agent/

The record of decisions that are not recoverable from the code. Everything here answers a question of the form “why is this odd thing the way it is”, asked by someone - a person or an agent - who is about to change it back.

choice-*.md are constraints, not history

This is the convention the root AGENTS.md leans on, and the reason the directory exists. A choice-*.md file records a tradeoff that was made deliberately and that looks, from the code alone, like an oversight waiting to be cleaned up: a suppression in a scanner config, a dependency pinned below its latest version, a backend selected by one property rather than the obvious one, a test fixture that duplicates something upstream.

Three rules follow from that:

  • Write one when the code cannot carry the reasoning. A comment is better than a document whenever it fits. What goes here is the decision too long for a comment and too load-bearing to lose - typically one where the alternative was tried, or where the cost of the choice is paid somewhere far from where it was made.
  • Read before reversing. The root AGENTS.md names three or four things that look reversible and are not. If a change here would undo something a choice-*.md argues for, the document is the first thing to read and the argument is the thing to answer - not the code.
  • A superseded choice is marked, not deleted. When the thing a document justified goes away, the reasoning usually still explains something that is still here: a Dependabot ignore entry, a Scorecard annotation, the shape of a package. Mark it superseded, name what superseded it, and leave the argument in place. Deleting it loses the answer to “why is this still configured”.

What else belongs here

  • AI usage disclosure. How agents are used in this repository and what review they are subject to. Where a release publishes a disclosure manifest, this is the page it is a snapshot of.
  • Design notes an agent wrote for itself - an investigation, a measurement, a survey of three approaches - where the conclusion is worth keeping but is not a decision. Name these something other than choice-*, so the constraint files stay findable.

What does not

An internal note is not a guide. If an operator would ever run the commands in it, it belongs in docs/guides/; if a contributor would, it belongs in docs/dev/. The distinction matters because the checking standard is different - a wrong count in a note here costs a reader a minute, and a wrong command in a guide costs an operator an afternoon.

The controller reads Clusters through CAPI’s typed API module

The controller imports sigs.k8s.io/cluster-api/api - the types-only module CAPI split out at v1.11 - and reads Cluster objects as clusterv1.Cluster from api/core/v1beta2. It does not read Clusters as unstructured.Unstructured or PartialObjectMetadata, and it does not import the main sigs.k8s.io/cluster-api module. Decided 2026-11-21, before the first functional reconcile milestone, which this gates. The pin is v1.14.4, matching cluster-api-provider-cargoship.

Why typed rather than unstructured

  • The v1beta2 contract is a set of field paths, and hand-encoding them is the failure mode the contract pass just fixed. The architecture doc moved from status.controlPlaneReady (v1beta1) to status.initialization.controlPlaneInitialized (v1beta2) precisely because a string path written from memory had drifted across contract versions. Unstructured access re-encodes every such path as a string literal (NestedBool(obj.Object, "status", "initialization", "controlPlaneInitialized")) that compiles against any contract, wrong or right. The typed struct makes the next contract migration a compile error instead of a silent false.
  • The sister repo has already validated the exact pin combination. cluster-api-provider-cargoship pins sigs.k8s.io/cluster-api/api v1.14.4 against the same controller-runtime v0.25.3 and apimachinery v0.37.2 this module pins, so the compatibility question the vendored build makes expensive to discover late is already answered in production next door. Mirroring its pin also keeps the two providers’ Renovate upgrades in lockstep.
  • The surface only grows from here. The reconcile core starts with labels, controlPlaneInitialized, and ownerReferences, but §6 already commits to reading conditions (ControlPlaneInitialized), status.phase for deletion handling, and the concurrent-deploys annotation - and envtest needs the real types to build fixture Clusters. An unstructured shim that is tolerable for three fields is not tolerable for the full §6/§7 read set, and converting mid-implementation would churn every reconciler layer above it.

What it costs: a vendored dependency carried by every clone. The types-only module bounds that - its dependency graph is apimachinery-sized, not the main module’s (which links the full CAPI controller machinery, webhooks, and feature gates). go list -deps the import before widening it.

The boundary: types module yes, main module not yet

Only sigs.k8s.io/cluster-api/api is imported. The main sigs.k8s.io/cluster-api module’s util/* helpers (patch, conditions, predicates) are genuinely useful and cargoship imports them - but each is a separate, later decision with its own vendor delta, taken when a reconciler actually wants the helper, not pre-emptively. Nothing here forecloses adding it; this file records that its absence today is deliberate, not an oversight.

A deploy runs in its own Kubernetes Job, and verification precedes it

Every package deploy (and removal) runs in a Kubernetes Job the controller stamps - one per ZarfPackageRelease - never in the controller process. The controller resolves the package’s tag to a digest and verifies its Cosign signature at resolution time, before any Job exists; the Job pulls that verified digest. Both halves were decided together, on 2026-11-20/21, and constrain the deploy subcommand, the resolver, and the manager deployment manifests. The user-facing contract is docs/dev/architecture.md §6 steps 4 and 6; this file is the why.

Why a Job rather than the in-process SDK

  • Zarf’s deployer selects its target cluster from the process environment. packager.Deploy (zarf v1.0.1, src/pkg/packager/deploy.go) takes no cluster handle: the unexported deployer calls cluster.NewWithWait, which resolves via clientcmd.NewDefaultClientConfigLoadingRules() - the KUBECONFIG environment variable. In-process, the only multi-cluster workaround is swapping a process-global variable under a mutex, which serializes every deploy fleet-wide and races anything else reading client-go loading rules. In a Job, “process environment” is a per-pod property: mount the <cluster-name>-kubeconfig secret, point KUBECONFIG at it, done. Parallelism across clusters is pods, not a scheduler we maintain.
  • Package actions are arbitrary command execution on the deploying machine. In-process, every package author gets code execution inside the pod whose service account can read every cluster’s kubeconfig secret. In a Job, the blast radius is one pod holding one cluster’s kubeconfig and a minimal service account.
  • Deploy lifetime decouples from controller lifetime. Packages are routinely tens of gigabytes and deploys run for tens of minutes; actions can legitimately block. A controller restart, leader-election flip, or OOM no longer kills in-flight deploys - the reconciler observes the Job it finds.
  • The package cache becomes a Job-pod concern. The largest-package disk mount moves off the controller and onto deploy pods, which spec.deployJob.nodeSelector can target at big-disk nodes.

What it costs: a deploy subcommand in the controller’s own image (no separate zarf binary to ship or pin), result plumbing from Job to release status, per-deploy spec handoff, and worse default cache reuse (per-Job emptyDir; a zarf-cache PVC volume is the escape hatch). The retry owner is the reconciler - Jobs carry backoffLimit: 0 - so the release stays the single record of attempts.

This forecloses the in-process SDK path. If zarf later grows a cluster-injection API (unchecked past v1.0.1), reasons two through four still stand; do not unwind this for that alone.

Why verification sits in the controller, not the Job

The two candidate orderings were: the Job pulls and verifies (verification code lives beside the cache it needs), or the controller verifies first and the Job pulls what was verified. The second won, with one refinement that removes its apparent cost:

  • Verifying a Cosign signature needs the manifest and the signature artifact, not the package layers. The controller already resolves tag → digest (status.resolvedDigest); verifying against that digest is a small registry read. The controller therefore needs no package-sized disk, which was the only reason to prefer in-Job verification.
  • Content addressing closes the gap between verify and deploy. The Job pulls repository@digest - never a tag - so the artifact that was verified and the artifact that is deployed are the same bytes by construction. There is no re-push window between the controller’s check and the Job’s pull.
  • The trust boundary lands where it should. Unverified content never reaches a pod holding a cluster’s admin kubeconfig; refusal happens before a Job is stamped, as a condition on the release, where an operator looks - not inside a Job log. A pull-in-Job-then-verify ordering would rely on the subcommand sequencing pull, verify, extract correctly inside the same process that later executes package actions.

The deploy subcommand may re-verify on load (LoadOptions.VerifyBlobOptions) as cheap defense in depth; that is an implementation choice, not part of this contract. What is part of it: the rendered spec handed to the Job carries a digest reference, never a tag, and a Job must never be stamped from an unresolved or unverified proxy.

The pod is a pure operator: files in, termination message out

Decided with the verification placement, for the same trust-boundary reason: the deploy pod knows nothing of the management cluster beyond the files on its disk. Its inputs are three mounts - the rendered deploy spec (a per-release Secret the controller writes: digest-pinned package reference, rendered values and variables, component selection), the target cluster’s kubeconfig, and the cache volume. It holds no management-cluster credentials, its service account grants nothing, and it makes no management-cluster API calls - which also settles where rendering runs (the controller, which can read Cluster metadata; the pod cannot and must not). Results return in the pod termination message; the controller reads the finished Job and patches release status. The alternative - the pod patching its own release status - would hand every deploy pod, and therefore every package action, a management-cluster write credential, re-opening the blast radius the Job model exists to close.

Why vendor/ carries two generated osv-scanner.toml files

go mod vendor copies two files into vendor/ that have nothing to do with Go: a requirements-test.txt under github.com/theupdateframework/go-tuf, and a requirements.txt under go.opentelemetry.io/otel. Next to each of them now sits a generated osv-scanner.toml that tells a scanner to skip that ecosystem. This document records why those files exist, why they are generated rather than committed by hand, and what they deliberately do not cover.

What forced it

The OpenSSF Scorecard Vulnerabilities check runs osv-scanner recursively over the whole checkout and scores it in checks/evaluation/vulnerabilities.go as MaxResultScore - numVulnsFound, floored at zero. There is no severity weighting and no reachability analysis: every finding is one point, so three findings and forty score the same. The check read 2 against eight findings, and vendor/ supplied five of them.

ManifestEcosystemFindingsWhat it pins
vendor/github.com/theupdateframework/go-tuf/requirements-test.txtPyPI5The Python harness go-tuf runs its own conformance tests under
vendor/go.opentelemetry.io/otel/requirements.txtPyPI0A codespell pin for otel’s own spelling check

None of it is a CAAPZ dependency. Nothing in those files is compiled, executed, installed or shipped; they are in the tree because they happen to sit in the directory of a module CAAPZ imports Go packages from, and go mod vendor copies directories. The five findings are three advisories against requests==2.31.0 and two against tuf==3.1.0 - true statements about those packages, and false statements about this repository.

The otel row is zero findings today and has an override anyway. A requirements.txt with one package in it is one CVE away from costing a point, and the whole purpose of the arrangement is that a new advisory upstream is not an event here.

Deleting the files does not work, and neither does un-vendoring

rm -rf vendor && go mod vendor puts both back; they are part of what the vendoring step produces. Removing them by hand means removing them again after every dependency bump, and a run of go mod vendor between the removal and the Scorecard run silently undoes it.

Dropping vendor/ entirely would have removed the problem at the root and was never a candidate. The tree is vendored so the repository builds in an air-gapped management cluster with no route to a module proxy; that constraint is the reason vendor/ exists at all, and it is not negotiable for a scorecard point.

The config has to sit beside the manifest

osv-scanner resolves configuration relative to the file it is scanning, not to the root of the scan, and it only consults a single root config when the caller passes ConfigPath. Scorecard’s clients/osv.go builds osvscanner.ScannerActions without one. A single osv-scanner.toml in the repository root therefore changes nothing at all - which is what anyone would try first, and the reason the files are scattered through vendor/ instead of sitting in one obvious place at the top of the repository.

Renovate cannot do this, which is the other thing people try

Renovate is the obvious place to look, because it already owns every dependency bump here. It cannot help, and the reason is worth writing down so nobody re-derives it.

Renovate’s vulnerability surface - vulnerabilityAlerts, osvVulnerabilityAlerts, and the osvVulnerabilitySummary on the dependency dashboard - decides only whether Renovate proposes a bump. Suppressing something in Renovate means a packageRules entry with enabled: false, or ignoreDeps: no justification field, and visible to nothing but Renovate. The Scorecard alert is raised by osv-scanner, which reads osv-scanner.toml and nothing else. Different consumer, so there is no Renovate setting that reaches it.

It is worse than merely unhelpful: .github/renovate.json5 has **/vendor/** in ignorePaths, so Renovate never sees these two files in the first place. A vendored module’s own manifests are upstream’s, not ours to bump.

Ecosystem-wide overrides, not lists of advisory IDs

[[IgnoredVulns]] suppresses named advisories and would work. It was rejected because the claim being made here is not “these particular advisories are harmless”. It is “this ecosystem is not part of the build”, which is a property of the manifest and stays true as the advisory list changes. An ID list would need a commit every time a new CVE landed against a requirements file nobody here reads, and each of those commits would look like a security decision while being pure bookkeeping.

[[PackageOverrides]] with only ecosystem and ignore = true says the intended thing once. Each generated file carries a reason and a comment explaining itself to whoever finds it while reading vendored third-party source.

Generated by mage, not committed by hand

magefiles/pkg/osv/osv.go holds the two entries and the text they render to. dev:writeOSVOverrides writes them; dev:vendor ends with it, so the normal way of updating dependencies leaves them in place without anybody remembering. Committing them as ordinary files was the alternative, and it fails the first time somebody runs dev:vendor and commits the result.

dev:verifyVendor is the guard, and it is wired into both the verify-vendor pre-commit hook and .github/workflows/check-go-mod.yaml. It fails if a declared override is missing or has drifted from the generator, and - the half that matters more - it fails if vendor/ contains a non-Go dependency manifest that no entry covers. Without that second check, a dependency bump that happens to pull in a module carrying a Gemfile.lock would drop the score on some later Scorecard run with nothing in the diff to point at. It fails on the commit that caused it instead. It also fails when a manifest an entry names has gone away, which is what turns a stale entry into a build error rather than a file quietly doing nothing.

check-go-mod.yaml needed a second change for the same reason. Its first step re-runs go mod tidy and go mod vendor and then diffs the result against the tree, which deletes both overrides and reports them as drift. dev:writeOSVOverrides runs between the vendor and the diff; because it is the same target dev:vendor ends with, a properly vendored tree comes out byte-identical and the diff still reports only real changes.

Renovate puts them back with a post-upgrade task, not a workflow

Generating the overrides from dev:vendor assumes the normal way of updating a dependency goes through mage. It does not: Renovate re-runs go mod vendor itself for every gomod update, the recreated tree arrives without the two files, and dev:verifyVendor fails the pull request. With 170-odd indirect updates queued behind prHourlyLimit, that is a hand-written ci: readd the osv scanner artifacts commit on every one of them.

Renovate here is self-hosted, out of .github/workflows/renovate.yaml, and that is what makes the fix a config entry rather than machinery. postUpgradeTasks runs a command in the branch workspace after the updates land, and it is a self-hosted-only feature precisely because it executes arbitrary commands - the hosted app cannot offer it. .github/renovate.json5 names the command and the paths it is allowed to write; the workflow sets RENOVATE_ALLOWED_COMMANDS, because allowedCommands is global-only config that Renovate refuses to read from a repository file. Both halves are required, and a command that does not match the allowlist is skipped with a warning in the log rather than an error.

The sister project cargoship solves the same problem with a pull_request_target workflow that builds a commit through the git data API and pushes it onto the branch, because its bumps come from Dependabot and Dependabot offers no hook of this kind. That is roughly a hundred lines of workflow, a pull_request_target trigger, and a second GitHub App token with write access to pull request branches - all of it avoided here by Renovate being self-hosted. If this repository ever moves back to the hosted Renovate app or to Dependabot, that workflow is the thing to port, because postUpgradeTasks stops working the moment Renovate is not ours.

Two cases are deliberately left to fail. A bump that drops a module entirely leaves no directory to copy into, and a bump that pulls in a module carrying an uncovered lockfile trips the second half of dev:verifyVendor. Both need Overrides edited by a person, so the task cannot fix either and the check reports instead.

What this does not do

It does not raise the check to 10. What remains is Go, and Go is where an override would be wrong: an advisory against a module that is actually in the binary is the thing this check exists to report. Registry credentials reach the controller and the deploy pod by different routes

The controller gets them per call. The deploy pod gets them as a file. That is not an inconsistency to tidy up later - the two consumers sit behind different upstream APIs, and the right answer differs.

This is the same problem cluster-api-provider-cargoship solved in its own choice-registry-credentials.md, and the API here is deliberately named after that one - pullSecretRef, caBundleSecretRef, fromZarfState, insecureSkipTLSVerify - so an operator running both reads one vocabulary. The mechanism diverges, and this records why.

The controller can use the in-process hook; cargoship could not

internal/resolver builds its remote itself, by calling zoci.NewRemote directly. That means zoci.RemoteClientOptions is ours to fill:

type RemoteClientOptions struct {
	CachePath      string
	CredentialFunc auth.CredentialFunc  // nil falls back to the Docker credential store
	Transport      *http.Transport      // proxies and mTLS
	types.RemoteOptions                 // PlainHTTP, InsecureSkipTLSVerify
}

So resolution passes a CredentialFunc built for that one call, and a Transport whose root pool is the system roots plus whatever caBundleSecretRef names. Nothing is process-wide, which matters here in a way it did not for cargoship: this controller reconciles every proxy in the cluster, and two proxies may name two registries with two different credentials. A per-call hook makes that a non-question.

Cargoship had no such hook - distro.Load builds the oras modifier list internally from RemoteOptions alone - so it writes a merged Docker config file on its cache volume and accepts a documented last-writer-wins where two resources name the same registry with different credentials. We do not inherit that shortcut.

The scheme negotiator is scoped per call for the same reason

zoci.NewRemote probes for plain HTTP when PlainHTTP is set, through ocischeme.From(ctx) - a package-level negotiator that caches its answer per registry host for the whole process, failures included for 30 seconds. In a CLI that is right; in this controller it means a proxy that cannot verify a registry’s certificate caches that failure for every other proxy naming the same registry, correctly configured or not. The e2e suite found it the honest way: three cases that should have resolved inherited the refusal of the case that should not have. So internal/resolver installs a negotiator per resolution. The zero TTL is the second half of the same problem - a long-lived process holding a scheme decision forever - and a per-call negotiator answers both.

The deploy pod gets a file, because it has no other way

packager.LoadOptions - what the deploy subcommand calls LoadPackage with - carries types.RemoteOptions and nothing else:

type LoadOptions struct {
	Shasum, Architecture string
	VerifyBlobOptions    *signing.VerifyBlobOptions
	Filter               filters.ComponentFilterStrategy
	// ...
	types.RemoteOptions   // PlainHTTP, InsecureSkipTLSVerify
	layout.VerificationStrategy
}

No credential function, no transport. The fallback oras takes when no credential function is set is the Docker credential store, and getDockerConfigPath() reads $DOCKER_CONFIG before ~/.docker. So the controller writes the credentials into the release’s deploy-spec Secret, the Job mounts it, and the pod’s DOCKER_CONFIG points at the mount. The CA arrives the same way, trusted through SSL_CERT_FILE, which Go’s crypto/x509 honours on Linux.

Two things make the file acceptable here that are worth stating, because “a credential on a disk” is where review attention goes:

  • One pod serves exactly one package. There is no merging, no shared file, and no window where one pull reads another’s credentials - the scoping problem cargoship had to solve with a mutex and a rename does not arise, because the process-wide variable is scoped to a process that exists to perform one pull.
  • The pod is already the blast radius. It mounts the target cluster’s admin kubeconfig. A registry pull credential is strictly less than what it already holds, and the pod runs as 65532 from an image with no shell.

It is also reversible: if LoadOptions ever carries a credential function, the pod uses the same per-call hook the controller does and the file goes away. The mount is the concession, not the design.

fromZarfState reads the management cluster, not the workload cluster

The field exists because the common air-gapped arrangement is a Zarf registry in the management cluster holding the packages the fleet pulls - and Zarf already generated that registry’s credentials and signed its certificate. Both are in that cluster as zarf-state and zarf-registry-server-tls, so making the operator export them by hand into a Secret whose server string has to match the repository host exactly is asking them to copy data that is already there.

Which cluster is the part to get right. Every other Zarf-state read in this controller targets a workload cluster, through the CAPI kubeconfig secret - the init gate, probe-and-adopt, removal. This one reads the controller’s own cluster, because that is where the registry being pulled from lives. A workload cluster’s Zarf registry is not a package source: its address in state is node-local, and nothing in the management cluster can route to it.

The repository is still named in the spec rather than derived from that state, for the reason cargoship found: Zarf records the address a node reaches the registry at, and a controller inside the cluster wants the service address, which the state does not carry.

No client certificate, and that is measured

A Zarf registry reports mTLS in its state for any mtlsStrategy other than none, and the obvious reading - that a client certificate is therefore required - is wrong. Zarf’s registry chart sets clientauth: verify-client-cert-if-given, which verifies a certificate where the client offers one and serves a client that offers none. The certificate Zarf issues belongs to the per-node registry proxy, not to anything a management-cluster controller runs. So the CA out of zarf-registry-server-tls is the whole requirement.

The case this does not cover is a registry that genuinely requires a client certificate - Harbor or Nexus configured for it, or a Zarf registry whose clientauth an operator overrode. That needs a clientCertSecretRef here and, for the deploy pod, somewhere to put it: the pod’s half runs through LoadOptions, which carries no transport, and SSL_CERT_FILE trusts roots rather than presenting a certificate. So it is an upstream change first. Deferred deliberately, not overlooked.

The Zarf package is built from out/, and pins its version everywhere it appears

This repository ships a Zarf v1beta1 package definition, zarf.yaml, for management clusters with no route to ghcr.io - the same environments this provider deploys into are the ones it has to be delivered through. The file mirrors cluster-api-provider-cargoship’s zarf.yaml, and its docs/agent/choice-zarf-package.md is the original of this argument. Two things about it look like oversights and are not.

It deploys out/addon-components.yaml, not the kustomization

Zarf can run kustomize itself - a manifest takes kustomize.files as readily as files - so the package could point at config/default and skip release:manifests entirely. It does not, because then the provider would be assembled two ways: once by release:manifests for the operator who installs with clusterctl, and once by Zarf for the operator in an air gap. Both would be correct on the day they were written and free to drift afterwards. Pointing at the release artifact means the air-gapped install is the same artifact, and release:zarfPackage builds it first so there is nothing to forget.

The one kustomization Zarf does run, manifest/turtle/addon, assembles nothing a second way: it wraps that same out/addon-components.yaml (staged beside it by release:zarfPackage, gitignored there) into the ConfigMap the Cluster API Operator reads a provider out of.

The version and image tags are literals, repeated

###ZARF_PKG_TMPL_...### does not reach an image reference in a v1beta1 package: Zarf parses the reference during validation, which runs before --set is applied, and the create fails with an invalid-reference error - zarf dev lint . reports the same thing, so this is cheap to re-confirm.

So the version is written out as a literal in every file that needs it - zarf.yaml (once as the package version, twice as image tags), manifest/turtle/capi-provider-addon.yaml, manifest/turtle/addon/kustomization.yaml - and release-please rewrites all of them on a release: each file is in extra-files in release-please-config.json, and each pinned line carries the x-release-please-version comment it looks for. Removing one of those comments is silent - the package still builds, pinning a tag a release ago.

release:zarfPackage reads the version back out of zarf.yaml and renders the component manifest at it, rather than taking a tag like release:manifests does. A tag parameter there would produce a package whose manifest names one version and whose image carries another, which fails at deploy time against the in-cluster registry rather than at build time.

What it deliberately leaves out

Core Cluster API, Rancher Turtles, and every Zarf package this provider itself deploys. Each is somebody else’s artifact with its own cadence, and bundling any of them would make this package a mirror of the whole air gap rather than of this provider. The rancher-turtle-artifacts component is optional: true for the related reason recorded inline: its CAPIProvider fails on a cluster without the Turtles CRDs, and the default deploy has to work for the clusterctl-shaped cluster too.
